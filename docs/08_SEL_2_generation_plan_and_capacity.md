## 1. 결론

- 후보 생성 방법은 **2단**이다. 1단은 LLM 1회 작성(가설 → 편집 명령)이고 기준선이다. 2단은 GEPA(반성형 진화)이고, 1단보다 낫다는 것이 **오프라인 비교에서** 확인될 때만 켠다(6장). 1차 오픈(2027.8) 범위에서는 GEPA를 빼자고 제안한다(docs/07 I, docs/09 4.7-13).
- MIPROv2와 GEPA 중 하나를 고른다면 **GEPA**다(3장).
- 켜더라도 같은 finding의 첫 후보는 1회 작성으로 만들고, ③에서 탈락한 2 · 3번째 시도에만 GEPA를 쓴다. 1회 작성은 구현이 단순하고 생성 근거(가설 → 편집 명령)를 승인자가 따라가기 쉬운 기준선이라 먼저 쓰고, 그것으로 안 풀린 finding에만 GEPA를 붙인다. GEPA의 부하는 이 선택의 근거가 아니라 4장 용량 계획에서 다룬다. GEPA가 만든 중간 후보는 draft로만 남고 candidate로 올리지 않으므로(7.1) finding당 후보 3개 상한(③ 유의수준 α/3의 근거)은 그대로다.
- ② 전체에서 **가장 큰 부하는 시험 문제 탐침**(생성 질문을 지금 버전으로 2회씩)이다. GEPA는 "느리지만 가볍다"(4장).
- **LLM Gateway를 위협하는지는 아직 판단할 수 없다.** 모델 호출은 사내 클라우드 LLM Gateway로 간다(기준 문서 6장: Runtime은 LLM 서빙을 하지 않음). 같은 Gateway가 동시 사용자 7천 명 규모(기준 문서 5장)의 운영 트래픽도 받는다. 평가 트래픽이 몰리면 분당 수백만 토큰 규모다. Gateway의 RPS · TPM 쿼터를 확인하기 전에는 결론을 내지 않는다(4장).
- 평가 실행은 eval 모드로, ERP 사용이 적은 시간대에 스케줄러가 돌린다(기준 문서 11장 ③ Tester. SEL 스케줄러 하나의 밤 일정이 SEL 오케스트레이터에 평가 배치를 요청한다, docs/16 4장). 사용자 실행과 분리된 대기열 · 동시 상한은 **[제안 → Runtime]** 이다(선례: ADR-0014 proposed). 기준선은 쓰기 Dry-Run만 명시한다(기준 문서 3.2 · 11장 ③). 조회를 실제 도구로 하는 것은 기준 문서 9장 Dry-Run의 목적("SEL 시험 실행이 업무 데이터를 건드리지 않게")과 2026-09-28 결정(이력)에서 나온 해석이라 확인이 필요하다. 조회가 실제 도구라면 평가 실행도 SAP 읽기 · DBC를 부르고, 그 부하 한도도 협의 대상이다.
- 확정 전에 풀어야 할 의존성은 둘이다(5장 1번): **eval 실행이 릴리스 안 된 버전(draft · candidate)을 가리키는 경로**(`overrides.refs`, 7.1. 인라인 주입은 대안), 그리고 **eval 실행 기록을 ① 분석에서 떼어 내는 규칙**.

## 2. GEPA가 하는 일과 시나리오

GEPA는 Improver 7단계(편집 명령 작성) 하나만 맡는다. "써 보고 → 돌려 보고 → 왜 틀렸는지 읽고 → 고쳐 쓰기"를 예산 안에서 자동으로 반복한다.

| 단계 | 누가 | GEPA와의 관계 |
| --- | --- | --- |
| 무엇을 고칠지 (가설, 대상 섹션) | Creator | 무관 |
| 무엇으로 판정할지 (시험 문제) | Creator 단계의 시험 문제 생성 LLM(finding만 봄) + 하네스(코드) | 무관. **GEPA는 시험 문제를 보지 않는다** |
| 어떻게 고쳐 쓸지 | Improver 7단계 | **GEPA** |
| 바꿔도 되는지 | 거버넌스 검사 | GEPA의 제안 훅 안에서도, 최종 후보에도 적용 |
| 나아졌는지 | ③ 평가 | 무관 |

**시나리오: 미결 조회의 ROW_LIMIT**

1. finding: `skill/fi/open-items@1.4.3`을 쓴 실행에서 `tool_arg_error`(결과 코드 ROW_LIMIT_EXCEEDED) 11%(평소 2%). 실패 서명은 "`fi_open_items_query`에 기간 인자 없음 → ROW_LIMIT_EXCEEDED".
2. Creator: 가설 "기간이 없을 때의 기본 규칙이 없다", 대상 `## 조회 절차` 섹션. 시험 문제 생성 · 검증 · 고정(생성 질문 중 같은 서명으로 2번 다 틀린 목표 문제 + 2번 다 통과한 정상 문제 + 필수 · 정책 고정 세트).
3. 첫 시도(1회 작성): LLM이 편집 명령 하나 → 거버넌스 검사 → candidate 등록 → ③. 통과하면 GEPA는 돌지 않는다.
4. ③ 탈락 → 두 번째 시도에서 GEPA.
   - `seed_candidate = {"skill/fi/open-items#조회 절차": <현재 본문>}`
   - **dev 질문만** 쓴다. 시험 문제 생성 LLM이 시험 문제와 따로 만들고 하네스가 같은 방식으로 거른 질문 20건.
     - 연습용 12건은 **실패 위주**로 고른다. `skip_perfect_score`가 켜져 있으면 다 맞힌 배치에서는 반성을 건너뛰기 때문이다.
     - 비교용 8건에는 정상 질문을 섞는다.
     - ③의 시험 문제는 넣지 않는다.
   - 반성 기록을 만들기 직전에 **그 질문을 노출 원장에 기록**한다. 반성용 LLM이 dev 질문과 그 실행 결과를 보므로, 그 질문이 이후 시험 문제와 겹치지 않게 하기 위해서다. 노출 원장은 GEPA를 넣을 때만 둔다(지금 설계에는 없다, docs/16 10.4).
   - 반복 한 번은 이렇게 돈다.
     1. 연습용 3건을 eval 모드로 실행한다. 이때 중간 후보를 실행에 넣는 방법은 7.1에 있다(권장: Registry에 draft로 등록해 `overrides.refs`로 가리킴. 대안: 등록 없이 인라인 주입, 5장 1번).
     2. 결정적 점수를 매긴다(오류 없음, 서명 소멸, 정책 준수).
     3. 증거 구획을 거친 반성 기록을 만든다(`Inputs` · `Generated Outputs` · `Feedback`).
     4. 사내 LLM이 섹션을 고쳐 쓴다.
     5. **우리 제안 훅**이 편집 명령으로 바꾸고 거버넌스 검사를 한다. diff는 대상 섹션 안으로만 제한하고, 걸리면 버린다.
     6. 같은 3건으로 다시 실행한다.
     7. 엄격히 나아지면 비교용 8건으로 점수를 매겨 후보 풀에 넣는다.
   - `max_metric_calls`(예: 150)에 닿으면 끝난다. 비교용 평균이 가장 높은 후보 **하나**만 나온다.
5. 그 후보를 기준 버전 대비 diff로 다시 검사한다(거버넌스, 그리고 예시가 있으면 "합성 값만").
   - 통과하면 candidate로 등록하고 ③으로 넘긴다.
   - 생성 근거에 남길 것: "GEPA, 반복 n회, 실행 m회, seed, 정책 버전, 가설 대비 변경 요약".

## 3. GEPA로 고른 근거 (확인일 2026.10.28)

| 기준 | MIPROv2 (DSPy) | GEPA |
| --- | --- | --- |
| 하는 일 | predictor별 지시문 + few-shot 예시를 함께 탐색. 예시는 학습 예시를 돌려 **맞게 나온 출력**에서 뽑음. 베이지안 최적화, 미니배치 기본 35 | 실행 궤적과 텍스트 피드백을 LLM이 되돌아보고 지시문을 제안. 사례별 최고 후보를 파레토 프런티어로 유지 |
| 입력 재료 | 정답 있는 예시와 점수 | 실행 기록 + 텍스트 피드백. finding · 실패 서명과 같은 재료 |
| 거버넌스 | 예시를 실제 출력에서 뽑아 "예시는 합성 값만" · 누출 · 등급 규칙과 충돌 | 제안 훅으로 우리 편집 명령 · 검사를 진화 단계 안에 넣을 수 있음 |
| 대상 형식 | DSPy 프로그램 구조 전제 | 임의 텍스트 구성요소(`dict[str, str]`). 스킬 섹션 · 도구 description을 그대로 다룸 |
| 결과 | 최적 조합 하나 | `best_candidate` 하나 |
| 보고된 성능 | — | 논문 v2(2026-02, ICLR 2026): 6개 과제에서 GRPO 대비 평균 +6%, 최대 +20%, rollout 최대 35배 적음. MIPROv2보다 우수(표 1, 기준 대비 개선 Qwen3 8B +9.62 vs +2.61). v1(2025-07)은 4개 과제 평균 +10%였다. 병합(Merge)은 모델에 따라 일부 과제에서 오히려 나빴다(2026-10-29 논문 재확인) |

**gepa 패키지** — PyPI 페이지와 GitHub `main` 브랜치 소스(`api.py`, `core/adapter.py`, `pyproject.toml`)로 확인했다. **0.1.4 태그 소스와는 대조하지 않았다.** 착수 시 고정 버전 소스로 다시 확인하고, 아래 API를 계약 테스트로 묶는다.
- 버전 0.1.4 (PyPI 표기 2026-07-15). 0.x이고 릴리스가 잦다 → `gepa==0.1.4`로 고정.
- Python 3.10~3.14. 기본 의존성 없음(litellm은 선택 extra). MIT.
- DSPy 없이 쓰는 경로: `gepa.optimize(seed_candidate, trainset, valset, adapter, reflection_lm, max_metric_calls, seed, ...)`.
- 어댑터 `GEPAAdapter`: `evaluate(batch, candidate, capture_traces) -> EvaluationBatch(outputs, scores, trajectories, ...)`, `make_reflective_dataset(candidate, eval_batch, components_to_update)`, 선택 `propose_new_texts`. `optimize`에는 `custom_candidate_proposer` 인자도 있다.
- `reflection_lm`은 문자열 또는 callable. 사내 OpenAI 호환 클라이언트를 감싸 넘긴다.
- 예산 `max_metric_calls` · `max_reflection_cost` · `stop_callbacks` 중 하나는 필수.
- 쓸 옵션: `seed`, `acceptance_criterion="strict_improvement"`(기본), `skip_perfect_score`(기본 True), `reflection_minibatch_size`(기본 3), `cache_evaluation`(**optimize 한 번 안에서만**. 실행이 확률적이라 캐시가 분산을 가린다).

**확인하지 못한 것**: 0.1.4 태그의 시그니처, gepa 내부 문자열 모델 해석 방식(callable을 넘기므로 무관), 기본 반성 프롬프트 길이, 논문의 과제별 반성 호출 수.

## 4. 부하 · 토큰 · 속도

### 가정 (전부 추정)

| 항목 | 기본값 | 범위 (민감도) | 근거 |
| --- | --- | --- | --- |
| 실행 1회의 LLM 호출 | 6회 | 4~10 | 판단 → 도구 호출 → 결과 확인을 몇 번 도는 조회 업무 기준 추정 |
| 호출 1회 입력 토큰 | 4,000 | **4,000~10,000** | DeepAgents 시스템 프롬프트, 도구 정의, 누적되는 도구 결과. 조회 결과가 큰 경우(ROW_LIMIT 시나리오) 위쪽 |
| 호출 1회 출력 토큰 | 300 | 200~800 | 도구 호출 인자 · 짧은 답 |
| 실행 1회 시간 | 25초 | 10~40초 | 기준 문서 10장: LLM 판단 10~30초, 홉은 1초 미만 |
| 실행 1회 도구 호출 | 5회 | 3~10 | 조회 위주. Dry-Run 검증이 SAP를 부르는지는 모른다(기준 문서 9장은 "검증 결과만 돌려줌"까지) |
| 반성 호출 1회 | 입력 9,000 / 출력 1,000 | 입력 6,000~20,000 | 현재 섹션(≤ 2,000) + 기록 3건(건당 1,500으로 자름) + 템플릿 |

### 단계별 부하

| 단계 | 실행 수 | LLM 호출 | 입력 토큰 (기본 / 상단) | 벽시계 시간 |
| --- | --- | --- | --- | --- |
| Creator 원인 가설 | 0 | 1~2 | 약 1만 | 1분 이내 |
| **시험 문제 탐침** (시도당, 생성 질문 N × 2회 + 1번만 틀린 질문 3번째) | N=400이면 800 (상한 쪽 가정. sel-lab D01은 N=44 → 88) | **4,800** | **1,920만 / 4,800만** | 동시 100이면 약 3~4분 |
| 1회 작성 | 0 | 1 | 약 1만 | 1분 이내 |
| GEPA (`max_metric_calls=150`) | 150 | 900 + 반성 10~23 | 360만 / 900만 | **약 15~40분** |
| 거버넌스 검사 · 등록 | 0 | 0 | 0 | 초 단위 |

**GEPA 반복 수**
- 시작할 때 seed를 비교용 8건으로 한 번 평가한다. 그 뒤 반복 1회에 실행 `6 + 8p`건이 든다(p = 채택률).
- 반복 수 = (150 − 8) ÷ (6 + 8p)
  - p = 1이면 10회
  - p = 0.5이면 14회
  - p = 0이면 23회
- 반복 1회는 1.5~2분이다(실행은 병렬, 반성은 1회). 그래서 15~40분이 걸린다.

### finding 하나에 드는 것 (②만)

탐침 예산은 "생성 질문 수 × 2회 + 1번만 틀린 질문의 3번째"다(docs/07 C). 탈락 뒤 2 · 3번째 시도에서는 시험 문제를 새로 만들므로 탐침도 시도마다 다시 든다. 예전 안(문제은행에서 고르고 첫 탐침 결과를 72시간 재사용)은 폐기했다.

| 경우 | 실행 | LLM 호출 | 입력 토큰 (기본) |
| --- | --- | --- | --- |
| 첫 시도에 통과 (1회 작성) | 탐침 800 | 약 4,800 | 약 1,920만 |
| 세 번 다 시도 (1회 작성 + GEPA 2번) | 탐침 800 × 3 + GEPA 300 = 2,700 | 약 16,200 + 반성 | 약 6,480만 |

비교: ③의 판정 1회는 목표 86 · 정상 221건 × 3회 + 필수 20건 × 10회를 기존 · 후보 두 번씩(약 2,240회 실행, 실행당 6회) 돌린다고 보면 약 1.35만 호출이다(③ 설계 전 추정. 문제은행 시절의 큰 세트 가정이라 생성 방식의 세트(sel-lab D01 31건)보다 훨씬 크다. 상한 쪽 값으로 둔다). ②의 비용은 **탐침이 대부분**이다.

### 하룻밤 처리량과 Gateway

| 항목 | 계산 | 값 |
| --- | --- | --- |
| 평가 동시 100일 때 RPS | 100 × 6 ÷ 25초 | 약 24 RPS |
| 그때의 TPM (입력) | 24 × 4,000 × 60 | **약 580만 TPM** (상단 10,000이면 약 1,440만) |
| 하룻밤 6시간 창의 처리 (6시간은 가정. 기준 문서은 "ERP 사용이 적은 시간대"까지) | 24 RPS × 21,600초 | 약 52만 호출 |
| finding 하나 (③ 판정 1회 + ② 첫 시도) | 1.35만 + 0.48만 | 약 1.8만 호출 |
| 하룻밤 처리 가능 finding (추정) | 52만 ÷ 1.8만 | 약 25~30건 (재시도 제외) |

이 숫자는 **사내 클라우드 LLM Gateway가 평가 트래픽에 이 정도를 내줄 때**의 이야기다. 사내 서빙에 580만 TPM은 큰 값일 수 있다. 실제 처리량은 Gateway 쿼터가 정한다(쿼터를 누구와 협의하는지는 기준 문서 13장 선행 협의에 없다. 확인 필요). 쿼터가 작으면 동시 수를 줄이고 하룻밤 처리 finding 수가 비례해 준다. 우선순위는 ③ 판정을 먼저, ② 탐침은 그다음, GEPA는 남는 용량으로 둔다 **[제안 → SEL 오케스트레이터]**.

### 문제가 될 수 있는 곳과 대응

| 걱정 | 무엇이 문제인가 | 대응 (제안) |
| --- | --- | --- |
| **eval 실행 기록이 ① 분석을 오염** | 탐침은 일부러 실패할 질문을 돌린다. 그 span이 운영 실패율에 섞이면 finding이 부풀고, 그 finding이 다시 탐침을 부르는 자기강화가 생긴다. 7일 뒤 Verifier도 오염된다. 탐침 1회에 span 약 1만 개 이상 | `run_mode`는 요청 컨텍스트 필드다(기준 문서 3.2). 이것을 필수 span 속성으로도 Protocol v1 `common/span-attributes.md`에 넣고(기준 문서의 erp.* span 속성은 `erp.request_id` · `erp.asset.refs` · `erp.outcome.type` 셋), ① · Verifier는 eval span을 제외한다. eval span을 Phoenix 별도 project로 보낼지 협의 **[협의 → ① · Protocol · 관측 운영]** |
| **탐침이 너무 큼** | 생성 질문 전체를 2회씩 | ① 생성 질문 수 상한(설정) ② 모든 질문 2회(정상은 2회 모두 통과해야 함. 1회로 정하면 흔들리는 질문이 정상으로 들어가 회귀 오탐). 1회만 실패한 질문은 버린다 ③ 생성 LLM에 finding 서명을 줘 같은 서명이 나올 만한 질문 위주로 만든다 |
| **실제 도구 부하** (eval에서도 조회는 실제 도구라는 해석, 1장) | 탐침 800회면 도구 호출 약 4,000회. Dry-Run 검증이 SAP를 부르면 더 늘어남 | ERP 사용이 적은 시간대만(기준 문서 11장), Tools Gateway · DBC에 평가 전용 쿼터, DBC 429면 백오프 **[협의 → Tools Gateway · DBC 담당]** |
| **사용자 속도** | 평가 실행이 같은 Runtime 워커를 잡음 | eval은 별도 대기열 · 낮은 우선순위 · 동시 상한 **[협의 → Runtime 담당]**. 선례: ADR-0014(proposed, 평가 트래픽을 별도 큐 · 우선순위 · 평가 전용 워커 클래스로). 큐 키만 나누면 안 된다. Aegra의 reaper와 Redis 장애 때의 PostgreSQL 폴링이 큐 키를 보지 않아 실행이 섞인다. 그래서 평가는 별도 인스턴스 + 별도 DB로 둔다(위키 Aegra 런타임 동작 근거 1-1) |
| **LLM Gateway 한도** | 위 표. RPS · TPM 모두 확인 필요 | 평가 트래픽 별도 쿼터, 하루 상한, 우선순위(③ > ② 탐침 > GEPA) |
| **데이터가 바뀜** | 탐침 시점과 ③ 시점 사이(월마감 등)에 조회 결과가 달라짐 | 시험 문제는 시도마다 새로 만들어 바로 탐침, 결산 기간에는 간격을 줄임, ③은 기존 · 후보를 같은 시간대에 짝 실행(③ 소관) |
| **실행이 결정적이지 않음** | temperature를 고정해도 같은 입력이 다른 경로를 탐. 탐침 2회와 GEPA의 "3건 엄격 개선"은 노이즈에 흔들림 | 탐침은 시험 문제를 거르는 데만 쓰고 판정은 ③(반복 실행)이 함. GEPA 채택은 비교용 8건 평균으로 확인. 최종 판단은 ③ |
| **GEPA가 느림** | 후보 하나에 15~40분 | 배치 작업이라 허용. finding당 GEPA 2회까지, `max_metric_calls` 상한 |
| **반성 프롬프트가 커짐 · 민감 정보** | 궤적에 실제 SAP · DBC 결과가 들어 있음 | 반성 기록은 증거 구획을 거친 요약만, 건당 1,500 토큰 상한. eval 실행의 `erp_grade_ceiling`은 대상 자산 등급보다 민감한 데이터를 받지 않게(비교는 ① · ②가 같이 쓰는 "민감한 순서" 설정) |
| **궤적 · 탐침 결과 저장** | 위치 · 등급 · 보존이 정해지지 않음 | PostgreSQL(SEL 스키마, SEL 직접 접근), 등급 열, 보존: 탐침 결과는 케이스 종료 + 30일, 궤적은 run ID만 남김(사용자 질문은 쓰지 않음) |
| **출력 잘림 · JSON 깨짐** | 사내 LLM 출력 한도 | 출력은 편집 명령 하나라 짧음. 스키마 검증 실패면 1회 재시도 후 포기 |
| **비용 폭주** | 예산 없이 돌 위험 | gepa는 예산 미지정 시 에러. 정책 파일 `limits`에 finding당 탐침 · GEPA 실행 상한 |

## 5. 설계 순서 (② 전체)

②에서 먼저 설계할 것은 **다른 담당과 맞물리는 경계**와 **모든 생성 방법이 공유하는 바닥**이다. 알고리즘(1회 작성, GEPA)은 그 위에 얹는다.

| 순서 | 설계할 것 | 왜 이 순서인가 | 맞물리는 곳 |
| --- | --- | --- | --- |
| 1 | **② 입출력 계약과 실행 경로 요구사항** — finding 수신 필드, ③ 평가 요청 형식, Registry 등록 · 생성 근거. 그리고 두 가지 요구사항: ⓐ eval 실행이 **릴리스 안 된 버전(draft · candidate)을 가리키는 경로**(`overrides.refs`, 7.1. 인라인 주입은 대안) ⓑ 필수 span 속성 `run_mode`와 ① · Verifier의 eval 제외 규칙 | 상대 일정(Registry v0 12월, Protocol v1 12월 말)에 실려야 함. ⓐ가 없으면 ③(그리고 GEPA)이 후보를 못 돌림. ⓑ가 없으면 ① 분석이 오염됨 | ① · ③ · Registry · Runtime(Runtime · Registry 담당) · Harness(Harness · 오케스트레이터 담당) · Protocol(Protocol 담당) |

## 7. GEPA를 쓸 때의 두 가지 대가와 해결 방안 (제안, 2026.10.30)

GEPA는 거버넌스 원칙 안에서 쓸 수 있다(docs/07 I). 대가가 둘 있다. 등록 안 된 텍스트를 실행하는 경로가 필요하고, ② 안에 작은 평가 루프가 생긴다. 둘 다 아래처럼 풀면 새 예외나 새 실행 체계를 만들지 않아도 된다.

### 7.1 등록 안 된 텍스트 실행 → 중간 후보를 draft로 등록한다

**문제.** GEPA는 중간 후보를 연습 입력으로 돌려 봐야 한다. 지금 안(docs/09 C2 `overrides.inline`)은 등록 안 된 텍스트를 eval 실행에 바로 넣는다. "Registry가 정한 버전만 실행한다"는 원칙의 유일한 예외라서 MUST 5개(4.4-10), 산업보안 승인, 주입 텍스트 별도 보관이 따라온다. 기준 문서에는 없는 경로다.

| 안 | 방법 | 좋은 점 | 나쁜 점 |
| --- | --- | --- | --- |
| **A. draft 등록 (권장)** | 거버넌스 검사를 통과한 중간 후보를 Registry에 **draft로 등록**하고, eval 실행은 `overrides.refs`로 그 draft를 가리킨다. candidate로는 올리지 않는다 | 기준선 안이다(기준 문서 8장 그림 4 "사람 또는 SEL 작성 → draft", `POST .../versions`). 돌린 것이 전부 불변 버전 · 내용 해시로 남아 감사가 Registry 하나로 끝난다. 주입 텍스트 별도 보관 · 인라인 MUST · 산업보안 예외 항목이 없어진다. `overrides.refs`는 ③이 candidate를 돌릴 때 어차피 필요하다(4.4-8, M0) | GEPA 1회에 draft가 10~23개 쌓인다. 버전 번호를 어떻게 매길지 정해야 한다 |
| B. 인라인 주입 (이전 안, 대안) | docs/09 C2 그대로 | Registry 변경이 없다 | 원칙의 예외라 통제 5개와 보안 승인이 필요하다. 감사 대상 텍스트가 SEL 저장소와 Registry 두 곳으로 갈린다 |
| C. 오프라인에서만 GEPA | 실제 Runtime 대신 sel-lab 같은 모의 도구로 진화 | 운영 경로가 필요 없다 | 실제 도구 · 프롬프트와 동작이 달라 진화 결과를 믿기 어렵다. 방법 비교(6장)에는 쓴다 |

A를 하려면 정할 것:

| 항목 | 제안 | 상대 |
| --- | --- | --- |
| 번호 | 중간 후보는 semver pre-release로 매긴다: `@1.5.0-sel.0007.3`(케이스 · 순번). semver 규칙상 `1.5.0`보다 앞 순서라 minor 번호를 소모하지 않는다. 최종 후보만 `1.5.0`으로 candidate 등록한다. 번호는 Registry가 배정한다(4.4-15와 같은 이유). Registry v0가 pre-release 표기를 받는지는 확인 필요 | Runtime · Registry 담당 |
| 상태 | 중간 draft는 candidate로 올리지 않는다. 그림 4에는 draft를 치우는 전이가 없으므로 지우지 않고, `source: sel-gepa` 표시로 목록 · ④ 화면에서 숨긴다. 불변 버전이라 그대로 감사 기록이 된다 | Runtime · Registry 담당 · ④ |
| 실행 | `overrides.refs`는 `run_mode = eval`이고 SEL 주체일 때만 릴리스되지 않은 ref(draft · candidate)를 해석한다. ③이 candidate를 돌리는 규칙과 같다 | Runtime · Registry 담당 · Harness · 오케스트레이터 담당 |
| 검사 시점 | 중간 후보도 등록 전에 ② 거버넌스 검사를 통과해야 한다(2장 반복의 5단계). Registry의 스키마 · 린트는 draft → candidate 때 돌므로 중간 draft에는 ② 검사가 유일한 문이다 | ② |
| 부하 | GEPA 1회당 Registry 등록 10~23건(Registry가 DBC를 거쳐 씀, 기준 문서 8장). 탐침 실행 수백 건에 비하면 작다 | — |

A가 받아들여지면 docs/09의 인라인 관련 항목(C2 `overrides.inline`, 4.4-3 인라인 표기, 4.4-10 인라인 MUST 5개, 산업보안 예외)은 B를 대안으로만 남기고 내린다.

### 7.2 ② 안의 평가 루프 → 실행은 ③ 경로, ②는 채점 함수와 예산표만

**문제.** GEPA는 "돌려 보고 → 점수 매기고 → 고쳐 쓰기"를 반복한다. ②가 실행 · 채점 · 상한을 따로 만들면 ③ Tester와 겹치는 실행 체계가 하나 더 생기고, 비용 계측이 두 곳으로 갈린다.

②가 갖는 것은 세 가지뿐이다.

| ②가 갖는 것 | 내용 |
| --- | --- |
| GEPA 어댑터 | `GEPAAdapter`의 실행 단계에서 Runtime을 직접 부르지 않는다. docs/09 C2 eval 요청(`purpose: gepa`)을 ③과 같은 실행 경로(대기열 · 동시 상한 · 비용 계측)로 보내고, 결과는 C2 결과(구조 정보만)로 받는다 |
| 결정적 채점 함수 | 점수 = 결과 코드가 성공인가 · finding 서명이 사라졌나 · 정책 케이스를 지켰나. GEPA가 반성에 쓰는 텍스트 피드백도 이 구조 정보로만 만든다(사용자 질문 · 도구 결과 본문이 없어 등급 문제가 없다). judge는 쓰지 않는다 |
| 예산표 | 아래 상한을 SEL 원장에 두고 오케스트레이터가 집행한다. GEPA 설정값(`max_metric_calls`)에만 기대지 않는다 |

| 상한 | 값 (제안) | 넘으면 |
| --- | --- | --- |
| GEPA 1회 | 실행 150회(`max_metric_calls`), 벽시계 60분, 입력 토큰 900만(4장 상단) | 그때까지의 최선 후보 하나로 끝낸다 |
| finding 1개 | GEPA 2회(2 · 3번째 시도에만) = 실행 300회 | 더 돌리지 않는다(후보 3개 상한과 같은 자리) |
| 하룻밤 전체 | eval 쿼터의 20% 이내. 우선순위는 ③ > ② 탐침 > GEPA(4장) | GEPA 작업을 다음 밤으로 미룬다 |
| 개선 없음 | 연속 4회 반복에서 비교용 점수가 오르지 않음 | 조기 종료. 구현 방법(gepa의 중단 조건 API)은 착수 시 버전에서 확인 |
| 플랫폼 오류 | 한 반복에서 timeout · 429 · 권한 거부가 연습 실행의 1/3 이상 | 그 반복을 버리고 1회 재시도, 또 나면 GEPA 중단. 인프라 잡음에 맞춰 진화하지 않게 |

**집행.** eval 요청마다 `sel.case_id` · `sel.purpose = gepa`가 실리고(C2, span `erp.sel.*`), ②는 결과를 받을 때마다 원장의 사용량을 올린다. 오케스트레이터는 다음 요청을 보내기 전에 원장을 보고 상한을 넘으면 보내지 않는다. 사후 점검은 span의 `erp.sel.purpose`로 한다.

**나뉘는 것.** 실행기와 대기열은 ③(TBD) 소유, 어댑터 · 채점 함수 · 예산 상한은 ② 소유, 집행은 SEL 오케스트레이터. ③이 배정되기 전에는 sel-lab의 `tester.py`가 실행기 자리를 대신한다.

### 7.3 남는 것

- A와 7.2 모두 `overrides.refs`(4.4-8, M0 차단)에 기댄다. 이것이 정해지면 GEPA는 새 예외 없이 기준선 안에서 돈다.
- 1차 오픈에서 GEPA를 뺄지(1장)는 그대로 남는다. 위 안은 "넣는다면 이렇게"이고, 넣을지는 오프라인 비교(6장)와 PM 결정이 정한다.
