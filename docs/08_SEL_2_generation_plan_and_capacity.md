## 1. 결론

- 후보 생성 방법은 **2단**이다. 1단은 LLM 1회 작성(가설 → 편집 명령)이고 기준선이다. 2단은 GEPA(반성형 진화)이고, 1단보다 낫다는 것이 **오프라인 비교에서** 확인될 때만 켠다(6장).
- MIPROv2와 GEPA 중 하나를 고른다면 **GEPA**다(3장).
- 켜더라도 같은 finding의 첫 후보는 1회 작성으로 만들고, ③에서 탈락한 2 · 3번째 시도에만 GEPA를 쓴다. 비용을 어려운 finding에만 쓰기 위해서다. GEPA가 만든 내부 후보는 등록하지 않으므로 finding당 후보 3개 상한(③ 유의수준 α/3의 근거)은 그대로다.
- ② 전체에서 **가장 큰 부하는 기준 실패 탐침**이다. GEPA는 "느리지만 가볍다"(4장).
- **LLM Gateway를 위협하는지는 아직 판단할 수 없다.** 평가 트래픽이 몰리면 분당 수백만 토큰 규모다. 사내 Gateway의 RPS · TPM 쿼터를 확인하기 전에는 결론을 내지 않는다(4장).
- 평가 실행은 업무량이 적은 시간에 eval 모드로, 사용자 실행과 분리된 대기열 · 동시 상한 안에서 한다. Q5(평가를 실제 도구로 하는지)가 실제 도구로 정해지면 평가 실행도 SAP 읽기 · DBC를 부르므로, 그 부하 한도도 협의 대상이다.
- 확정 전에 풀어야 할 의존성은 둘이다(5장 1번): **등록하지 않은 텍스트를 eval 실행에 주입하는 경로**, 그리고 **eval 실행 기록을 ① 분석에서 떼어 내는 규칙**.

## 2. GEPA가 하는 일과 시나리오

GEPA는 Improver 7단계(후보 작성) 하나만 맡는다. "써 보고 → 돌려 보고 → 왜 틀렸는지 읽고 → 고쳐 쓰기"를 예산 안에서 자동으로 반복한다.

| 단계 | 누가 | GEPA와의 관계 |
| --- | --- | --- |
| 무엇을 고칠지 (가설, 대상 섹션) | Creator | 무관 |
| 무엇으로 판정할지 (시험 문제) | Creator의 결정적 코드 | 무관. **GEPA는 시험 문제를 보지 않는다** |
| 어떻게 고쳐 쓸지 | Improver 7단계 | **GEPA** |
| 바꿔도 되는지 | 거버넌스 검사 | GEPA의 제안 훅 안에서도, 최종 후보에도 적용 |
| 나아졌는지 | ③ 평가 | 무관 |

**시나리오: 미결 조회의 ROW_LIMIT**

1. finding: `skill/fi/open-items@1.4.3`을 쓴 실행에서 `tool_error`(ROW_LIMIT) 11%(평소 2%). 실패 서명은 "`fi_open_items_query`에 기간 인자 없음 → ROW_LIMIT".
2. Creator: 가설 "기간이 없을 때의 기본 규칙이 없다", 대상 `## 조회 절차` 섹션. 시험 문제 고정(같은 서명 실패 34건 + 정상 120건).
3. 첫 시도(1회 작성): LLM이 편집 명령 하나 → 거버넌스 검사 → candidate 등록 → ③. 통과하면 GEPA는 돌지 않는다.
4. ③ 탈락 → 두 번째 시도에서 GEPA.
   - `seed_candidate = {"skill/fi/open-items#조회 절차": <현재 본문>}`
   - **dev 입력만** 쓴다. 이미 노출 원장에 오른 입력(Creator가 본 증거, dev 쪽 스킬 케이스)에서 20건.
     - 연습용 12건은 **실패 위주**로 고른다. `skip_perfect_score`가 켜져 있으면 다 맞힌 배치에서는 반성을 건너뛰기 때문이다.
     - 비교용 8건에는 정상 입력을 섞는다.
     - ③의 시험 문제는 넣지 않는다.
   - 반성 기록을 만들기 직전에 **그 입력을 노출 원장에 기록**한다. 반성용 LLM은 Creator와 같은 역할이기 때문이다. 이미 노출된 입력만 쓰므로 원장이 새로 늘지는 않는 것이 정상이고, 늘면 경보를 낸다.
   - 반복 한 번은 이렇게 돈다.
     1. 연습용 3건을 eval 모드로 실행한다. 이때 중간 후보 텍스트는 Registry에 등록하지 않고 **인라인 주입**한다(5장 1번).
     2. 결정적 점수를 매긴다(오류 없음, 서명 소멸, 정책 준수).
     3. 증거 구획을 거친 반성 기록을 만든다(`Inputs` · `Generated Outputs` · `Feedback`).
     4. 사내 LLM이 섹션을 고쳐 쓴다.
     5. **우리 제안 훅**이 편집 명령으로 바꾸고 거버넌스 검사를 한다. diff는 대상 섹션 안으로만 제한하고, 걸리면 버린다.
     6. 같은 3건으로 다시 실행한다.
     7. 엄격히 나아지면 비교용 8건으로 점수를 매겨 후보 풀에 넣는다.
   - `max_metric_calls`(예: 150)에 닿으면 끝난다. 비교용 평균이 가장 높은 후보 **하나**만 나온다.
5. 그 후보를 기준 버전 대비 diff로 다시 검사한다(거버넌스, 그리고 예시가 있으면 "합성 값만").
   - 통과하면 candidate로 등록하고 ③으로 넘긴다.
   - 생성 근거에 남길 것: "GEPA, 반복 n회, 실행 m회, seed, 정책 버전, 가설 대비 변경 요약".

## 3. GEPA로 고른 근거 (확인일 2026.10.28)

| 기준 | MIPROv2 (DSPy) | GEPA |
| --- | --- | --- |
| 하는 일 | predictor별 지시문 + few-shot 예시를 함께 탐색. 예시는 학습 예시를 돌려 **맞게 나온 출력**에서 뽑음. 베이지안 최적화, 미니배치 기본 35 | 실행 궤적과 텍스트 피드백을 LLM이 되돌아보고 지시문을 제안. 사례별 최고 후보를 파레토 프런티어로 유지 |
| 입력 재료 | 정답 있는 예시와 점수 | 실행 기록 + 텍스트 피드백. finding · 실패 서명과 같은 재료 |
| 거버넌스 | 예시를 실제 출력에서 뽑아 "예시는 합성 값만" · 누출 · 등급 규칙과 충돌 | 제안 훅으로 우리 편집 명령 · 검사를 진화 단계 안에 넣을 수 있음 |
| 대상 형식 | DSPy 프로그램 구조 전제 | 임의 텍스트 구성요소(`dict[str, str]`). 스킬 섹션 · 도구 description을 그대로 다룸 |
| 결과 | 최적 조합 하나 | `best_candidate` 하나 |
| 보고된 성능 | — | 논문: 4개 과제에서 GRPO 대비 평균 +10%, 최대 +20%, rollout 최대 35배 적음. MIPROv2 대비 +10% 이상 |

**gepa 패키지** — PyPI 페이지와 GitHub `main` 브랜치 소스(`api.py`, `core/adapter.py`, `pyproject.toml`)로 확인했다. **0.1.4 태그 소스와는 대조하지 않았다.** 착수 시 고정 버전 소스로 다시 확인하고, 아래 API를 계약 테스트로 묶는다.
- 버전 0.1.4 (PyPI 표기 2026-07-15). 0.x이고 릴리스가 잦다 → `gepa==0.1.4`로 고정.
- Python 3.10~3.14. 기본 의존성 없음(litellm은 선택 extra). MIT.
- DSPy 없이 쓰는 경로: `gepa.optimize(seed_candidate, trainset, valset, adapter, reflection_lm, max_metric_calls, seed, ...)`.
- 어댑터 `GEPAAdapter`: `evaluate(batch, candidate, capture_traces) -> EvaluationBatch(outputs, scores, trajectories, ...)`, `make_reflective_dataset(candidate, eval_batch, components_to_update)`, 선택 `propose_new_texts`. `optimize`에는 `custom_candidate_proposer` 인자도 있다.
- `reflection_lm`은 문자열 또는 callable. 사내 OpenAI 호환 클라이언트를 감싸 넘긴다.
- 예산 `max_metric_calls` · `max_reflection_cost` · `stop_callbacks` 중 하나는 필수.
- 쓸 옵션: `seed`, `acceptance_criterion="strict_improvement"`(기본), `skip_perfect_score`(기본 True), `reflection_minibatch_size`(기본 3), `cache_evaluation`(**optimize 한 번 안에서만**. 실행이 확률적이라 캐시가 분산을 가린다).

**확인하지 못한 것**: 0.1.4 태그의 시그니처, gepa 내부 문자열 모델 해석 방식(callable을 넘기므로 무관), 기본 반성 프롬프트 길이, 논문의 과제별 반성 호출 수.

## 4. 부하 · 토큰 · 속도

### 가정 (전부 추정)

| 항목 | 기본값 | 범위 (민감도) | 근거 |
| --- | --- | --- | --- |
| 실행 1회의 LLM 호출 | 6회 | 4~10 | 판단 → 도구 호출 → 결과 확인을 몇 번 도는 조회 업무 기준 추정 |
| 호출 1회 입력 토큰 | 4,000 | **4,000~10,000** | DeepAgents 시스템 프롬프트, 도구 정의, 누적되는 도구 결과. 조회 결과가 큰 경우(ROW_LIMIT 시나리오) 위쪽 |
| 호출 1회 출력 토큰 | 300 | 200~800 | 도구 호출 인자 · 짧은 답 |
| 실행 1회 시간 | 25초 | 10~40초 | 기준 문서: LLM 판단 10~30초, 홉은 1초 미만 |
| 실행 1회 도구 호출 | 5회 | 3~10 | 조회 위주. Dry-Run도 SAP 검증 호출을 만든다 |
| 반성 호출 1회 | 입력 9,000 / 출력 1,000 | 입력 6,000~20,000 | 현재 섹션(≤ 2,000) + 기록 3건(건당 1,500으로 자름) + 템플릿 |

### 단계별 부하

| 단계 | 실행 수 | LLM 호출 | 입력 토큰 (기본 / 상단) | 벽시계 시간 |
| --- | --- | --- | --- | --- |
| Creator 원인 가설 | 0 | 1~2 | 약 1만 | 1분 이내 |
| 재현 실행 (내용이 지워진 실패만) | 10 | 60 | 24만 / 60만 | 1분 이내 (병렬) |
| **기준 실패 탐침** (finding당, 후보 풀 N × 최대 2회) | N=400이면 최대 **800** | **4,800** | **1,920만 / 4,800만** | 동시 100이면 약 3~4분 |
| 1회 작성 | 0 | 1 | 약 1만 | 1분 이내 |
| GEPA (`max_metric_calls=150`) | 150 | 900 + 반성 10~23 | 360만 / 900만 | **약 15~40분** |
| 거버넌스 검사 · 등록 | 0 | 0 | 0 | 초 단위 |

**GEPA 반복 수**
- 시작할 때 seed를 비교용 8건으로 한 번 평가한다. 그 뒤 반복 1회에 실행 `6 + 8p`건이 든다(p = 채택률).
- 반복 수 = (150 − 8) ÷ (6 + 8p)
  - p = 1이면 10회
  - p = 0.5이면 14회
  - p = 0이면 23회
- 반복 1회는 1.5~2분이다(실행은 병렬, 반성은 1회). 그래서 15~40분이 걸린다.

### finding 하나에 드는 것 (②만)

탐침 예산은 **finding 단위**로 센다(docs/07과 같음). 같은 finding의 2 · 3번째 시도에서는 첫 탐침 결과를 재사용하고 새로 노출된 입력만 뺀다. 재사용에는 유효기간을 둔다(제안 72시간). 기간이 지났거나 결과 코드가 데이터에 따라 달라지는 신호(조회 건수 등)면 다시 탐침하고, 그 실행도 같은 상한 안에서 센다.

| 경우 | 실행 | LLM 호출 | 입력 토큰 (기본) |
| --- | --- | --- | --- |
| 첫 시도에 통과 (1회 작성) | 탐침 800 | 약 4,800 | 약 1,920만 |
| 세 번 다 시도 (1회 작성 + GEPA 2번) | 탐침 800 + GEPA 300 = 1,100 | 약 6,600 + 반성 | 약 2,640만 |

비교: ③의 판정 1회는 목표 86 · 정상 221건 × 3회 + 필수 20건 × 10회를 기존 · 후보 두 번씩(약 2,240회 실행, 실행당 6회) 돌린다고 보면 약 1.35만 호출이다(③ 설계 전 추정). ②의 비용은 **탐침이 대부분**이다.

### 하룻밤 처리량과 Gateway

| 항목 | 계산 | 값 |
| --- | --- | --- |
| 평가 동시 100일 때 RPS | 100 × 6 ÷ 25초 | 약 24 RPS |
| 그때의 TPM (입력) | 24 × 4,000 × 60 | **약 580만 TPM** (상단 10,000이면 약 1,440만) |
| 하룻밤 6시간 창의 처리 | 24 RPS × 21,600초 | 약 52만 호출 |
| finding 하나 (③ 판정 1회 + ② 첫 시도) | 1.35만 + 0.48만 | 약 1.8만 호출 |
| 하룻밤 처리 가능 finding (추정) | 52만 ÷ 1.8만 | 약 25~30건 (반복 · 재탐침 제외) |

이 숫자는 **Gateway가 평가 트래픽에 이 정도를 내줄 때**의 이야기다. on-prem 사내 서빙에 580만 TPM은 큰 값일 수 있다. 실제 처리량은 Gateway 쿼터가 정한다. 쿼터가 작으면 동시 수를 줄이고 하룻밤 처리 finding 수가 비례해 준다. 우선순위는 ③ 판정을 먼저, ② 탐침은 그다음, GEPA는 남는 용량으로 둔다 **[제안 → SEL 오케스트레이터]**.

### 문제가 될 수 있는 곳과 대응

| 걱정 | 무엇이 문제인가 | 대응 (제안) |
| --- | --- | --- |
| **eval 실행 기록이 ① 분석을 오염** | 탐침은 일부러 실패할 입력을 고른다. 그 span이 운영 실패율에 섞이면 finding이 부풀고, 그 finding이 다시 탐침을 부르는 자기강화가 생긴다. 7일 뒤 Verifier도 오염된다. 탐침 1회에 span 약 1만 개 이상 | `run_mode`를 필수 span 속성으로 Protocol v1에 넣고, ① · Verifier는 eval span을 제외한다. eval span을 Phoenix 별도 project로 보낼지 협의 **[협의 → ① · Protocol · 관측 운영]** |
| **탐침이 너무 큼** | 후보 풀 전체를 2회씩 | ① 풀 표본 N ≤ 200 ② 모든 입력 2회(정상 입력은 2회 모두 통과해야 함. 1회로 정하면 흔들리는 입력이 정상으로 들어가 회귀 오탐), 2회 중 1회만 실패한 경계 입력만 3회째 ③ finding 안에서는 재사용(유효기간 72시간) ④ 서명이 정해진 신호는 서명이 맞을 만한 후보만. (docs/10 W9-2 기준) |
| **실제 도구 부하** (Q5가 실제 도구일 때) | 탐침 800회면 도구 호출 약 4,000회, Dry-Run도 SAP 검증 호출 | 업무량이 적은 시간대만, Tools Gateway · DBC에 평가 전용 쿼터, DBC 429면 백오프 **[협의 → Tools Gateway · DBC 담당]** |
| **사용자 속도** | 평가 실행이 같은 Runtime 워커를 잡음 | eval은 별도 대기열 · 낮은 우선순위 · 동시 상한 **[협의 → Runtime 담당]** |
| **LLM Gateway 한도** | 위 표. RPS · TPM 모두 확인 필요 | 평가 트래픽 별도 쿼터, 하루 상한, 우선순위(③ > ② 탐침 > GEPA) |
| **데이터가 바뀜** | 탐침 시점과 ③ 시점 사이(월마감 등)에 조회 결과가 달라짐 | 재사용 유효기간, 결산 기간에는 재탐침, ③은 기존 · 후보를 같은 시간대에 짝 실행(③ 소관) |
| **실행이 결정적이지 않음** | temperature를 고정해도 같은 입력이 다른 경로를 탐. 탐침 2회와 GEPA의 "3건 엄격 개선"은 노이즈에 흔들림 | 탐침은 선정용일 뿐 판정은 ③(반복 실행)이 함. GEPA 채택은 비교용 8건 평균으로 확인. 최종 판단은 ③ |
| **GEPA가 느림** | 후보 하나에 15~40분 | 배치 작업이라 허용. finding당 GEPA 2회까지, `max_metric_calls` 상한 |
| **반성 프롬프트가 커짐 · 민감 정보** | 궤적에 실제 SAP · DBC 결과가 들어 있음 | 반성 기록은 증거 구획을 거친 요약만, 건당 1,500 토큰 상한. eval 실행의 `erp_grade_ceiling`은 대상 자산 등급 이하 |
| **궤적 · 탐침 결과 저장** | 위치 · 등급 · 보존이 정해지지 않음 | PostgreSQL(SEL 스키마, DBC 경유), 등급 열, 보존: 탐침 결과는 유효기간 + 30일, 궤적은 run ID만 남기고 원문은 Phoenix 참조 |
| **출력 잘림 · JSON 깨짐** | 사내 LLM 출력 한도 | 출력은 편집 명령 하나라 짧음. 스키마 검증 실패면 1회 재시도 후 포기 |
| **비용 폭주** | 예산 없이 돌 위험 | gepa는 예산 미지정 시 에러. 정책 파일 `limits`에 finding당 탐침 · GEPA 실행 상한 |

## 5. 설계 순서 (② 전체)

②에서 먼저 설계할 것은 **다른 담당과 맞물리는 경계**와 **모든 생성 방법이 공유하는 바닥**이다. 알고리즘(1회 작성, GEPA)은 그 위에 얹는다.

| 순서 | 설계할 것 | 왜 이 순서인가 | 맞물리는 곳 |
| --- | --- | --- | --- |
| 1 | **② 입출력 계약과 실행 경로 요구사항** — finding 수신 필드, ③ 평가 요청 형식, Registry 등록 · 생성 근거. 그리고 두 가지 요구사항: ⓐ eval 실행에 **등록하지 않은 텍스트를 인라인 주입**하는 경로(eval 전용, 감사 기록, 등록 안 함) ⓑ 필수 span 속성 `run_mode`와 ① · Verifier의 eval 제외 규칙 | 상대 일정(Registry v0 12월, Protocol v1 12월 말)에 실려야 함. ⓐ가 없으면 탐침 · GEPA · ③ 모두 후보를 못 돌림. ⓑ가 없으면 ① 분석이 오염됨 | ① · ③ · Registry 담당 · Harness · Runtime 담당 · Protocol 담당 |
| 2 | **편집 대상 주소와 편집 명령 형식** — `asset ref + #섹션` / `+ 필드 경로`, `replace_section` · `set`, 적용기 | 거버넌스 허용목록 · GEPA `seed_candidate` · 인라인 주입 · 생성 근거 diff가 모두 이 주소를 씀 | Registry 자산 스키마 |
| 3 | **증거 구획 규칙** — 범위를 운영 증거와 **eval 궤적(GEPA 반성 기록 포함)** 까지로. 허용 필드, 지시문 의심 패턴, 등급 처리 | 외부 텍스트가 LLM으로 들어가는 모든 경로의 선행조건. 5(피드백)의 전제 | ① 전처리 |
| 4 | **거버넌스 정책 파일 v0** — 2의 주소로 쓴 허용목록, 내용 규칙, 한도(후보 수 · finding당 실행 상한) | ②의 핵심 산출물. 진화 중 필터와 최종 검사의 기준 | Registry 전이 검사(협의안) |
| 5 | **점수와 피드백 정의** — 실행 1건 → 점수(결과 코드, 서명 소멸, 정책), 피드백 틀(3을 거친 필드만) | 1회 작성 기준선과 GEPA `evaluate` · `make_reflective_dataset`이 공유 | Harness 결과 코드 |
| 6 | **시험 문제 선정 · 노출 원장** — dev와 시험 문제의 경계, 반성 입력의 노출 기록, 탐침 규모 · 재사용 · 상한 | 부하의 대부분이 여기. GEPA에 넣을 데이터와 ③에 넘길 데이터가 여기서 갈림 | ③ 최소 규모 · MDI |
| 7 | **Creator 가설 출력 스키마와 프롬프트** | 1~6이 정해져야 입력 · 출력이 고정됨 | — |
| 8 | **생성 방법** — 1회 작성 기준선 → GEPA 어댑터(제안 훅에 2 · 4 연결) → 오프라인 비교 | 바닥 위에 얹는 부분 | — |

1 · 2는 이번 주에 시작할 수 있다(상대 의존 없이 요구사항 · 형식을 먼저 쓰고 협의를 건다). 3 · 4는 11월, 5 · 6은 12월 초, 7 · 8은 12월 원칙 초안과 P3다.

## 6. 언제 무엇을 재나

| 시점 | 잴 수 있는 것 | 못 재는 것 |
| --- | --- | --- |
| 12월 (sel-lab, 가짜 자산 · 가짜 도구) | 1회 작성과 GEPA의 **LLM 쪽** 비용(작성 · 반성 토큰), 결함 주입 세트에서의 원인 적중률 · 후보 품질 비교, 거버넌스 차단율 | 실제 Runtime · 도구에서의 실행 시간, 실제 토큰(실제 시스템 프롬프트 · 도구 결과 크기) |
| P2 (2027.1~3, Runtime · Gateway 연동 이후) | 실제 eval 실행 1회의 호출 수 · 토큰 · 시간, Gateway 쿼터 안에서의 동시 수 | 실사용 finding 규모 |
| P3 (2027.2~5) | 탐침 · GEPA의 실제 비용, 하룻밤 처리 finding 수 | — |

**1회 작성과 GEPA의 비교는 sel-lab이나 별도 오프라인 세트에서 한다.** 실제 루프에서 비교하면 GEPA는 1회 작성이 탈락한 어려운 finding에만 쓰이므로 같은 조건의 비교가 안 되고, finding당 후보 상한도 소모한다.
