# M0 미결 질문 4개: 답에 따른 설계 분기

작성 2026-10-27 · v0.2 (독립 리뷰 반영) · 대상: [SEL 샌드박스 PRD v0.1](01_PRD_SEL-sandbox-eval_v0.1.md)

네 질문 모두 아직 답이 없다. 각 질문마다 나올 수 있는 답을 경우로 나누고, 경우별로 PRD의 어느 부분(A·B·C, M0–M4, 지표, 결정 D1–D8)이 어떻게 바뀌는지 적는다. 답이 오기 전에 작업을 진행하려면 기준이 필요하므로 질문마다 "답 전 기본 가정"을 둔다.

기본 가정은 **틀렸을 때 버려지는 작업이 가장 적은 쪽**으로 골랐다. 이 기준이 항상 비관적인 쪽과 같지는 않다. 그래서 가정마다 틀렸을 때 무엇이 버려지는지 함께 적는다.

질문마다 답할 수 있는 사람이 다르다. 설계자에게만 보내면 "모름"이 돌아올 수 있다. 그래서 질문마다 받는 사람을 적었다. 담당자를 모르는 경우에는 설계자에게 "누구에게 물으면 되는가"를 함께 묻는다.

## Q1. 비운영 SAP 클라이언트(QA/dev)가 있는가

**정확히 물을 것**

| # | 질문 | 받는 사람 |
| --- | --- | --- |
| ① | 클라이언트가 있는지, 담당자는 누구인지 | SAP Basis |
| ② | 데이터 출처: 운영 복사본인지, 마스킹·익명화된 복사본인지, 비어 있는지 | SAP Basis |
| ③ | 운영 복사로 갱신(refresh)하는 주기와, 그 대상에서 빠질 수 있는지 | SAP Basis |
| ④ | 같은 클라이언트에 다른 팀 데이터가 있는지. 우리 회사코드로만 권한이 제한된 기술 사용자(F_BKPF_BUK 등 권한 객체)를 받을 수 있는지 | SAP Basis, 보안 파트 |
| ⑤ | 운영과 네트워크·계정이 분리돼 있는지(RFC destination, 공유 계정 여부) | SAP Basis, 보안 파트 |
| ⑥ | 운영 도구 구현을 destination 설정만 바꿔서 QA로 향하게 할 수 있는지 | 도구 담당 |
| ⑦ | 최종 상태를 읽을 경로가 있는지(RFC, OData, 테이블 조회 권한) | SAP Basis |

### 1-a. 쓸 수 있다: 아래 세 조건을 모두 충족

조건은 세 가지다. 하나라도 빠지면 1-b나 1-c로 간다.
- (가) 전용 클라이언트이거나, 우리 회사코드로만 권한이 제한된 사용자를 쓴다. 그래야 거래처 이름 검색 같은 조회에서 다른 팀 데이터(운영 복사본일 수 있음)가 섞여 나오지 않는다. 이 샌드박스는 비즈니스 영역에 공개되므로 섞이면 누출이다.
- (나) refresh 대상에서 빠진다. 빠지지 않으면 refresh 때마다 합성 데이터가 지워지고 실데이터가 들어온다.
- (다) 운영과 네트워크·계정이 분리돼 있다.

**이때 바뀌는 것**

- **원칙 4(op 동작 검증)는 조건부로만 줄어든다.** 에이전트는 SAP를 직접 부르지 않고 Tool op를 부른다. 필터 의미, row limit, 페이지네이션 중 상당 부분은 도구 구현에 있다.
  - 실제 도구 구현을 QA destination으로 실행할 수 있으면(질문 ⑥) 원칙 4의 대부분이 필요 없어진다.
  - 도구 계층을 우리가 다시 만들고 백엔드만 QA로 바꾸면 운영과의 차이는 그대로 남는다.
- **B2**: "합성 SAP 백엔드 구현"이 "QA에 합성 데이터를 넣는 적재기"로 바뀐다.
  - 테이블에 직접 넣을 수 없다. BAPI(예: `BAPI_ACC_DOCUMENT_POST`)로 전기해야 한다.
  - 계정 결정, 회계연도 variant, 세금코드, 필수 필드를 QA 설정에 맞춰야 한다.
  - mock용으로 만든 엔티티 모델은 재사용하지만, SAP 설정에 맞춘 보정이 추가된다.
- **C2 Gateway**: "SAP 자격증명 없음" 원칙을 그대로 지킬 수 없다. Gateway가 QA 전용 자격증명을 가지게 된다.
  - 안전 근거를 "운영 자격증명이 없고, 네트워크상 운영 SAP에 닿지 않는다"로 바꾼다.
  - 보안 파트가 다시 검토해야 한다.
  - 열리는 경로는 샌드박스 Gateway → QA뿐이다. 에이전트 쪽 허용 목록은 PRD C1b 그대로다.
- **격리와 채점**
  - M2a(조회 업무): 세계가 바뀌지 않으므로 에피소드 격리가 필요 없다.
  - 쓰기 업무(M2b): SAP는 에피소드마다 스냅샷을 띄우고 버리는 방식이 사실상 불가능하다. 대신 run(시나리오 × 버전 × k회)마다 새 키로 데이터를 만든다.
  - 반대 전표로 되돌리는 방식은 쓰지 않는다. 반대 전표는 상태를 원래대로 돌리지 않는다. 새 전표와 반대 표시가 남고, 번호가 소모되고, 반제된 항목이나 마감된 기간에서는 막힌다.
  - 채점은 테이블 전체 diff가 아니라 "배정 범위 안의 변경만 있었는가"로 한다.
  - **D2의 제안("에피소드마다 초기화")은 이 경우 성립하지 않으므로 D2를 고쳐야 한다.**

### 1-b. 읽기 권한은 있지만 쓰기 권한이 없다

- 합성 SAP mock은 그대로 만든다. QA는 오류 코드와 응답 스키마가 같은지 확인하는 비교 기준으로만 쓴다.
- 페이지네이션과 row limit은 데이터 양에 따라 달라지므로 이 비교로 검증할 수 없다. 이 부분은 원칙 4대로 사람이 검증한다.
- 비교는 샌드박스 밖에서 돌린다. QA 데이터가 실데이터에서 나온 것이면 비교 하네스도 보안 파트 승인이 필요하다.

### 1-c. 쓸 수 없다: 없음 / 실데이터에서 나옴 / 격리 불가

- 클라이언트가 없거나, 1-a 조건 (가)–(다) 중 하나라도 충족하지 못하는 경우다.
- QA가 운영 복사본이면 실데이터이므로 샌드박스에서 쓸 수 없다. 마스킹·익명화된 복사본이라도 보안 파트가 판정할 때까지는 이 경우로 취급한다.
- **PRD v0.1 그대로 간다.** SAP 기능 담당의 op별 동작 검증이 M2a의 critical path다. 그 사람의 시간을 M0에서 확보하지 못하면 M2a op 수를 2개로 줄인다.
- 도구 계약(B1)이 Tool 레지스트리에도 없으면 trace의 `output.summary` 컬럼명으로 역추정한다. 정확도 근거가 가장 약한 경우다.

**답 전 기본 가정**: 1-c. 단, mock op 구현은 Q1 답 전에 시작하지 않는다.

**답과 무관하게 지금 할 수 있는 일**: B1 도구 계약 수집, 엔티티 모델 초안, 예약 범위 ID 규칙.

## Q2. Aegra 평가 샌드박스가 있는가, 담당은 누구인가

**정확히 물을 것** (받는 사람: 런타임 팀. 모르면 설계자에게 담당을 묻는다)

① 존재 여부와 담당 팀
② `erp.asset.refs`로 skill·prompt·에이전트 버전을 고정해 실행할 수 있는지
③ 체크포인터·스토어(특히 장기 메모리)가 운영과 물리적으로 분리돼 있는지
④ 네트워크 정책: 기본 차단이 되는지, 허용 목록을 우리가 정할 수 있는지, deny 로그를 볼 수 있는지
⑤ 운영 런타임과 같은 이미지·버전을 쓰는지
⑥ 동시 실행 한도와 비용 부담 주체
⑦ 비즈니스 팀이 제출한 미검토 버전의 실행을 허용하는지 (M4 셀프서비스 전제)
⑧ 없다면, 운영 런타임 이미지와 자산 로더를 받아서 우리가 띄울 수 있는지
⑨ (M2b용) HITL interrupt를 가로챌 수 있는지

### 2-a. 있고, 버전 고정과 저장소 분리가 된다

- **C1이 "구축"에서 "연동"으로 줄어든다.** 실행기(C4)는 실행 API만 호출한다.
- C1b(외부 경로 차단)가 그 샌드박스에서도 성립하는지 확인해야 한다. 네트워크 정책을 우리가 정할 수 없으면 deny 로그 접근을 요구사항으로 넘긴다.
- 런타임 장애나 버전 변경이 우리 평가에 영향을 준다. 그래서 평가 결과마다 런타임 버전을 기록한다.

### 2-b. 있지만 일부만 된다

- **버전 고정이 안 될 때**: 기준 버전과 후보 버전을 같은 조건에서 비교할 수 없으므로 회귀 판정(C6)이 성립하지 않는다. 버전마다 별도 배포를 만들어 실행한다. 이 경우 배포 비용이 들고, M4에서는 제출할 때마다 배포가 필요하다.
- **저장소가 공유될 때**: 평가 run이 운영 체크포인터·장기 메모리를 오염시킨다. 특히 Personal은 실제 사용자 메모리를 읽을 위험이 있다. 분리될 때까지 Personal 평가(B4)는 시작하지 않는다. Business 단일 턴 조회(M2a)는 별도 네임스페이스나 prefix로 버틸 수 있는지 확인한다.

### 2-c. 없거나 담당이 없다

- 격리 네임스페이스에 Aegra 런타임을 우리가 띄운다. 필요한 것은 다섯 가지다: 운영과 같은 이미지(질문 ⑧), 자산 로딩, 사내 LLM Gateway 연결, 분리된 저장소, 기본 차단 네트워크.
- **M2a 공수가 크게 늘어난다.** 범위를 더 줄이면 A/A와 변형 검출의 통계력이 떨어진다. 그래서 범위는 그대로 두고 M2a 종료 시점을 늦춘다.
- **운영 유지 부담이 우리 팀에 생긴다.** 운영 이미지 digest를 평가 결과에 기록하고, 운영과 다르면 경고한다. 런타임 팀에 이관할 대상으로 표시하고, 이관 전까지 런타임 소유가 우리라는 점을 PRD 3장 경계 표에 반영한다.

**답 전 기본 가정**: 2-c 기준으로 공수만 추정한다. 구축은 답이 온 뒤 시작한다.

**답과 무관하게 지금 할 수 있는 일**: C1b 외부 경로 목록, 실행기 설계. 실행기가 런타임 어댑터를 거쳐 실행을 요청하게 만들면, 2-a든 2-c든 어댑터만 바꾸면 된다.

## Q3. 과거 skill·prompt 버전과 사고·롤백 이력을 버전 단위로 조회할 수 있는가

**정확히 물을 것** (받는 사람: 자산 레지스트리 담당, 실행 원장 담당, 운영 담당)

① 과거 자산 버전을 다시 실행할 수 있는 형태로 꺼낼 수 있는지 (자산 레지스트리, git)
② 롤백·장애·사용자 불만을 원인 버전과 연결한 기록이 있는지
③ 최근 6개월(예시. 운영 기간에 맞춤) 동안 롤백·사고가 몇 건인지
④ 사고 원인이 데이터 특이성인지 에이전트 동작인지 구분돼 있는지
⑤ 당시의 LLM 모델 버전, 도구 스키마, 런타임 이미지가 기록돼 있는지

⑤가 필요한 이유: 과거 버전은 skill·prompt만으로 재실행되지 않는다. 지금 합성 세계는 현재 도구 스키마로 만든다. 그래서 과거 버전이 지금은 없거나 바뀐 op를 부르면 그 결과는 에이전트 결함이 아닌데도 실패로 나온다.

### 3-a. 버전, 사고 이력, 당시 환경이 모두 있다

- PRD대로 **백테스트를 M2b 성공 판정에 쓴다.** 사고 버전과 정상 버전을 샌드박스에서 돌려 둘을 구분하는지 본다.
- **분모 규칙**: 두 조건을 모두 충족하는 사고만 센다. ① 합성 세계에서 재현 가능한 유형이다(특정 실데이터 때문에 생긴 사고가 아니다). ② 당시 도구 스키마가 현재 합성 세계와 호환된다.
- 해당 사고가 적으면(예: 5건 미만, 예시 값) 비율 목표를 두지 않고 "몇 건 중 몇 건을 잡았나"로 사례 보고한다.

### 3-b. 일부만 있다

- **버전은 있는데 사고 연결이 없을 때**: 장애 보고서나 인터뷰로 손 라벨을 붙인다. 이 경우 사례 보고만 한다.
- **사고 목록만 있고 그 버전을 재실행할 수 없을 때** (당시 환경 기록이 없는 경우 포함): 백테스트가 불가능하다. 사고는 시나리오 아이디어(`exercises_failure_mode`)로만 쓴다.

### 3-c. 없다

- **백테스트를 뺀다.** M2b 성공 판정은 변형 검출, A/A 오판률, 행동 현실성으로만 한다.
- 그러면 "샌드박스 결과가 운영을 예측한다"는 근거가 M4 이후 "샌드박스 통과·운영 회귀" 추적 전까지 없다. 그래서 D6(배포 게이트 사용 여부)은 참고 지표로 더 오래 남는다. 이 점을 설계자에게 미리 알린다.
- 지금부터 자산 버전, 모델·도구 스키마·런타임 버전, 운영 사고를 서로 연결해서 기록하도록 요구사항을 넘긴다. 사고 기록이 충분히 쌓이면 백테스트를 다시 검토한다.
- 변형은 실제 운영 실패 유형(A6 분석)을 보고 만든다. 사람이 상상한 결함만으로 만들면 실제 회귀 분포와 어긋나기 때문이다.

**답 전 기본 가정**: 3-c. M2b는 백테스트 없이도 성립하게 짜고, 백테스트는 가능하면 추가한다.

**답과 무관하게 지금 할 수 있는 일**: 심각도별 변형 목록 설계 (M2a에서 바로 사용).

## Q4. v3 SEL 섹션과 `eval-job/v1` 규격

**정확히 물을 것** (받는 사람: 팀 설계자)

① v3(또는 최신) 설계 문서의 SEL 섹션 원문
② `eval-job/v1`의 상태: 확정된 스키마인지, 이름만 있는지, 바뀌었거나 폐기됐는지
③ case가 외부 world·snapshot 참조를 허용하는지. 운영 run id만 참조하는 구조인지
④ Tester 평가셋을 `replay_candidate`(운영 run 재실행)로 만드는 계획이 지금도 유효한지. 유효하다면 replay 입력의 출처(Phoenix에는 내용이 없으므로 정본 또는 실행 원장)와 접근 권한
⑤ `regressed_cases: 0`에서 "회귀 케이스"의 정의 (반복 실행과 노이즈를 어떻게 처리하는지)

**가장 급한 이유**: 세부 설계 1순위인 시나리오·채점 계약을 `eval-job/v1` 확장으로 정했다. 이 답이 없으면 계약을 확정할 수 없다. 계약이 확정되지 않으면 B와 C를 동시에 진행할 수 없다.

### 4-a. 규격이 확정됐고, case 구조가 world 참조를 허용하고, 합성 세계로 바꾸는 데 동의한다

- B의 suite가 Tester의 평가셋이 된다. 시나리오·채점 계약은 `eval-job/v1`의 case 부분을 확장하는 형태로 쓴다.
- PRD v0.2에서 할 일: 3장 대응표의 이름·형식을 v3 그대로 맞추고, 실행 요청·결과 형식을 `eval-job/v1`로 바꾼다. 회귀 판정은 v3 게이트에 노이즈 폭 처리를 더하는 제안으로 정리한다.
- v3 문서에서 Tester 평가셋 출처를 고치는 일은 설계자 몫이다.

### 4-b. 설계자가 `replay_candidate`를 유지하려 한다 (가장 비관적인 경우)

- replay에는 실데이터가 필요하다. 그래서 비즈니스 영역에 공개하는 샌드박스에서는 돌릴 수 없다. 평가가 두 갈래로 나뉜다.
  - **replay 갈래**: 운영 SAP 읽기 접근이 있는 비공개 환경에서 돌린다.
    - 입력은 정본이나 실행 원장에서 가져와야 한다.
    - 정답을 계산할 수 없다. 원래 run의 결과나 라벨과 비교하거나 LLM judge를 써야 하므로 규칙 채점(G3)이 적용되지 않는다.
    - 운영 SAP 데이터는 시간이 지나면 바뀐다. 그래서 원래 run과 비교하면 데이터 변화가 노이즈로 섞인다.
    - 쓰기 업무는 재실행할 수 없다. 3등급 마스킹 run은 도구 조회가 실패하므로 대상에서 빠진다(PRD 2장).
  - **합성 갈래**: 우리 샌드박스. PRD v0.1 범위 그대로이고 replay와 독립이다.
- `eval-job/v1`에 실행 환경을 구분하는 필드(예: `source: replay | synthetic`)가 필요하다. 두 갈래의 결과를 하나의 게이트에 합칠지는 설계자가 정한다. 그대로 합치면 노이즈 특성이 섞인다.
- replay 갈래의 소유자를 정해야 한다. 우리가 맡으면 범위가 커지고, 실데이터를 다루므로 보안 검토가 새로 필요하다.

### 4-c. v3 문서는 있지만 `eval-job/v1`이 이름만 있거나 초안이다

- 우리가 쓰는 계약이 사실상 `eval-job/v1` 초안이 된다. 지금 바로 쓸 수 있다.
- 다만 v3 쪽(Creator·Improver)이 요구하는 필드를 우리가 모른다. 그래서 계약을 확정하기 전에 설계자 리뷰를 받는다.

### 4-e. 규격이 바뀌었거나 폐기됐다, 또는 case 구조가 맞지 않는다

- 예: case가 운영 run id만 참조하고, world·snapshot을 가리킬 필드가 없는 경우.
- 확장으로 해결되지 않으면 case 층을 별도 규격으로 제안하고, job 층만 `eval-job/v1`(또는 후속 규격)에 맞춘다.

**답 전 기본 가정**: 4-c. 계약을 job(실행 요청·결과)과 case(시나리오·기대 결과·채점 결과) 두 층으로 나눈다.
- 4-a로 결정되면 job 층은 이름만 맞추면 된다. case 층은 구조를 다시 검토할 수 있다.
- 4-b로 결정되면 case 층에 `source`를 더한다.
- 4-e로 결정되면 case 층을 따로 제안한다.

**참고 · D1**: "새로 생성하는 데이터"가 skill·prompt 개선안을 뜻하는 경우의 영향은 PRD 1장에 있다(M3·M4의 필요가 줄어듦). D1은 v3 규격 질문과 성격이 달라 Q4와 별도로 묻는다.
