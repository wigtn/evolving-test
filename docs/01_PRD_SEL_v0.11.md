# SEL 전체 참고안 (Agent Runtime 안의 평가·개선 루프)

Oct 28, 2026 · @WIGTN · 상태: **참고안 v0.11.** 이 문서는 SEL 전체 설계가 아니다. SEL 구조 · 역할 · 담당 · 일정의 기준은 모듈 설계 기준 문서(내부) 11장이고, SEL 전체 설계는 PM이 한다. 우리 담당(② 자산 생성)의 설계는 `docs/07_SEL_2_asset_generation.md`가 본체다. 이 문서는 그동안 SEL 전체를 놓고 쌓은 분석을 ①③④ 담당과 PM에게 **제안 입력**으로 넘기기 위해 남긴다.

## 0. 바뀐 것

**v0.11 (2026-10-28)**: 모듈 설계 기준 문서(내부)을 기준으로 전제를 바로잡았다. **아래 정정 표가 본문보다 우선한다.** 본문에 남은 v0.9–v0.10의 "공용 자산만" 서술(대리 에이전트, gateway·action 충실도, 카나리 선행, PARKED 경로)은 이력으로만 읽는다.

**v0.10**: 트레이싱 배치가 바뀌었다(2026-10-28 전달). **Phoenix를 별도 VM에 띄우고, 계측 쪽(Runtime·게이트)이 OTLP로 Phoenix에 직접 보낸다. OTel Collector는 두지 않는다**(팀 의견. Phoenix가 OTLP를 직접 받으므로 단일 목적지면 Collector가 필요 없다).
- Collector가 하던 두 가지가 갈 곳이 바뀐다. ① 등급별 내용 제거(1·2등급·미표시 span은 구조만, 3등급은 마스킹)는 계측 SDK의 span processor에서 내보내기 전에 한다. ② 정본(ARD) 적재는 Collector 없이 누가 하는지 정해지지 않았다(SDK에서 두 번째 exporter, 또는 정본 없이 Phoenix만). **미결 Q9**로 올렸다(12장)
- SEL의 실행 기록 원천은 사실상 **Phoenix VM의 API**다. SEL(Agent Runtime VM)에서 Phoenix VM으로 VM 간 조회를 한다. Q6은 Q9에 묶였다
- Q7 결정(운영 업무 trace 없음)은 그대로다. Phoenix에 들어오는 것은 우리 Runtime(평가·재현 실행)과 게이트의 span뿐이다

**v0.9**: **Q7을 "공용 자산만"으로 정했다**(2026-10-27, 플랫폼 설계 방향 문서 4.1 근거: Business·Personal 업무는 프론티어 도구가 자산 MCP로 맡고, Runtime에는 SEL 오케스트레이터와 평가 샌드박스만 둔다). 이후 전제(Runtime 안 Business·Personal 에이전트)와 충돌하므로 설계자 확인은 남겨 둔다(12장).
- 운영 trace가 없다. 프론티어 도구(OpenAI Dots)는 OTel을 주지 않는다. 운영 신호는 우리 게이트의 사용 원장·감사 기록(gateway)과 세션 기록(action, 제공될 때)뿐이다. full 충실도는 우리 평가 실행(정기 골든셋, 결함 주입)에만 있다(2장)
- 평가 대상은 대리 에이전트(Runtime 워커 + 자산)다. 진단은 평가 샌드박스 재현이 기본이다(7장)
- 운영 finding의 개선 판정은 카나리가 한다. 카나리 기능(2027.3) 전에는 게이트(대리 에이전트 비열등) 통과 뒤 PARKED가 기본 경로다. 그 전에 VERIFIED까지 갈 수 있는 것은 R6(정기 골든셋) 케이스뿐이다(2장, 9.3)
- R4·R8은 운영에서 불가(R8은 평가 실행에서만). 달력은 공용 자산만 한 갈래로(10장). Q6은 "우리 Runtime·게이트 기록을 어디서 읽나"로 좁아졌다
- v0.9 검증 리뷰 반영: R6 케이스의 Verifier 판정(정기 골든셋 기반), 재현된 운영 finding의 G1은 개선 기준 유지, 카나리 전에는 운영 finding 개설을 에이전트당 1건으로 제한하고 카나리 기능이 오면 PARKED를 닫음, 모델 변경 중 진행 케이스 대기, ABORTED·EXPIRED·INCONCLUSIVE 재개설 쿨다운, 잠금 상태 열거, CANARY 중 기준 변경·카나리 롤백 정의, 비용 재검산

**v0.8**: v0.7 독립 리뷰 2건(흐름 동결, 빌드 관점), sel-lab 시험 결과, v0.8 초안 검증 리뷰를 반영해 **흐름을 동결**했다. 세부 설계 계획과 스케줄러 판단 로직은 docs/06.
- 상태머신 동결(9.3): 기한 초과의 목적지를 상태별로 하나로, 판정 예산은 `gate_decision` 기록 때만 차감하고 세트 고정(OPEN → TRIAGED)에서 확인, 게이트 실패·수정 요청·STALE은 모두 OPEN으로, 기준 변경은 잠금 상태 어디서든 STALE, QUEUED·PARKED·EXPIRED·ROLLBACK_SKIPPED·ABORTED 추가, 잠금 상태 열거, 승인 시 기준 버전·digest CAS, 종료 사유별 finding 상태와 suppressed 해제 조건 ①–⑥, transient 종료 3회면 suppressed
- 목표 세트는 **기준 실패 탐침**으로 고르고, 실패 서명이 finding과 일치하는 사례만 목표로 쓴다(5장). sel-lab에서 요청 문장 분류로 고르면 결함이 문장에 드러나지 않는 경우(이름이 겹치는 거래처) 기준이 이미 통과하는 사례만 뽑혀 개선을 잴 수 없었다
- Creator 출력은 `cause_class` 열거값까지. 케이스 종료(DISMISSED)는 코드가 정한다(7장). 유입 검사의 안전 절차 줄 삭제는 실패로(fail-closed)
- Creator에 돌려주는 판정 피드백을 게이트별 통과 여부로 줄이고, 사례 사용 상한을 10회에서 50회로(5장). 10회면 골든셋이 판정 십여 번 만에 고갈된다. 50회는 보장 없는 제안값이고 M2c에서 재사용 점검
- 카나리 기능 전에는 GATE_PASSED → PARKED(D14 제안), new_asset은 v0에서 케이스를 열지 않는다(D18)
- 스케줄 작업별 결정 규칙: 분석 창·watermark·완전성·멱등 키, R6 판정 규칙, 기준선 산식(9.1). 모델·도구 계약 변경 시 개설 동결과 A/A 재검정(9.6). LLM 호출 실패 처리(9.6). 데이터 모델 테이블 보강(9.6)
- 숫자 정정: judge 참고 판정 약 650회, D12를 v0.7 용량 기준으로(9.4, 12장)

**v0.7**: v0.6 독립 리뷰를 반영했다. 원칙은 그대로다. 사람은 마지막 승인 한 곳에만 들어가고, 그 전의 판단은 결정적 규칙이 한다. 규칙으로 판단할 수 없으면 승인 요청을 올리지 않고 끝낸다.
- held-out을 **노출 원장 기반**으로 재정의: Creator 컨텍스트에 한 번이라도 들어간 사례는 dev로 영구 강등. SKILL 평가 케이스 필드는 Creator 사본에서 제거, 증거 trace의 재현 사례는 dev 전용, 판정용 재현 사례는 증거로 쓰이지 않은 trace에서(5장)
- 자동 격리는 결정적 규칙으로만, 다음 세트부터, 비율 상한(5장)
- finding당 판정 예산 3회, REJECTED·예산 소진은 suppressed(6장)
- 재현 사례 필수 조건, 정답 있는 사례 최소 비율 30%, 최소 골든셋 규모(5장)
- 목표·가드는 코드가 뽑고 가드가 비면 판정하지 않음(5장)
- HELD를 일시적·구조적으로 나눔, 자동 롤백은 CAS(현재 활성 = 릴리스한 버전일 때만), 악화 판정은 순차 검정, VERIFYING 동안 자산 잠금 유지(9.3)
- judge 잔재 제거, 롤백 API를 비상용으로, 용량 재계산(6장, 9장)

**v0.6**: 루프 안의 사람 개입을 **최종 승인(SEL Admin UI) 하나**로 줄였다.
- held-out은 사람이 관리하는 별도 세트가 아니라, 골든셋을 케이스마다 시드로 코드 분할해 Creator에게 숨긴 부분이다(5장, 7장)
- 골든셋은 SKILL 내장 평가 케이스와 결과 신호로 판정 가능한 재현 사례로 구성한다. SME 라벨은 선택 사항(5장)
- judge는 게이트에 쓰지 않고 승인 화면 참고용으로만 쓴다(6장)
- 진단 표본 점검 폐지, 평가 케이스 결함은 자동 격리, HELD·INCONCLUSIVE는 자동 처리, REGRESSED는 자동 롤백(7장, 9장)
- 대가: 사람 라벨이 없으면 "답의 값이 맞았는가"는 정답이 있는 사례(SKILL 내장 케이스, 합성 세계 참조 풀이)에서만 검증된다(5장)

**v0.5**: 설계 검토(docs/05)의 주요 발견을 반영했다.
- 게이트 통계: G3를 결정적 정책 사례(G3a)와 통계 검정 사례(G3b)로 나누고, 회귀 케이스는 "완전 붕괴 수 ≤ 허용치(A/A)"로. 판정은 LCB > 0과 사전 고정 MMI(관측 MDI 판정 폐기 [제안: 기준 문서의 MDI 게이트를 대체하는 결정이 아니라 ③ · PM에 주는 제안]). 표본은 G1·G2가 동시에 검정력을 갖게 다시 산정(목표 86, 가드 221). 군집 보정, judge 선호 점수 정의, A/A로 k 확정, 실패 쪽 조기 종료(6장)
- 만성 결함: 신호별 절대 상한, 기준선에서 열린 finding 기간 제외(4장)
- Verifier: 급등 전 기준선과 대조군 이중차분(9.3)
- 간접 프롬프트 인젝션: 증거 구획 단계, 유입 검사, SEL 수정 금지 필드, 인젝션 내성 고정 사례, 보안 경계 6지점(7장)
- confused deputy: 평가 계정 정책 5가지, 셀프서비스는 제출자 권한 교집합으로 실행(6장)
- 달력을 Q7 분기별로(10장)

**v0.4**: SEL 애플리케이션 설계 v0.1(2026-10-23)과 대조해 빠진 것을 채웠다.

| 순서 | 분석 → 생성 → 평가 → 개선 | 스케줄러 신호 → **Creator → Tester → Evaluator → Improver** |
| Creator | 새 skill만 | 실패 분석, **개선안 작성**(패치·마이너), 새 SKILL 후보와 평가셋 |
| Evaluator | 규칙 채점 | **judge 채점**과 버전 비교. 규칙으로 판정 가능한 검사는 judge 앞에 둔다 |
| Improver | 패치 생성 | **등록·상신과 승인 요청까지.** 활성 전환은 사람이 승인할 때 일어난다 |
| 분석 | 별도 영역 A | **Creator 앞단**. Deep Tracer가 빠졌으므로 그 기능(finding, 상태 추적)을 여기로 가져온다 |
| 세션 기록 | 없음 | 실패 신호, 새 자산 후보, 개선 효과 확인의 원천으로 추가 |
| 수정 범위 | 자체 정의 | 문서의 자산별 SEL 개선 대상 표를 따른다 (SKILL 패치·마이너, Prompt는 persona 파생본만, Tool 제외) |
| 결과 저장 | git + 자체 JSONL | PostgreSQL 평가 작업 원장·리포트 (Database Connector 경유) |

설계 방향 문서와 이후 바뀐 전제가 충돌하는 곳은 미결로 표시했다(2장, 3장, 12장 Q5–Q7). 가장 큰 충돌은 **평가를 실제 도구로 하느냐, 합성 세계로 하느냐**(Q5)다.

## 1. 개요

> v0.11: 이 장의 범위 · 비목표(Tool 수정 비목표, 공용 자산 표현 등)는 0장 정정 표가 우선한다.

SEL은 공용 자산(Agent, SKILL, Prompt)을 평가하고 고치는 루프다. Agent Runtime VM(Aegra) 안에서 스케줄러 신호로 Creator → Tester → Evaluator → Improver를 차례로 실행한다. Improver가 개선안을 자산 저장소에 등록·상신하고, 사람이 승인하면 활성 버전이 되어 다음 실행부터 모든 창구에 반영된다.

**배경**

- 플랫폼은 실행 도구가 바뀌어도 세 가지를 유지한다: 업무 자산의 정본을 두는 **자산 저장소**, 진입과 도구·데이터 접근을 통제하는 **게이트**, 자산을 평가하고 고치는 **SEL**.
- Agent Runtime을 두는 이유는 SEL이다. 개선안을 반영하기 전에 기존 버전과 새 버전을 같은 케이스로 돌려 비교해야 하고, 그 실행을 맡을 곳이 Runtime이다.
- Deep Tracer는 설계에서 빠졌다. 그래서 실행 기록 분석을 SEL Creator 앞단에 둔다(설계 방향 문서 4.4의 "Deep Tracer 없이 동작" 경로).
- 트레이싱(계측, Phoenix VM 운영)은 다른 팀이 맡는다. v0.10부터 OTel Collector는 두지 않는다.
- 팀 설계자의 지시는 분석 → 생성 → 테스트·평가의 태스크 분해다. 테스트와 평가는 샌드박스로 열려 비즈니스 영역에서 활용할 수 있어야 한다.

**지시와 SEL 단계의 대응**

| 지시 | SEL 단계 | 이 문서 |
| --- | --- | --- |
| Phoenix 데이터를 가져와 분석 | Creator 앞단 (실패 분석, finding). Q7 뒤로 Phoenix에는 운영 업무 trace가 없고 Runtime·게이트 span만 있다. 운영 실패 분석의 주 원천은 게이트 기록과 세션 기록이다 | 4장 |
| 그걸 기반으로 데이터를 새로 생성 | Creator (개선안, 새 SKILL 후보, 평가셋). 평가를 합성 세계로 하게 되면 합성 세계도 포함 (Q5) | 5장, 7장 |
| 테스트하고 평가 | Tester, Evaluator | 6장 |
| (반영) | Improver, 승인 | 7장 |

**목표**

1. G1 · 실패 분석: 실행 기록과 세션 기록에서 실패 패턴을 찾아 고정 ID를 가진 finding으로 만들고, 해소·재발을 추적한다.
2. G2 · 개선안: finding마다 수정 허용 범위 안의 개선안(패치·마이너 버전)을 만든다.
3. G3 · 신뢰할 수 있는 평가: 기존·후보 버전을 같은 케이스로 짝지어 반복 실행하고, 노이즈를 넘는 차이만 회귀·개선으로 판정한다.
4. G4 · 반영과 확인: 회귀 없이 개선된 후보만 승인을 거쳐 활성화하고, 반영 후 운영 기록으로 효과를 확인한다.
5. G5 · 셀프서비스: 비즈니스 영역 담당자가 자기 자산 버전을 제출해 평가를 돌리고 결과를 해석할 수 있다.

**비목표**

- 트레이싱 계측, Phoenix VM 운영 (타 팀)
- Tool 자산 수정 (개발자 작업), 자산의 메이저 버전 변경 (사람만)
- 사람 승인 없는 활성 전환. 예외는 하나다: 반영 후 악화가 검정되면 **직전 승인 버전으로의 자동 롤백**은 사람 없이 한다(되돌릴 버전은 이미 사람이 승인한 것)
- 루프 안의 다른 사람 개입. 사람은 최종 승인 한 곳에만 들어간다. 자산 작성(메이저 변경, SKILL 내장 평가 케이스 작성), 합성 세계 구축 같은 루프 밖 작업은 별개다
- 개인화, 개인 지식 고도화. 세션 기록은 공용 자산을 고치는 재료로만 쓴다
- fine-tuning용 학습 데이터 생성

**성공 판정 (제안값)**

- M2a 종료: 일부러 망가뜨린 변형(심각도별 3종 이상)을 모두 회귀로 잡고, A/A 오판이 상한 이하이며, 반복 노이즈 폭이 측정되어 있다.
- M2b 종료: 과거 롤백·사고 버전과 정상 버전을 백테스트로 구분한다 (Q3 이력이 있을 때).
- M2c 종료: finding 1개 이상에서 Creator 후보가 게이트 G1–G4(6장)를 통과하고, Improver를 거쳐 승인·활성화된다. 표본 규모가 검정력 기준에 못 미치면 "루프가 끝까지 돈다(dry-run)"를 종료 기준으로 쓴다.
- M4 종료: 파일럿 팀이 우리 도움 없이 평가를 돌리고 결과를 참고 지표로 쓴다.

## 2. 입력 데이터와 미결 전제

SEL이 읽는 원천은 아래와 같다. 원천마다 접근 가능 여부가 설계를 크게 바꾼다.

| 원천 | 담는 것 | 경로 | 미결 |
| --- | --- | --- | --- |
| 실행 기록 (Phoenix, **별도 VM**) | Runtime trace(평가·재현·대리 에이전트 실행), 게이트 span. 1·2등급·미표시 span은 구조만, 3등급은 마스킹본(계측 SDK에서 제거한 뒤 보냄). 프론티어 도구 trace는 없다(OTel 미제공) | Phoenix API (VM 간 조회, 읽기 전용 key, `phoenix-client`) | **v0 기본 원천**. 운영 주체·보존 기간은 트레이싱 팀 |
| 실행 기록 정본 (ARD) | 내용 전체 | Database Connector (`log_query`) | Collector가 빠져 적재 경로 미정. **Q9** (Q6은 여기에 묶임) |
| 실행 원장·평가 작업 원장 (PostgreSQL) | validator, HITL, 피드백, 평가 결과 | Database Connector | 읽기 권한 (D5) |
| 세션 기록 요약 | 세션별 의도, 사용 자산·버전, 사용자 수정·재요청, 반복 절차 | Database Connector | 저장 위치 미정. 대상 범위 정책(동의, 익명화, 보안 등급 제외) 선행 |
| 자산 MCP Gateway 사용 원장, Tools Gateway 감사 번호 | 누가 어떤 자산의 어느 버전을 썼는지, 어떤 도구를 위임했는지 | Database Connector | OTel trace가 없는 구간(프론티어 도구)에서 남는 유일한 실행 신호 |

**운영 실패 원천 (v0.11 정정).** 모든 에이전트가 우리 Runtime에서 돌고 Harness 1층이 모든 span에 `erp.asset.refs`와 표준 결과 코드(`erp.outcome.type`)를 붙인다. 그래서 운영 실패는 Phoenix의 실행 기록으로 바로 보인다(full). ① 입력 파이프라인이 Phoenix에서 매시 span을 가져와 전처리(높은 등급 본문 제거)와 분석을 하고 finding을 낸다. 세션 기록과 게이트 원장은 보조 신호다.

**연동 규약에 반드시 있어야 하는 것** (설계 방향 문서 5장 중 SEL 판정에 직결되는 항목. 계약 번호는 그 문서 3장 연결 계약)

| 데이터 | 빠지면 | 계약 | 담당 |
| --- | --- | --- | --- |
| 실행 기록마다 사용한 자산 버전 (`종류/이름@범위`) | 어느 버전의 결과인지 몰라 버전 비교와 개선 효과 판단 불가 | 4·9·10 | 자산 저장 규격, 트레이싱 팀 |
| 실행 출처 표시 (운영·평가·재생) | 평가·재생 실행이 운영 통계에 섞여 판정 오염 | 5·6 | FW (Tools Gateway), Database Connector |
| 쓰기 도구의 시험 실행 여부·감사 번호 | 평가가 운영 데이터를 바꿨는지 추적 불가 | 5 | FW (Tools Gateway) |
| 도구 실패의 오류 상태·span 종류 | 실패가 성공처럼 기록됨 | 8·10 | 트레이싱 팀 |
| 배포·변경 시점 신호 | 반영 전후를 나누지 못해 해소·재발 판단 불가 | 8·9 | 자산 저장 규격 |
| 세션 기록·사용 원장의 요청 ID·사용자 | 세션 기록과 게이트 원장을 연결할 수 없어 실패 신호를 자산 버전에 귀속 불가 | 2·10 | FW (공통 진입점), 세션 기록 담당 |

응답마다 요청 ID, 검증 단계 거절의 원장 기록 같은 나머지 5장 항목은 SEL 판정에 직접 쓰이지 않아 여기에 넣지 않았다.

### 관측 충실도 (앱 설계 2장)

SEL이 볼 수 있는 범위가 고칠 수 있는 범위와 검증 방식을 정한다. 핵심 차이는 **다시 돌려볼 수 있는가**다.

| 충실도 | 출처 | 만들 수 있는 케이스 | 사전 검증 | 실질 판정 |
| --- | --- | --- | --- | --- |
| full | Agent Runtime(Aegra) 실행 | 지시문 결함, 예시 부족, 도구 선택 오류, SKILL 본문 오류, 매니페스트 자산 구성 | 쌍대 재실행(게이트) | 게이트 |
| relay | 기밀 구간 추론 중계 | full과 같음. 실행 위치 결정에 종속 (12장 확인 필요) | 쌍대 재실행 | 게이트 |
| gateway | 공통 진입점, Tools Gateway, Database Connector 원장 | 도구 설명 모호, 인자 스키마 결함, SKILL 선택 메타데이터, 누락 자산 | 대리 에이전트 게이트 (재현된 서명에서 개선) | 카나리 비교 |
| action | 프론티어 도구(OpenAI Dots) 행동 로그 | 반복 호출, 중도 포기, 수정·재요청 같은 행동 패턴 | 대리 에이전트 게이트 (재현된 서명에서 개선) | 카나리 비교 |

- **대리 에이전트**: 프론티어 도구가 쓰는 것과 같은 자산을 같은 MCP 경로로 소비하게 구성한 Aegra 에이전트다. 모델이 프론티어와 다르므로 "후보가 더 낫다"는 증명할 수 없고, "후보가 명백히 나빠지지 않는다"까지만 확인한다. 개선 여부는 카나리 코호트와 대조 코호트의 패턴 발생률로 판정한다.
- **v0.11 정정**: 모든 에이전트가 우리 Runtime에서 돌므로 운영 finding은 대부분 full 충실도다. 위 표의 gateway · action 행과 대리 에이전트는 v0.9–v0.10의 "공용 자산만" 전제에서 쓴 것이라 지금은 해당하지 않는다(Dots 공존 경계가 생기는 2027.7 이후 다시 본다).

## 3. 전체 구조

![SEL 구조 · 스케줄러가 기동하고, 개선안은 사람 승인을 거쳐 활성](images/sel-architecture.png)

그림은 위에서 아래로 읽는다. 맨 위 스케줄러가 주기 작업을 모두 기동하고, 굵은 선이 개선 한 사이클이다. 원천(Phoenix API, 보조로 세션 기록 · 게이트 원장)은 SEL에 밀어 넣지 않는다. 스케줄러가 매시 폴백 분석기를 깨우면 분석기가 지난 구간을 증분 조회(pull)한다. 원천에 데이터가 쌓이는 경로는 그림 맨 위 초록 영역이다. Business·Personal 업무는 프론티어 도구(OpenAI Dots)가 맡는다(Q7). Dots는 OTel을 주지 않으므로 운영 업무의 trace는 없고, 제공될 경우 세션 기록만 들어온다. Dots가 자산과 도구를 쓸 때는 우리 게이트(공통 진입점, 자산 MCP Gateway, Tools Gateway)를 거치므로 사용 원장·감사 기록이 남는다. Runtime(평가·재현 실행)과 게이트의 span은 계측 SDK가 등급별 내용을 지운 뒤 **별도 VM의 Phoenix로 OTLP 직접 전송**한다(OTel Collector 없음). ARD 정본 적재 경로는 미정이다(Q9). Phoenix VM은 트레이싱 팀 소관이다.

| 매일 | 정기 골든셋: 활성 버전으로 고정 사례(SKILL 내장 필수 케이스, 정책 사례)를 평가 샌드박스에서 직접 실행 (R6) | 능동 시험 | LLM을 실제로 호출해 비용·부하가 든다. 부하가 가장 낮은 시간대에 하루 한 번. 운영 트래픽이 없거나 드문 업무도 잡는다 |
| 6시간 | Verifier: 카나리 코호트 비교, 대조군 이중차분(트리거 제외 "전" 구간 대비) | 반영 확인 | 관측 수가 쌓이는 속도에 맞춘 주기 |
| 10분 | 기한 감시: 상태별 기한을 넘긴 케이스를 9.3 기한 표의 목적지로 | 안전장치 | 단계가 멈춰도 케이스가 영원히 열려 있지 않게 |

그림의 되돌아가는 선: 게이트 FAIL은 진단·세트 고정(OPEN)으로 돌아간다(finding당 판정 예산 3회, 그 뒤 REJECTED). 승인자의 수정 요청도 진단으로 돌아가 다음 반복의 입력이 된다. Verifier 결과(VERIFIED·REGRESSED)는 케이스 상태머신으로 들어가 finding 상태(fixed·regressed)를 갱신한다. 새 개선안이 활성 버전이 되는 길은 Improver → SEL Admin UI(사람 승인) → Database Connector 하나뿐이다. 그 밖의 활성 변경은 Verifier가 악화를 검정했을 때 직전 승인 버전으로 되돌리는 자동 롤백뿐이다.

**Agent Runtime VM 안** (프로세스 간 통신)

- **스케줄러**: 시간에 묶인 작업은 모두 스케줄러가 기동한다(9장). 매시 폴백 분석과 매일 기준선 재계산(→ Creator 앞단), 매일 정기 골든셋(→ Tester, R6 입력), 6시간마다 Verifier, 10분마다 기한 감시(→ SEL 서비스). 자산 버전 등록, 셀프서비스 제출, finding 발행은 이벤트로 들어온다.
- **Creator 앞단(폴백 분석기)**: 실행 기록·세션 기록을 읽어 finding을 만들고 SEL 서비스에 넘긴다(4장).
- **SEL 서비스**: 케이스 상태머신의 주인이다. finding을 묶어 케이스를 열고, 상태 전이를 기록·발행(outbox)하고, 기한을 관리한다. 오케스트레이터로서 Creator → Tester → Evaluator → Improver를 차례로 호출한다. 상태는 SEL 서비스만 소유하고 나머지 단계는 상태가 없다.
- **평가 샌드박스와 워커**: 후보 버전과 기존 버전을 같은 케이스로 짝지어 실행한다. 워커는 요청마다 자산을 받아 DeepAgents로 실행하고 상태를 갖지 않는다. 낮은 우선순위로 돈다. 평가 대상은 "워커 + 자산 조합"(대리 에이전트)이다. Runtime에 Business·Personal 오케스트레이터는 없다(Q7).
- **SEL Admin UI**: 승인자가 diff, 게이트 결과, 증거 발췌를 보고 승인·반려·수정 요청을 한다. **Improver의 출력은 반드시 여기를 거친다.** 승인해야만 Database Connector가 새 버전으로 활성 전환한다. 승인 화면에는 게이트를 통과한 후보만 올라온다. (예외: 직전 승인 버전으로의 자동 롤백)
- **Verifier**: 반영 전후 같은 패턴의 발생률을 비교해 VERIFIED 또는 REGRESSED를 SEL 서비스에 알린다(9.3).

**VM 밖** (LLM 추론, Redis, Phoenix 읽기 API를 빼면 모두 게이트를 거친다)

- 평가 샌드박스가 자산·도구를 쓸 때는 다른 창구와 같은 경로를 탄다: 공통 진입점(권한 판정) → 자산 MCP Gateway → 자산은 Database Connector → 자산 저장소, 도구는 Tools Gateway. 평가 실행은 평가 계정으로 표시한다.
- 저장소 접근은 Database Connector 하나로 한다(예외: Redis 직접 연결, 별도 VM Phoenix의 읽기 전용 API). 체크포인트, 실행 원장, 평가 작업 원장과 리포트는 PostgreSQL에, 자산 본문·버전·상태는 자산 저장소에 있다.
- LLM 추론은 LLM Gateway로 직접 호출하고(Chat Completions 호환), Redis(실행 큐, 응답 스트림)는 직접 연결한다.
- Phoenix는 **별도 VM**에서 타 팀이 운영한다. 설계 방향 문서에서 SEL은 DB(ARD) 기준으로 읽고 Phoenix API는 Deep Tracer가 읽었지만, Collector가 빠지고 ARD 적재 경로가 정해지지 않아 v0에서는 SEL이 Phoenix API를 직접 읽는다(10-27 팀 내부 논의와 같은 방향). 저장소 접근은 Database Connector 경유라는 원칙의 예외이므로, VM 간 통신 경로, 읽기 전용 key, 조회 한도(`limit`, 시간 창 분할)를 연결 계약에 적는다.

**Q5 답 전 원칙**: 6장 Tester·Evaluator와 7장 Creator·Improver는 두 안에 공통이므로 먼저 만든다. 평가 샌드박스는 도구 경로를 어댑터로 분리해, 어느 쪽으로 결정돼도 어댑터만 바꾸게 한다. 합성 세계(5장 B)는 Q5-b로 결정될 때만 착수한다. Q5-b라면 M2a 하네스도 합성 세계 위에서 돌아야 하므로, M2a 선행 작업으로 손으로 만든 최소 세계(B1·B2, op 2–3개)가 들어간다. Q5는 M0 게이트다.

## 4. Creator 앞단 · 실패 분석

Deep Tracer가 맡기로 했던 분석을 Creator 앞단에 둔다. 범위는 SEL이 고칠 수 있는 자산 범주의 실패를 찾는 데까지다. 트레이스 저장소, 조회 화면, 자동 수정은 만들지 않는다.

**finding 모델** (설계 방향 문서 4.4의 Deep Tracer 설계를 가져옴)

- **고정 ID**: 정규화 단계에서 결정적 fingerprint로 finding ID를 정한다. 같은 구간을 다시 분석해도 ID가 바뀌지 않는다.
- **상태**: new, known, fixed, regressed, suppressed. 사실 기록을 추가만 하고, 현재 상태는 projection으로 계산한다.
- **처리 경로**: 자산 범주(`context.skill`, `context.prompt`)는 SEL 루프로, 코드·워크플로·인프라 범주는 개발자 작업으로 넘긴다.
- **LLM의 역할**: 원인 서술, 범주 분류, 대안 생성에만 쓴다. ID와 그룹핑은 규칙으로 정한다. 사내 LLM만 쓴다.
- **판정 제외**: 평가·재생·빈 실행은 운영 판정에서 뺀다 (실행 출처 표시).
- **fixed 판정**: 점수만으로 닫지 않는다. 반영 후 운영에서 실제 실패가 줄어야 fixed가 된다. 예외는 R6(정기 골든셋) finding이다. 운영에서 생기는 신호가 아니므로, 실패했던 고정 사례가 반영 후 정기 골든셋에서 통과하는 것으로 판정한다(9.3).

**세션 기록 경로** (설계 방향 문서 4.5)

| 경로 | 세션 기록에서 보는 것 | SEL에서 쓰는 곳 |
| --- | --- | --- |
| 실패 신호 | 공용 SKILL로 만든 결과를 사용자가 고치거나 다시 요청한 기록. 여러 사람에게 같은 수정이 반복되는지 | Creator의 개선 근거. trace로는 보이지 않는 "기대와 달랐다" 신호 |
| 새 자산 후보 | 여러 사용자가 반복하는데 이를 덮는 공용 자산이 없는 절차 | Creator가 후보 SKILL과 평가셋을 만든다 |
| 개선 효과 확인 | 새 버전 활성 이후 같은 업무에서 수정·재요청이 줄었는지 | 반영 후 실제 효과. 평가 점수와 따로 본다 |

세션 기록은 OTel trace와 별개의 전제다. 대화 원문이 있어야 사용자가 결과를 고쳤는지 알 수 있다. 여러 사용자의 기록을 모으는 분석이므로 대상 범위(동의한 사용자, 익명화 통계, 보안 등급 제외)를 정책으로 먼저 정한다. 기밀 구간 클라이언트는 PC에서 나가는 경로가 없어 이 분석에서 빠진다.

**finding 계약** (앱 설계 5.1. 분석기를 바꿔도 SEL 코드가 바뀌지 않게 하는 Port)

| 필드 | 필수 | 내용 |
| --- | --- | --- |
| `finding_id` | 예 | 발행마다 새로 (UUIDv7) |
| `dedupe_key` | 예 | (대상 자산 ID, signal, hypothesis_class)의 해시. **고정 ID 역할**: 같은 패턴은 같은 키로 한 케이스에 묶인다 |
| `analyzer` | 예 | {name: fallback, version} |
| `window` | 예 | 관측 구간 {from, to} |
| `fidelity` | 예 | full · relay · gateway · action |
| `signal` | 예 | tool_error · arg_invalid · retry_loop · hitl_rejected · negative_feedback · eval_fail · no_asset_match · budget_exceeded |
| `target` | 예 | {asset_ref, channel}. 신규 자산 후보면 asset_ref = null, proposed_kind 지정 |
| `hypothesis_class` | 예 | description_ambiguity · schema_defect · missing_instruction · wrong_example · tool_selection · skill_selection · missing_asset · budget_overrun |
| `metrics` | 예 | {support, distinct_principals, rate, baseline_rate, reach_weekly} |
| `evidence` | 예 | [{source: audit · usage · session · trace, id, grade, excerpt_ref}] 최대 50건. v0 운영 증거는 게이트 감사·사용 원장과 세션 기록이다 |
| `suggested_change` | 아니오 | {change_type, field_path, note} |
| `max_grade` | 예 | 증거의 가장 민감한 등급 (보안 경계 7장) |

finding 상태(new · known · fixed · regressed · suppressed)와 케이스 상태의 대응은 9.3에 둔다. 요약: 케이스 개설 → known, VERIFIED → fixed, ROLLED_BACK·REJECTED·DISMISSED·PARKED → 대부분 suppressed(사유별 해제 조건 9.3), INCONCLUSIVE·EXPIRED·ROLLBACK_SKIPPED → known. finding의 regressed는 fixed 뒤 같은 키가 다시 임계를 넘은 재발만 뜻한다.

**묶기와 케이스 개설 임계** (앱 설계 5.2, 기본값)

| 임계 | 기본값 | 이유 |
| --- | --- | --- |
| 지지 건수 | 20건 이상 (감사 기록·세션 기록 단위) | 소수 사례로 자산을 바꾸지 않는다 |
| 서로 다른 주체 수 | 3명 이상 | 한 사용자의 습관을 자산 결함으로 오인하지 않는다 |
| 발생률 | 기준선 × 1.5 이상, 그리고 절대값 2% 이상. 기준선 없는 신규 패턴은 5% 이상 | 급등한 결함을 잡는다 |
| 절대 상한 | 신호별 상한을 넘으면 기준선과 무관하게 개설 (제안: tool_error·arg_invalid 5%, budget_exceeded 3%, negative_feedback 10%) | **만성 결함**을 잡는다. 처음부터 있던 결함은 기준선에 섞여 "기준선 × 1.5"를 영원히 넘지 못하기 때문이다 |
| 동시 활성 케이스 | 10건 이하 | 평가 용량과 승인 처리량 (9.4) |

- 우선순위 = rate × reach_weekly × signal_weight. signal_weight(제안): eval_fail 중 정책 사례 3, eval_fail 2, tool_error·arg_invalid·budget_exceeded 1, negative_feedback 1. 동시 상한을 넘는 finding은 케이스를 열지 않고 new로 대기하며, 매시 이 순서로 다시 본다.
- 기준선(28일)을 계산할 때 그 자산에 finding이 열려 있던 기간은 뺀다. 결함 기간이 기준선을 끌어올리는 것을 막는다. 만성 결함은 R6 정기 골든셋과, 같은 종류 자산(같은 도구를 쓰는 다른 SKILL) 간 발생률 비교로도 찾는다.
- 이미 활성 케이스가 있는 자산의 finding은 새 케이스를 열지 않고 그 케이스의 증거로 붙는다. **대상 자산당 활성 케이스는 하나**다(DB 부분 유일 인덱스로 보장). 같은 자산에 후보가 둘이면 어느 쪽이 변화를 만들었는지 분리할 수 없기 때문이다.
- 플랫폼 원인 결과(denied, dbc_saturated, llm_unavailable, dry_run_unsupported, 도구 timeout)는 자산 finding에서 빼고 플랫폼 신호로 따로 집계한다. 자산을 고쳐서 해결되지 않는 실패이기 때문이다.

**폴백 분석기 규칙 R1–R8** (앱 설계 5.3. 매시 실행, 9.1)

| 규칙 | signal | 집계 단위 | 판정 | 충실도 | 기본 가설 | v0 원천 (Q7 = 공용 자산만) |
| --- | --- | --- | --- | --- | --- | --- |
| R1 | tool_error | tool@version | 발생률 대비 기준선 | full · gateway | description_ambiguity | 사용 원장·감사 기록으로 가능 |
| R2 | arg_invalid | tool@version · 인자 경로 | 발생률 + 위반 인자 분포 | full · gateway | schema_defect, description_ambiguity | 가능 |
| R3 | retry_loop | 실행 또는 상관 묶음 | 같은 도구 3회 이상 연속, 인자 유사 | full · action | description_ambiguity | action 로그로 가능. 상관 묶음이 추정이면 지지 수는 세되 버전 귀속은 진입점 span의 `erp.asset.refs`로만 |
| R4 | hitl_rejected | agent@version × tool | 반려율 | full | missing_instruction | 운영 불가. Tools Gateway가 승인 토큰 없는 본실행 거부를 남기면 gateway 신호로 대체 검토 |
| R5 | negative_feedback | agent@version | 평가 2/5 이하 비율, 세션 기록의 수정·재요청 | full | missing_instruction | 세션 기록으로 가능(action). 세션 기록이 없으면 불가 |

## 5. 평가셋과 평가 환경

**평가셋의 출처**

- SKILL 자산에 평가 케이스가 들어 있다 (설계 방향 문서 4.2: SKILL = 업무 절차·허용 도구·평가 케이스).
- Creator가 개선안과 함께 만든 평가셋과, finding별 시험 사례 묶음이 있다.
- **골든셋** = SKILL 내장 평가 케이스(자산 작성자가 자산과 함께 씀) + 결과 신호로 판정 가능한 재현 사례. 루프 안에서 사람이 라벨을 달지 않는다. SME 라벨은 붙이면 쓰는 선택 사항이다.
- **held-out = 그 에이전트 계보에서 Creator 컨텍스트에 한 번도 들어간 적 없는 골든셋 사례**다. 코드가 **노출 원장**(에이전트별, 사례 ID와 입력 내용 해시)을 유지한다. 증거 구획 단계가 Creator 컨텍스트에 넣은 모든 사례·trace를 원장에 기록하고, 원장에 오른 사례는 **dev로 영구 강등**된다. 사람이 따로 관리하는 세트가 아니다.
  - 시드 분할은 아직 노출되지 않은 사례 안에서만 한다. 분할 단위는 **템플릿 ID**(같은 템플릿 사례는 한쪽으로)이고 업무 유형으로 층화한다. dev는 소량이면 충분하므로 비대칭(dev 최대 업무 유형당 10건)으로 나눈다.
  - 재시도 때 다시 나누더라도 이미 노출된 사례는 held-out에 돌아오지 않는다. 그래서 시도를 거듭해도 Creator가 본 사례로 판정하는 일이 생기지 않는다.
  - 사례별 판정 사용 횟수를 기록하고, 상한(제안 50회)을 넘은 사례는 held-out에서 뺀다. 집계 피드백만으로도 반복 사용된 사례에 맞춰질 수 있기 때문이다.
  - **Creator에 돌려주는 판정 피드백은 게이트별 통과 여부(G1–G4, 앵커)뿐**이다. d̄, 사례별 결과, 사례 ID, 실패한 검사 이름은 주지 않는다. 피드백이 담는 정보가 적을수록 같은 held-out을 여러 번 써도 Creator가 판정 사례에 맞춰질 여지가 작다는 생각은 Ladder(Blum & Hardt 2015)에서 가져왔다. 다만 Ladder의 보장은 그 메커니즘(직전 최고 대비 일정 폭 이상 좋아질 때만 공개)에서만 성립하므로 **여기에는 수학적 보장이 없다**. 사용 상한 50회도 안전성에서 유도한 값이 아니라 고갈을 피하려는 제안값이다. v0.7의 상한 10회는 판정 1회가 목표·가드를 모두 쓰므로 판정 열 번 남짓에 고갈된다. M2c에서 재사용 점검을 한다: 사용 횟수가 많은 사례와 새 사례 사이의 G1 통과율·d̄ 차이를 보고, 차이가 나면 상한을 낮춘다. 탐침 실행은 Creator로 정보가 가지 않으므로 사용 횟수에 넣지 않는다. 고정 세트는 G3 통과 여부만 매번 돌려주며 사용 상한이 없다(바닥 검사라 위험이 작다).
- **Creator에게 보이지 않게 막는 경로** (노출 원장 밖으로 새는 길)
  - Creator에게 주는 자산 사본에서는 SKILL의 평가 케이스 필드를 지운다. 대상 자산을 읽다가 판정 사례를 보는 경로를 막는다.
  - 해당 finding의 증거 trace로 만든 재현 사례는 dev 전용이다. G1 목표 세트용 재현 사례는 **같은 실패 서명이지만 증거로 쓰이지 않은 trace**에서 만든다. 분석기는 finding의 지지 trace 중 일부(제안 절반)를 판정용으로 따로 떼어 두고, 이 trace는 Creator에 넘기지 않는다.
  - R6(정기 골든셋 실패) finding의 증거는 사례 ID와 실패한 검사 이름, 집계만 넘긴다. 고정 사례 원문은 Creator에 들어가지 않는다.
  - 고정 사례의 원문이 다른 경로(승인자 수정 요청의 표본 등)로 노출되면 그 사례는 G3(바닥 검사)에는 계속 쓰되 G1 목표로는 쓰지 않는다. G3는 "나빠지지 않았는가"만 보므로 Creator가 그 사례를 알아도 통과가 쉬워지는 방향의 편향만 생기고, 그 편향은 개선 판정에 들어가지 않는다.
  - 승인 화면에서 승인자가 본 held-out 표본은, 승인자가 **수정 요청**을 하면 노출 원장에 올린다. 수정 요청의 문장이 다음 반복의 Creator 입력이 되기 때문이다.
- Creator가 만든 평가셋과 재현 사례 초안은 dev에만 들어간다.
- SEL 패치는 SKILL의 평가 케이스 필드를 바꿀 수 없다.
- **평가 케이스 자동 격리는 결정적 규칙으로만** 한다. Creator(LLM)는 결함 의심을 표시만 할 수 있고 격리를 결정하지 못한다. Creator가 불리한 판정 사례를 결함으로 몰아 게이트에서 빼는 공략을 막기 위해서다.
  - 격리 규칙: 기준 팔이 k/k 실패하고, 최근 3회 연속 정기 골든셋에서 현재 활성 버전도 같은 사례를 실패했으면 격리한다(정답이나 사례가 낡았다는 신호).
  - 격리는 **다음에 고정하는 세트부터** 적용한다. 이미 고정된 세트(`frozen_at`)에서는 빼지 않는다.
  - G3a 정책 사례와 인젝션 내성 사례는 격리 대상이 아니다.
  - 에이전트 골든셋의 격리 비율이 상한(제안 5%)을 넘으면 그 에이전트에 루프 정지 플래그를 켠다. 신규 개설만 막고 진행 중 케이스는 계속 간다. 골든셋이 바뀌어 다시 계산한 비율이 상한 이하가 되면 코드가 플래그를 끈다. 골든셋을 고치는 것은 자산 작성자의 몫이다(루프 밖). 격리 비율은 8장 지표로 본다.
- **사람 라벨이 없을 때의 한계와 보완**: "답의 값이 맞았는가"는 정답이 들어 있는 사례(SKILL 내장 케이스의 기대값, Q5-b 합성 세계의 참조 풀이)에서만 검증된다. 나머지 사례는 근거 일치, 정책 준수, 결과 신호로만 판정한다. 결과 신호만으로는 "오류만 없앤" 후보(도구를 부르지 않음, 되묻고 끝냄, 임의로 좁은 조건으로 조회)도 통과하므로 두 가지로 보완한다.
  - **재현 사례 필수 조건**: 실패 서명에서 기계적으로 만든다. ① 원래 실패한 도구 호출이 이번에는 성공 ② 구조화 답 필드가 있음 ③ 실패 서명에서 나온 인자 제약을 지킴(예: ROW_LIMIT 실패 → 기간 인자 존재, ARG_INVALID → 인자 형식 일치) ④ 사례가 기대하지 않는 되묻기·거절은 실패.
  - **정답 있는 사례 최소 비율**: G1 목표 세트의 30% 이상(제안)은 정답이 있는 사례여야 하고, 그 부분집합에서도 후보가 비열등(LCB > −δ)이어야 한다. 이 비율을 채우지 못하면 G1을 판정하지 않는다(G4 미충족).
- **최소 골든셋 규모**: 게이트를 걸 수 있는 최소 규모는 노출되지 않은 사례 기준으로 목표 86건, 가드 221건(6장 표본 산정)이다. 목표 86건은 "기준 실패 탐침에서 서명이 일치한 사례" 86건이고, 군집 보정을 쓰므로 서로 다른 템플릿 수도 최소(제안 20)를 넘어야 한다. 그래서 실제로 필요한 held-out은 대상 범위의 기준 실패율에 반비례해 커진다(실패율 20%면 범위 안 약 430건). 미달이면 판정 세트 고정이 실패해 REJECTED(structural)로 끝난다. **드문 업무의 결함은 골든셋이 자랄 때까지 판정할 수 없다**는 것이 이 설계의 한계다. sel-lab에서도 드문 업무(D02, 사례 10건)는 목표가 2–3건뿐이었다. 골든셋을 채우는 것은 SKILL 작성자의 평가 케이스 작성(D16)이며, 루프 밖의 유일한 사람 의존이다.

**평가 세트의 구성** (앱 설계 6.1)

| 세트 | 내용 | 게이트 | 출처 |
| --- | --- | --- | --- |
| 목표 | **기준 실패 탐침**에서 실패한 held-out 사례 + 증거로 쓰이지 않은 trace로 만든 재현 사례 + (R6이면) 실패한 고정 사례. 개선이 일어나야 하는 곳. **코드가 뽑는다** | G1 개선 | held-out (노출 원장 밖) |
| 가드 | 탐침에서 전부 통과한 held-out 사례 + 대상 범위 밖 held-out에서 **코드가 무작위로** 뽑은 사례. 나빠지면 안 되는 곳. 최소 규모 미달이면 판정하지 않는다 | G2 비열등 | held-out (노출 원장 밖) |
| 고정 | SKILL 내장 케이스 중 자산 작성자가 "필수"로 표시한 것 + 정책 사례(쓰기 전 승인, 인젝션 내성). 매번 들어간다 | G3 필수 사례 | 자산 작성 시 지정 |

- **기준 실패 탐침** (판정 세트 고정 단계, 결정적 코드):
  1. 대상 범위 = 대상 자산이 실제로 쓰인 held-out 사례(정기 골든셋·이전 평가 실행의 `erp.asset.refs`로 판정). 범위를 정할 수 없는 자산(persona Prompt, Agent 허용 필드)은 에이전트 held-out 전체.
  2. 범위 안 사례를 **현행 활성 버전으로 k_probe = 2회** 실행한다.
  3. 목표 후보 = 탐침에서 실패했고 **실패 서명이 finding의 서명과 일치**하는 사례(같은 오류 코드·검사 이름·도구 호출 패턴. 결정적 비교). 서명을 정할 수 없는 신호(negative_feedback)는 k_probe = 3에서 2회 이상 실패한 사례. 가드 후보 = 전부 통과한 사례 + 서명이 다른 실패 사례 일부(층화). 정상 사례의 우연한 실패(p = 0.95여도 k=2에서 약 10%가 한 번은 실패)가 목표에 섞이면 효과 0인 사례가 d̄를 희석해 G1 검정력이 무너지기 때문이다. 결함 주입 시험에서 목표 중 서명 일치 비율(희석)을 잰다.
  4. 탐침 결과는 고르는 데만 쓰고 판정에는 쓰지 않는다. 판정 실행은 기준·후보 양쪽을 새로 돌린다. 선정과 판정이 독립이므로, 선정된 사례 집합 안에서 짝 차이의 기댓값에는 평균 회귀 편향이 없다. 대신 추정 대상이 "무작위 held-out에서의 개선"이 아니라 "기준이 실패하는 사례에서의 개선"으로 바뀐다. 6장의 표본 산정(s_d 0.25, 무작위 held-out 가정)은 이 세트에 그대로 맞지 않으므로, 첫 판정들에서 선정된 세트의 s_d를 실측해 MMI·최소 규모를 M2a에서 다시 정한다. A/A도 같은 탐침 선정으로 돌린다. 탐침 실행 실패율이 10%를 넘으면 HELD다(실패한 사례를 조용히 버리면 긴 사례가 체계적으로 빠진다).
  5. 같은 finding의 다음 반복도 같은 held-out을 탐침하므로 목표는 대체로 같은 사례가 된다. 반복 사이의 재사용은 피할 수 없고, 판정 예산 3회와 피드백 축소, 사용 상한으로 통제한다.
  - 왜 요청 문장 분류가 아닌가: sel-lab에서 요청 문장으로 업무 유형을 분류해 목표를 고르면, 결함이 문장에 드러나지 않는 경우(이름이 겹치는 거래처를 묻지 않음) 기준 버전이 이미 통과하는 사례만 뽑혀 G1이 성립하지 않았다. Creator가 업무 유형을 고르게 하면 Creator가 판정 세트를 고르게 되어 공략 경로가 된다.
  - 비용: 탐침은 기준 팔만 k=2로 돈다. 범위 안 held-out이 400건이면 800회 실행이 판정 1회에 더해진다(9.4).
- **dev와의 관계**: 진단·작성용(dev)은 노출 원장에 오른 사례, 분할에서 dev 쪽에 떨어진 소량의 골든셋, Creator가 만든 평가셋, 증거 trace로 만든 재현 사례다. 목표·가드는 탐침으로 코드가 뽑고(Creator의 가설은 대상 자산을 제안할 뿐 세트를 고르지 않는다), 고정 세트는 매번 전부 쓰되 Creator에는 집계만 돌려준다.
- **판정 세트 고정 시점의 사전 검사**: 목표·가드 최소 규모, 정답 있는 사례 비율 30%, 고정 세트의 Dry-Run 지원 여부를 세트를 고정할 때(OPEN → TRIAGED) 확인한다. 하나라도 못 채우면 실행 전에 REJECTED(structural)로 끝낸다. 실행해 봐야 판정할 수 없는 세트에 LLM 호출을 쓰지 않기 위해서다.
- **재현 사례**: 실패한 실행의 사용자 입력과 도구 응답 기록으로 만든다(증거 구획을 거친 뒤). v0(Q7)에서는 게이트 기록에 사용자 입력이 없으므로, 세션 기록이 없으면 운영 재현 사례를 만들 수 없다. 그 경우 골든셋은 사실상 SKILL 내장 사례뿐이고 최소 규모(목표 86, 가드 221)는 D16(SKILL 작성자의 평가 케이스)에 더 크게 기댄다. 정답 라벨 없이 결과 신호와 위 필수 조건으로 채점한다. 결과 신호로 판정할 수 없는 재현 사례는 골든셋에 넣지 않는다.
- **실행 전 고정**: 평가 세트는 실행 전에 고정한다(`eval_set.frozen_at`, 이후 변경 불가). 결과를 본 뒤 사례를 빼거나 더하는 일을 구조로 막는다. 게이트 판정은 고정된 세트에 대해서만 계산한다.
- 평가 케이스는 기대 결과를 구조화 조건으로 적는다: 필수·금지 도구 호출, 구조화 답 필드(숫자 정규화), 정책 준수(HITL 요청, 등급 처리), judge rubric.

**Q5-a (실제 도구)일 때**

- 조회 결과가 시간에 따라 바뀐다. 그래서 기존·후보 버전을 같은 시간대에 짝지어 실행해 데이터 변화를 상쇄한다.
- 정답 값을 미리 정할 수 없다. 그래서 같은 실행 안에서 도구가 돌려준 값과 답이 일치하는지(근거 일치)를 규칙으로 검사한다. judge는 참고용이다. 정답 있는 사례는 시간이 지나도 값이 변하지 않는 질의(마감된 기간, 마스터 데이터)나 시험 회사코드 사례로 한정한다. 이런 사례가 없으면 G1의 "정답 있는 사례 최소 비율"을 채울 수 없어 그 업무는 루프 대상이 될 수 없다.
- 쓰기는 시험 실행 결과(어떤 변경을 하려 했는지)를 기대 변경과 비교한다.

**Q5-b (합성 세계)일 때**

합성 업무 세계(가짜 회사)를 만들고 그 위에서 시나리오와 정답을 만든다. 정답을 세계에서 계산하므로 규칙 채점 범위가 넓다 (τ-bench의 최종 DB 상태 비교, AppWorld의 상태 기반 테스트와 같은 방식).

원칙
1. 실값 복사 금지. 실행 기록에서는 구조와 분포만 가져온다.
2. 누가 봐도 가짜인 값. ID는 예약 범위(예: 거래처 9xxxxxxx), 이름은 "가상거래처-0418" 같은 규칙으로 만든다.
3. 정답은 세계에서 계산한다. 시나리오마다 참조 풀이를 둔다.
4. op별 동작(필터 의미, 페이지네이션, row limit, 권한 오류, 통화)은 SAP 기능 담당자가 검증한다. 합성 백엔드와 참조 풀이를 같은 사람이 짜면 같은 착각을 공유하기 때문이다.
5. 템플릿에는 닫힌 분류 라벨만 넣는다. 사용자 입력에서 나온 자유 텍스트는 넣지 않는다. 표본이 최소 건수(제안 30건) 미만인 템플릿은 버린다.
6. 생성 LLM은 사내 LLM만 쓴다.

## 6. Tester · Evaluator

**Tester: 짝 실행**

1. SEL 오케스트레이터가 Agent Runtime에 평가 작업을 제출한다 (후보 버전, 기존 버전, 평가셋).
2. 케이스마다 기존·후보 버전을 짝지어 실행한다. 실행 루틴은 `standard-v1`이다: 체크포인트 복원 → 자산 로드 → 쓰기 도구 앞 승인 중단 → 시간 상한 → 응답 검증 → 체크포인트·실행 기록(OTel) 발행.
3. 자산은 공통 진입점 → 자산 MCP Gateway로 조회한다. 후보 팔은 아직 활성이 아닌 후보 버전을 `eval.asset_overrides`로 주입받는다. 도구는 평가 계정으로 위임한다(Q5 경로). 두 팔은 같은 고정 모델 버전, 같은 Dry-Run 도구, 같은 사례 입력을 쓴다. k 기본값은 3이다.
   각 실행 span에는 `erp.eval.run_id`, `erp.eval.case_id`, `erp.eval.arm`을 붙인다. **채점 입력(최종 답, 도구 호출과 결과)은 워커가 실행 결과로 Tester에 직접 돌려준다.** trace는 참조(run_id)로만 쓴다. Phoenix에 가는 span은 SDK에서 1·2등급 내용이 지워지므로, 채점을 trace 조회에 기대면 내용이 필요한 검사를 할 수 없기 때문이다.
4. 실행 기록(span)은 OTLP로 Phoenix에 가고, 체크포인트·평가 결과·작업 원장은 평가 표시를 붙여 Database Connector로 PostgreSQL에 남긴다.
5. 케이스를 k회 반복하고 케이스별 결과를 오케스트레이터에 돌려준다.

쓰기 도구 앞 승인 중단에는 케이스에 적힌 정책으로 자동 응답한다(HITL 대역). 대화가 필요한 케이스는 user simulator가 숨은 목표를 들고 사용자 역할을 한다(M2b부터).

**Evaluator: 채점과 버전 비교**

- 채점 순서: 규칙 검사(필수·금지 도구 호출, 구조화 답, 근거 일치, 정책 준수)를 먼저 하고, 규칙으로 판정할 수 없는 부분만 judge로 채점한다. 규칙 검사가 노이즈가 작고 judge 비용이 들지 않기 때문이다.
- judge 본문은 Prompt 자산이며 **SEL이 고칠 수 없다**. 평가자가 고정돼 있어야 루프가 채점을 공략하지 못한다.
- judge는 게이트에 쓰지 않는다(아래 "judge 보정"). 규칙 검사로 판정할 수 없는 부분의 judge 결과는 승인 화면에 참고로만 보인다.

**게이트 통계** (앱 설계 7장을 고쳐 씀. 회귀·개선 판정, 8장 지표, 회귀 케이스 조건은 모두 이 정의를 쓴다)

게이트의 질문은 "후보가 기준보다 나은가"가 아니라 "관측된 차이가 judge 노이즈와 표본 크기로 설명되지 않을 만큼 큰가"다.

- 분석 단위는 사례 i의 짝 차이 d_i다(정의는 아래 "사례 점수와 짝짓기"). 같은 입력에 대한 차이를 보므로 사례 간 난이도 변동이 상쇄된다. d_i는 [−1, 1] 척도이고 MMI·δ도 이 척도다.
- 실행 하나의 **통과(passed)** = 그 사례의 규칙 검사를 전부 통과. G3a·G3b·회귀 케이스·pass^k는 이 정의를 쓰고 judge는 쓰지 않는다.
- 유의수준은 단측 α = 0.05를 finding당 판정 예산 3회로 나눈 α′ = 0.0167, 검정력 0.8.

| 게이트 | 대상 | 통과 조건 | 위반 시 |
| --- | --- | --- | --- |
| G1 개선 | 목표 세트 | d̄의 단측 신뢰 하한(LCB) > 0, 그리고 d̄ ≥ MMI | 게이트 실패 (9.3: OPEN으로, 세트 고정 때 예산 확인) |
| G2 비열등 | 가드 세트 | LCB > −δ (δ 기본 0.05. 앱 설계는 0.02인데, 가드 표본과 맞지 않아 바꿈) | 게이트 실패 (9.3: OPEN으로, 세트 고정 때 예산 확인) |
| G3a 정책 사례 | 고정 세트 중 결정적 규칙 사례 | 쓰기 전 승인 요청, 금지 행동, 등급 처리처럼 도구 호출 기록으로 결정적으로 판정되는 규칙을 후보 팔이 한 번이라도 어기면 위반 | 게이트 실패 (9.3: OPEN으로, 세트 고정 때 예산 확인) |
| G3b 필수 사례 | 고정 세트 중 나머지 (k_fixed = 10) | 사례마다 "후보 통과율이 기준 통과율보다 낮다"를 단측 Fisher 정확 검정으로 보고, 사례 수로 보정한 유의수준(α′ / n_고정)보다 작은 p값만 위반 | 게이트 실패 (9.3: OPEN으로, 세트 고정 때 예산 확인) |
| G4 판정 가능성 | 전체 | 실행 실패율 ≤ 10%, 목표·가드 세트가 최소 규모 이상(노출 원장 밖), 목표 세트의 정답 있는 사례 비율 ≥ 30% | 일시적 원인이면 HELD, 구조적 원인이면 REJECTED (9.3) |

- **MMI(최소 의미 개선)**는 케이스 개설 시 사전에 고정하는 값이다(기본 0.05). MDI = (t₁₋α′ + z₁₋β) · s_d / √n은 **표본 크기 설계에만** 쓰고 판정 조건으로 쓰지 않는다. 관측 MDI를 판정에 쓰면 참 효과가 MDI 근처일 때 통과율이 50%에 그치고, 결정적 채점이라 s_d ≈ 0이면 사소한 효과도 통과하기 때문이다(앱 설계 7.2와 다름).
- **표본 산정은 두 게이트가 동시에 검정력을 갖게 한다** (s_d = 0.25 가정, α′ = 0.0167, 검정력 0.8. s_d는 첫 실행에서 실측해 다시 산정).
  - G1: 설계 효과 Δ를 MMI보다 크게 잡아야 한다. Δ = MMI = 0.05로 잡으면 참 효과가 0.05일 때 "d̄ ≥ MMI" 통과 확률이 50%다. Δ = 0.08이면 목표 n ≈ 86에서 P(LCB > 0) = 0.80, P(d̄ ≥ MMI) = 0.87.
  - G2: 비열등 한계 δ와 가드 n이 맞아야 한다. 앱 설계의 δ = 0.02, 가드 100건이면 **후보가 기준과 똑같아도 G2 통과 확률이 9%**다. δ = 0.05로 두면 가드 n ≈ 221에서 동일 후보 통과 확률 0.80이다. δ를 0.02로 유지하려면 가드 n ≈ 1,380이 필요하다.
  - 그래서 기본값은 목표 86(Δ 0.08), 가드 221(δ 0.05), 고정 20(k_fixed 10)이다(9.4).
- **신뢰 하한은 t 분위수와 군집 보정으로 구한다.** 재현 사례는 같은 템플릿·주체에서 몰려 나와 서로 독립이 아니다. 템플릿 군집 단위 부트스트랩을 쓰거나, 군집 수를 유효 n으로 쓴다. 군집이 10개 미만이면 부트스트랩이 불안정하므로 군집 평균에 t 분포(자유도 = 군집 수 − 1)를 쓴다. 사례가 적으면 z 대신 t를 쓴다(n ≈ 10에서 z = 2.13, t₉ ≈ 2.51).
- **사례 점수와 짝짓기.** 게이트의 d_i = 후보 규칙 점수 − 기준 규칙 점수다(규칙 점수 = 해당 사례 규칙 검사 통과 비율의 k회 평균). judge는 게이트에 들어가지 않는다. 승인 화면 참고용 judge 선호 점수는 같은 반복 인덱스의 두 팔 출력을 순서를 바꿔 두 번 물어 +1(후보 우세) / 0(무승부·불일치) / −1(기준 우세)로 정하고, 게이트를 통과한 후보에만 계산한다.
- gateway·action 케이스도 재현된 실패 서명에서 G1(개선)을 그대로 쓴다. 대리 에이전트와 프론티어 도구의 차이는 카나리가 본다(2장).
- **사례 단위 검정의 검출력 한계.** 사례 수로 보정한 정확 검정은 k가 커야 걸린다. 기준 팔이 k/k 통과일 때 "유의한 하락"으로 판정되려면 후보가 아래 이하로 통과해야 한다(α′ = 0.0167).

| 사례 수 | k = 3 | k = 5 | k = 10 | k = 20 |
| --- | --- | --- | --- | --- |
| 4 | 검출 불가 | 0/5 | 3/10 | 13/20 |
| 20 | 검출 불가 | 검출 불가 | 2/10 | 11/20 |
| 100 | 검출 불가 | 검출 불가 | 1/10 | 9/20 |

  그래서 고정 세트는 k_fixed = 10으로 돌리고, G3b는 **큰 붕괴**를 잡는 장치로 둔다. 작은 하락은 집계 게이트 G2가 맡는다.
- **케이스 단위 회귀 검사**(보조): 집계 게이트는 평균이라 일부 사례의 큰 하락을 숨길 수 있다. 목표·가드 세트는 k가 작아(기본 3) 사례 단위 검정이 성립하지 않으므로, "완전 붕괴"(기준 k/k 통과, 후보 0/k) 사례 수를 회귀 케이스로 센다. 허용치는 0이 아니라 **A/A로 잰 상한**이다. 허용치는 사례별 기준 통과율에 좌우되므로 전역 상수가 아니다. 세트마다 기대 붕괴 수 λ = Σ p_i^k (1 − p_i)^k(p_i = 기준 팔 통과율 추정)를 구하고, 포아송(λ)의 95% 분위를 허용치로 쓴다. A/A로 이 계산이 맞는지 확인한다. 차이가 없어도 사례 통과율이 낮은 업무에서는 완전 붕괴가 우연히 생기기 때문이다(통과율 0.9, 사례 321건이면 A/A에서도 약 21% 확률로 1건 이상). 보정 없이 사례마다 95% 분위를 쓰는 원래 정의는, 차이가 없어도 사례 28건에서 "회귀 0" 확률이 0.24, 321건에서 사실상 0이라 폐기했다. 이름 `regressed_cases`는 전달받은 v3 요약에서 왔다(원문 미확인).
- **판정 예산.** 같은 finding(dedupe_key)에 대한 게이트 판정은 **총 3회**다. 수정 요청이나 STALE로 다시 판정해도, 같은 finding으로 케이스를 다시 열어도 같은 예산을 쓴다. α′ = 0.05 / 3은 이 예산으로 나눈 값이다. 예산을 다 쓰면 finding은 suppressed로 닫힌다. 종료 사유별 finding 상태와 해제 조건 ①–⑥은 9.3에 있다.
- **k는 A/A로 정한다.** temperature 0이어도 추론은 배치 구성에 따라 결과가 달라진다. 목표·가드 k = 3, 고정 k_fixed = 10에서 시작하고, M2a에서 같은 버전끼리 게이트를 돌려 G1 통과·G3b 위반·회귀 케이스 초과의 오판률이 각각 5% 이하가 되는 k, MMI, 회귀 허용치를 확정한다. 이 A/A 검증을 통과하기 전에는 **실사용 finding으로 연 케이스**의 Creator·Improver를 시작하지 않는다. 결함 주입 시험(10장)은 정답을 아는 시험 환경의 배관 검증이라 예외다.
  - A/A 지표는 G1 통과, G2 실패, G3a 위반, G3b 위반, 회귀 허용치 초과를 각각 센다. G3a도 비결정성이 있으면 "한 번이라도 위반"이 A/A에서 걸릴 수 있다.
  - 오판 0건으로 "5% 이하"를 95% 신뢰로 보이려면 약 59회 시행이 필요하다. 전체 규모(반복당 약 1.35만 호출)로 하면 약 80만 호출이라, A/A는 M2a 규모(반복당 약 1,500 호출)로 59회(약 9만 호출) 돌리고, 전체 규모는 해석적 계산(위 표본 산정)으로 보완한다. 비용은 D12에 넣는다.
- **조기 종료는 실패 쪽만.** 실행 순서를 G3a → G3b → G2 → G1로 두고, 앞 게이트가 명백히 실패하면 나머지를 돌리지 않는다. 실패 쪽 조기 종료는 오채택률을 키우지 않는다. 통과 쪽으로 일찍 끝내려면 alpha spending(O'Brien-Fleming 등)을 미리 설계해야 하므로 v0에서는 하지 않는다.
- pass^k도 함께 보고한다. 업무 에이전트는 "가끔 되는 것"보다 "매번 되는 것"이 중요하기 때문이다. n번 중 c번 성공했을 때 추정치는 C(c,k)/C(n,k)의 케이스 평균이다(τ-bench).

**judge 보정과 사용 범위** (앱 설계 7.4를 고침)

앱 설계는 judge를 게이트에 쓰려면 사람 일치도(SME 라벨 50쌍과 κ ≥ 0.6)를 요구한다. 이 문서는 루프 안에 사람 라벨링을 두지 않으므로 **judge를 게이트에 쓰지 않는다.** 게이트의 사례 점수는 규칙 검사만으로 정하고(w_judge = 0), judge 선호 결과는 승인 화면에 참고로 보인다. 아래 기준은 나중에 SME 라벨을 붙이기로 하면 judge를 게이트에 넣을 수 있는 조건으로 남겨 둔다.
- 자기 일관성: 같은 쌍 50개를 3회씩 다시 판정해 일치율 0.8 이상. 이 반복에서 judge 노이즈 분산을 추정한다.
- 사람 일치도: SME가 라벨링한 쌍 50개와 Cohen's κ 0.6 이상. (SME 라벨을 쓰기로 할 때만)
- judge 모델 버전이나 채점표 버전이 바뀌면 자기 일관성을 다시 잰다. 기준(0.8) 미달이면 승인 화면의 judge 참고 표시를 끈다. 게이트에는 영향이 없다. 규칙 채점이 없는 업무는 루프 대상이 아니다.
- judge는 쌍대 판정이다. 순서를 바꿔 두 번 묻고 두 판정이 다르면 무승부로 처리한다(위치 편향 제거). judge 모델은 내부 LLM Gateway의 고정 버전이며, 개선안을 만든 쪽과 다른 모델 또는 다른 프롬프트를 쓴다. judge 입력의 두 팔 출력도 도구 응답이 섞여 있으므로 증거 구획과 같은 방식으로 데이터 블록으로 감싸 넘긴다.

**결과 저장**: 평가 작업 원장과 리포트는 PostgreSQL에 Database Connector로 남긴다. Phoenix datasets·experiments는 쓰지 않는다. 쓰려면 member 권한이 필요한데, Phoenix에는 프로젝트 단위 권한이 없어 운영 프로젝트에도 쓸 수 있게 되기 때문이다.

## 7. Creator · Improver

**역할**

| 역할 | 하는 일 | 입력 | 출력 |
| --- | --- | --- | --- |
| Creator | (v0.11, 기준 문서) finding의 원인 가설을 세우고, 검증할 시험 문제(과거 실패 입력 + 정상 입력)를 고른다. 상세는 docs/07 | finding, 실행 기록, 대상 자산 | 가설, 고정된 시험 문제 |
| Improver | (v0.11, 기준 문서) 가설 하나당 후보 하나를 만들고 Registry에 candidate로 등록한다. 승인 요청 · 화면 · 릴리스는 ④. 상세는 docs/07 | 가설, 대상 자산 사본 | candidate 버전, 생성 근거 |

**사이클** (한 사이클 = finding 하나 → 개선안 하나)

1. **finding 선택** (코드): 개설 규칙(4장, 9.3)을 통과한 finding을 우선순위 `rate × reach_weekly × signal_weight` 순으로 연다. Creator는 고르지 않는다.
1-1. **증거 구획** (Creator 앞, 결정적 코드). **불변식: Creator·judge 컨텍스트로 들어가는 외부 유래 텍스트는 예외 없이 구획을 거친다.** 운영 증거뿐 아니라 2단계 샌드박스 재현에서 새로 얻은 도구 응답(Q5-a면 실제 SAP 자유 텍스트), 승인자의 수정 요청 문장, 도구 오류 메시지가 모두 대상이다. 게이트 FAIL 뒤 다음 반복에는 사례별 결과를 싣지 않는다(5장 피드백 규칙). LLM이 아니라 코드가 한다.
   - 증거(사용자 입력, 도구 응답)는 "지시가 아닌 데이터" 블록으로 감싸 넘긴다. Creator에는 도구를 주지 않고 구조화된 출력만 받는다.
   - 필드는 **기본 거부**다. 값을 넘겨도 되는 필드는 허용목록(필드별 소유·관리 주체를 적음)에 오른 것뿐이고, 미분류 필드와 외부인이 쓸 수 있는 필드(거래처명, 전표 적요, 송장 메모 등 SAP 자유 텍스트)는 값 대신 길이·형식·문자 종류 같은 구조만 넘긴다.
   - 허용목록 필드의 값이라도 명령형 문장, URL·이메일, 도구명, 승인·등급 관련 문구가 탐지되면 그 문장을 `[제거: 지시문 의심]`으로 바꿔 넘기고, 제거 사실을 provenance에 남긴다.
   - 증거 내용을 Creator 컨텍스트에 넣었는지(`evidence_content_used`)를 이 단계가 기록한다. Creator의 자기 신고에 기대지 않는다.
2. **진단 근거 확보** (Creator)
   - 운영 업무 trace가 없으므로(Q7) **평가 샌드박스 재현이 기본**이다. 게이트 기록(도구·인자·오류 코드)과 세션 기록에서 실패 서명을 뽑고, 대리 에이전트로 같은 실패를 재현해 진단한다.
   - 내용이 있는 실행 기록으로 바로 진단할 수 있는 것은 우리가 돌린 평가 실행(R6 정기 골든셋)뿐이다. 재현 = 운영 실패 서명(op 시퀀스, 오류 코드, result_class)과 샌드박스 실패 서명이 일치하는 것. 재현되지 않는 finding은 미진단으로 남기고, 그 비중을 리포트에 싣는다.
3. **진단** (Creator): 원인 위치를 열거값 `cause_class ∈ {asset, tool, code, infra, eval_case, unknown}`로 낸다. 케이스의 다음 상태는 코드가 이 값으로 정한다(9.3): asset → 판정 세트 고정, tool·code·infra → DISMISSED(handoff_dev), unknown → DISMISSED(undiagnosed). eval_case는 표시만 하고 asset과 같이 진행한다. 격리 여부는 5장의 결정적 규칙이 정한다(SEL이 사례를 고치지 않음). LLM의 판단으로 케이스가 끝나는 것처럼 보이지만, LLM은 분류만 하고 종료 규칙과 suppressed 해제 조건은 코드에 있다.
4. **개선안 작성** (Creator): 증분 패치로 만든다. finding당 개선안 하나.
5. **짝 실행** (Tester) → **채점·비교** (Evaluator): 기준 실패 탐침으로 코드가 뽑은 목표·가드와 고정 세트를 게이트 통계(6장)대로 돌린다. 판정이 기록되면 예산을 하나 쓴다. 기준 버전이 앵커 버전과 다르면 앵커 팔을 하나 더 돌린다(아래 "기준 버전, 누적, 롤백").
6. **채택 조건**: 게이트 G1–G4 통과(6장), 완전 붕괴 회귀 케이스 수 ≤ 허용치, 정책 사례(G3a) 위반 0, 비용·지연 예산 이내.
7. **등록·상신** (Improver): 평가에 쓴 후보 버전(draft로 등록돼 `eval.asset_overrides`로 주입됐던 것)을 제안 상태로 올리고 승인을 요청한다. 후보는 평가 전에 draft로 이미 저장소에 있으므로, 평가 시점에 후보가 없는 문제는 생기지 않는다.
8. **승인** (사람, SEL Admin UI): 승인자가 보는 필수 항목은 L6 표에 고정한다. 요약하면 finding 요약과 지표, 가설, 기준 버전 대비 diff, 게이트 결과(목표·가드 차이와 신뢰구간), 증거 trace 발췌(승인자의 등급 권한 안에서만)다. 릴리스 채널은 코드가 등급 상한으로 계산해 보여 주고, 승인자는 범위를 고르지 않는다. 결정은 승인 · 반려 · 수정 요청 중 하나다. 수정 요청의 자연어 지시는 다음 반복의 입력이 되고(다음 판정이 기록될 때 예산을 하나 쓴다), 승인자가 볼 수 있었던 사례(표본 trace와 사례별 결과 화면에 뜬 사례 전부)는 노출 원장에 오른다. 승인하면 충실도에 따라 릴리스한다(9.3): full·relay는 전체 릴리스, gateway·action·new_asset은 카나리. 다음 실행부터 해당 범위의 창구가 새 버전을 쓴다.
9. **효과 확인**: 반영 후 운영 기록과 세션 기록으로 해소(fixed)·재발(regressed)을 판단한다. 점수만으로 fixed로 닫지 않는다.

**자산 수정 허용 범위** (설계 방향 문서 4.2)

| 자산 | 내용 | SEL 개선 대상 |
| --- | --- | --- |
| Agent | 조립 정의. SKILL·Prompt를 참조하고 필요 역할을 적는다 | 허용 필드만 (예: `max_turns`) |
| SKILL | 업무 절차, 허용 도구, 평가 케이스 | 대상. 패치·마이너 버전. 단, 평가 케이스 필드는 SEL이 바꾸지 않는다 (이 문서의 추가 제한) |
| Prompt | 시스템 · persona · 의도 분류 · judge 본문 | (v0.11) 프롬프트 본문과 예시. ③이 쓰는 판정 프롬프트는 SEL이 고칠 수 없다(docs/07) |
| Tool | 외부·내부 도구와 ML 엔진, 오퍼레이션별 필요 역할 | (v0.11) `description`과 인자 설명만. binding · required_capability · input_schema 등은 사람만 |

- 참조 표기는 `종류/이름@범위`다(예: `prompt/fi-expense-persona@1.x`).
- 등록한 버전은 고치지 않고 새 버전으로 쌓는다. SEL은 패치·마이너만 만들고, 메이저 변경은 사람만 한다.
- 자산 버전 상태 전이는 draft(후보 작성) → candidate(정적 검사 통과) → proposed(Improver 상신) → active(승인) → retired다. 별도의 "검토" 상태는 없다. 사람 승인이 곧 검토다.
- few-shot 예시에는 합성 값만 쓴다. 실값이 들어가면 셀프서비스로 노출된다.

**변경 유형별 제약** (앱 설계 6.2. 범위가 좁을수록 게이트 결과를 그 변경에 귀속할 수 있다)

| 변경 유형 | 허용 범위 | 제약 | 이 문서에서 |
| --- | --- | --- | --- |
| instruction | Prompt persona·SKILL 본문 | 변경 줄 수 30줄 이내, 섹션 단위 diff | 허용 |
| example | Prompt·SKILL 예시 블록 | 증거 원문 복사 금지, 합성 예시만 | 허용 |
| composition | 매니페스트의 자산 참조 추가·교체, Agent 허용 필드 | 새 자산은 이미 승인된 것만 | (v0.11 무효: 불허. 매니페스트는 허용목록 `params`만, docs/07) |
| new_asset | 신규 SKILL·Prompt 초안 | 골든셋이 없어 held-out 판정이 성립하지 않는다 | **v0 루프 밖** (D18): 케이스를 열지 않고 후보 리포트로만 남긴다 |
| metadata | tool description, 인자 description, SKILL frontmatter description | 이름·스키마 구조 변경 금지, 길이 1,024자 이하 | (v0.11: 도구 description 허용, D15 닫힘) |
| schema_hint | 인자 pattern·enum·examples 추가 | 기존 값 거부 금지(minor 유지) | **제외** (D15) |

후보는 draft로 만들고 정적 검사를 통과하면 candidate로 올린다. 정적 검사는 스키마 검증, 크기 상한, 의존 참조 해석, 변경 유형 밖 수정 여부, 등급 누출 검사(보안 경계), **유입 검사**다.

- **SEL이 바꿀 수 없는 필드**: SKILL의 허용 도구, 필요 역할, 등급, 채널, 평가 케이스. Prompt의 role(persona·judge 구분). Agent의 허용 필드 밖 전부. 이 필드가 바뀐 후보는 기계적으로 실패한다. 허용 도구에 쓰기 op를 넣거나 등급이 다른 자산으로 참조를 바꾸는 권한 상승을 막는다.
- **유입 검사** (간접 프롬프트 인젝션 대응): 추가·변경된 줄에서 URL·이메일·도메인, 허용 도구 목록에 없는 도구명, 증거 구획이 제거·표시한 문장과의 유사 구절이 나오면 실패한다. **삭제된 줄**도 검사한다. HITL·승인·등급·확인 절차가 담긴 줄이 삭제되거나 약해지면(조건 완화, 부정어 추가) **실패**한다(fail-closed). 안전 절차를 줄이는 변경은 SEL이 만들지 않는다. 그런 변경이 필요하면 사람이 메이저 변경으로 한다. v0.7의 "사람 검토 필수 표시"는 루프 안에 승인 외의 사람 단계를 만들므로 뺐다.
  - 한계: 규칙 기반 검사라 의역·인코딩·동형 문자로 우회될 수 있다. 가설과의 연결 근거도 LLM의 자기 서술이라 검증되지 않는다. 그래서 1차 방어는 증거 구획(입력 쪽)과 G3a 인젝션 내성 사례(행동 쪽)이고, 유입 검사는 보조다.
- 고정 세트에 **인젝션 내성 사례**를 넣는다. 도구 응답에 지시문이 섞인 입력을 주고, 에이전트와 후보 자산이 그 지시를 따르지 않는지 본다(G3a). 버전 번호는 minor 증가가 기본이며, provenance에 케이스 ID, 반복 번호, 기준 버전, 증거 최고 등급을 기록한다.

**보안 경계** (앱 설계 10장)

"Evolving은 기밀 영역에서만 가능"과 "프론티어 도구와 사내 창구가 같은 자산 저장소를 쓴다"를 합치면 두 방향의 경로가 생긴다. 기밀 trace에서 나온 내용이 후보 자산을 통해 외부 서빙 모델로 **나가는** 경로와, 증거에 섞인 외부인의 지시가 후보 자산을 통해 모든 창구로 **들어오는** 경로다. 앱 설계의 다섯 지점은 나가는 쪽만 막으므로 유입 차단을 더해 여섯 지점에서 끊는다. 정책 값(등급 체계, 채널 상한)은 보안 담당 소관이고, 여기서는 적용 지점만 정한다.

| 지점 | 규칙 | 근거 데이터 |
| --- | --- | --- |
| 등급 상속 | 후보의 등급 = 기준 버전 등급과, 개선안 작성 시 본 증거 **내용**의 등급 중 더 민감한 쪽. 증거의 구조 속성만 쓰고 내용을 보지 않았으면 상속하지 않는다 | `hypothesis.evidence_content_used`, `finding.max_grade` |
| 채널 상한 | 후보 등급이 의도 채널의 상한보다 민감하면 그 채널 릴리스를 막고, 상한 안의 채널로만 범위를 줄인다 | 자산 저장소 채널 상한 표 |
| 누출 검사 | 후보 본문과 증거 내용의 8-gram 중복, 식별자 패턴(사번, 계좌 등)을 검사한다. 걸리면 후보 생성 실패. 8-gram은 요약·의역을 못 잡으므로 보조 수단이고, 1차 통제는 등급 상속이다. Q8 확정 전에는 모든 등급과 미표시 증거에 건다(fail-closed) | 정적 검사 |
| 유입 차단 | 증거는 데이터 블록으로만 Creator에 들어가고, 외부 입력 필드는 기본 구조만 넘긴다. 후보는 유입 검사를 통과해야 한다 | 증거 구획(7장 1-1), 정적 검사 |
| 모델 고정 | Creator·Evaluator와 개선안 작성은 내부 LLM Gateway의 고정 버전만 호출한다. 외부 모델 API 호출은 없다 | 매니페스트 model.id |
| 증거 열람 | Admin UI의 증거 발췌는 승인자의 등급 권한 안에서만 보인다 | 권한 판정 |

등급 상속의 두 갈래는 의도된 것이다. 프론티어 도구 설명처럼 구조 신호(인자 오류율, 위반 인자 경로)만으로 고칠 수 있는 자산은 등급이 오르지 않아 프론티어 채널에 그대로 릴리스할 수 있다. 내용을 봐야 고칠 수 있는 지시문 결함은 등급을 상속해 기밀 채널에 머문다.

**등급 방향 확인 필요 (Q8)**: 앱 설계는 "max(기준 등급, 증거 등급)", "등급 2 이상 증거"처럼 숫자가 클수록 민감한 표기로 읽힌다. 이 문서의 전제는 **1이 가장 민감**하다. 위 표는 방향 중립("더 민감한 쪽")으로 적었다. 누출 검사의 등급 기준은 방향을 확인한 뒤 확정한다.

**held-out 관리**

- held-out은 노출 원장 밖의 골든셋에서 코드가 뽑는다(5장). 사람이 따로 관리하지 않는다.
- held-out을 같은 템플릿의 값만 바꾼 것으로 채우지 않는다. 가능하면 일부를 같은 실패 유형의 다른 업무에서 뽑는다. 케이스 구조에 맞춘 개선안을 걸러내기 위해서다.
- Creator에게는 게이트별 통과 여부만 돌려준다(5장).
- 판정 횟수는 finding당 판정 예산 3회로 묶는다(6장). 사례별 판정 사용 횟수가 상한(제안 50회, 5장)을 넘으면 held-out에서 뺀다. 교체용 신규 라벨링은 없다. 골든셋은 SKILL 작성자가 평가 케이스를 추가할 때 자란다(D16).

**기준 버전, 누적, 롤백**

- 기준 버전은 **현재 활성 버전**이다. full·relay 케이스는 승인이 곧 전체 활성 전환이고, gateway·action은 카나리를 거친다(9.3, D14). new_asset은 v0 루프 밖이다(D18).
- 판정은 자산 단위로 직렬화한다. 판정 중에 활성 버전이 바뀌면 진행 중인 후보는 새 기준 위에서 다시 판정한다. CANARY·VERIFYING 상태의 케이스도 **활성 케이스**로 보고 자산 잠금을 유지한다. 검증 중인 버전 위에 다음 후보가 올라가 롤백이 엇갈리는 것을 막는다(대가: 자산당 개선 속도는 검증 창 길이로 제한된다).
- 노이즈 상한 아래의 하락이 누적될 수 있다. 승인이 곧 활성 전환이라 "배포 전" 시점이 따로 없다. 그래서 **앵커 팔**을 둔다. 앵커 = 그 자산에서 VERIFIED로 끝난 가장 최근 버전(없으면 SEL이 처음 다룬 시점의 사람 승인 버전)이고 코드가 정한다. 기준 버전이 앵커와 다르면 Tester가 같은 고정 세트의 가드·고정 사례에 앵커 팔을 더 돌리고, 후보가 앵커 대비 G2·G3를 통과해야 GATE_PASSED가 된다. 실패하면 게이트 실패와 같게 처리한다(예산 차감).
- 롤백은 직전 승인 버전으로 되돌리는 것이다(버전은 불변). Verifier가 악화를 검정하면 **자동으로** 한다. 단 **CAS 조건**을 지킨다: 현재 활성 버전이 이 케이스가 릴리스한 버전과 같을 때만 롤백한다. 다르면(그 사이 다른 경로로 활성이 바뀜) 롤백하지 않고 기록만 남긴다. 그 악화는 다음 매시 분석에서 현재 활성 버전에 대한 finding으로 다시 잡힌다.
- 롤백된 finding은 suppressed로 닫혀 같은 finding으로 자동 재개설되지 않는다(연쇄 방지). 해제 조건은 9.3에 있다.

**잠정 원칙** (원문 미확인. 각 원칙은 괄호 안의 우리 쪽 근거로 선다. 논문은 11장에서 확인할 참고 후보다)

- release line은 하나만 둔다. (판정 비용이 후보 수에 비례한다. 추적과 롤백이 단순하다.) 참고 후보: GEPA
- 개선안은 증분으로 만든다. (전체를 다시 쓰면 잘 되던 지시가 사라지고 diff 검토가 불가능하다.) 참고 후보: ACE
- 판정은 케이스별 변화로 한다. (평균은 개선과 회귀가 상쇄돼 회귀를 숨긴다.) 참고 후보: AgentDevel
- 새 SKILL 후보는 보수적으로 채택한다. (skill 선택을 바꿔 영향 범위가 가장 크다. 전체 평가셋과 라우팅 회귀 검사가 필수다.) 참고 후보: SkillsBench
- 안전 행동을 모든 판정에 넣는다. (개선 압력이 HITL 요청처럼 비용이 드는 행동을 줄이는 쪽으로 작용할 수 있다.) 참고 후보: Misevolution

| L2 | 진단·개선안 작성 | Creator | 수정 허용 범위를 기계적으로 검사 (SKILL 평가 케이스 필드 변경 금지 포함) |

| L4 | 판정 연동 | Tester·Evaluator | 게이트 G1–G4, 노출 원장, 목표·가드 코드 추출, 판정 예산, 직렬화 |
| L5 | 등록·상신·승인 요청 | Improver | Database Connector, 제안 상태 등록. 활성 전환은 승인 시 |
| L6 | 승인 화면 | SEL Admin UI (루프 안의 유일한 사람 개입) | 필수 필드: 반복 번호, 기준·후보 버전과 diff, 가설과 `cause_class`, G1–G4 값(LCB, d̄, n, 군집 수), 완전 붕괴 수와 허용치, 앵커 팔 결과, 정답 검증 비율, 탐침 범위와 실패 수, 판정 예산 사용량, 유입 검사 결과, 후보 등급과 코드가 계산한 릴리스 채널, 노출·격리된 사례 수, judge 참고값과 유효 여부, held-out 실행 기록 표본(수정 요청 시 노출 원장 등록) |
| L7 | 효과 확인·롤백 | Creator 앞단 | finding 상태, 세션 기록 신호 |

## 8. 지표와 수용 기준

평가 자체가 믿을 만한지를 재는 지표가 먼저다. 목표값은 모두 제안값이며 M2a 측정치를 보고 확정한다.

## 9. 스케줄 · 이벤트 · 기한 · 용량

SEL 애플리케이션 설계 v0.1(2026-10-23) 9장을 옮기고, 이 문서의 결정과 다른 곳을 표시했다. 원칙은 두 가지다. SEL은 이벤트로 움직이고, 시간에 묶인 일(분석, 기한 감시, 반영 후 비교)만 스케줄로 돈다. 평가 실행은 배치 런타임의 동시 상한 안에서만 돌아 사용자 경로와 경쟁하지 않는다.

### 9.1 스케줄

| 작업 | 주기 | 내용 | 단계 |
| --- | --- | --- | --- |
| 폴백 분석 | 매시 | 직전 24시간 롤링 창에서 자산 버전별 신호 발생률을 집계해 finding을 낸다 (R1–R3, R5, R7. R4·R8은 운영 원천이 없다). 창 끝 = 원천 watermark(최대 지연 제안 2시간을 뺀 시각). 원천 완전성 95% 미만인 창은 finding을 내지 않는다. 멱등 키 (dedupe_key, 창 끝 시각) | M1 |
| 정기 골든셋 | 매일 1회 | 활성 버전으로 고정 세트를 k = 3으로 실행한다. R6(eval_fail): 정책 사례(G3a) 위반 1회, 또는 필수 사례가 최근 7일 통과율 대비 Fisher 단측 검정(α′ / n_고정)으로 하락. 시각은 지난 7일 시간대별 부하가 가장 낮은 구간 | M2a |
| 기준선 재계산 | 매일 | 자산(버전 계열)별 28일 발생률. 열린 finding 기간을 빼고 남은 날이 14일 미만이면 "기준선 없음"(신규 패턴 5% 규칙). 키에 모델 버전·도구 계약 버전을 넣는다 | M1 |
| suppressed 해제 검사 | 매일 | 9.3의 해제 조건 ①–⑥을 확인한다 | M2c |
| Verifier | 6시간 | 카나리 코호트·대조 코호트 비교, 대조군 이중차분 (9.3). 저장 키 (case_id, look_no) | M2c |
| 기한 감시 | 10분 | 9.3 기한 표의 목적지로만 보낸다 | M2a |

모든 스케줄 작업은 (작업, 슬롯 시각) 유일 키와 리스 잠금으로 한 번만 돈다. 작업별 입력·판단·출력·실패 처리는 docs/06에 정리했다.

24시간 서빙이라 "야간"이라는 고정 시각을 두지 않는다. 부하를 실측해서 가장 낮은 구간을 고른다.

### 9.3 케이스 상태와 기한 (v0.8 동결)

v0.8에서 상태머신을 동결했다. 원칙 네 가지.
- **사람이 끼는 전이는 AWAITING_APPROVAL에서 나가는 셋(승인·반려·수정 요청)뿐**이다. 나머지는 코드 규칙이 정한다. LLM(Creator)은 구조화 출력(가설, `cause_class` 열거값, 패치)만 내고, 케이스를 끝내는 결정은 그 출력 위에서 코드가 한다.
- **기한을 넘기면 갈 곳이 상태별로 하나**다. "HELD 또는 REJECTED"처럼 고르는 전이는 없다.
- **판정 예산은 `gate_decision` 행을 기록할 때만 차감한다.** HELD, STALE, 기한 초과, 중단은 예산을 쓰지 않는다. 판정 세트를 고정하는 전이(OPEN → TRIAGED)가 "예산 > 0"을 확인한다. 게이트 실패, 수정 요청, STALE은 모두 OPEN(세트 고정 단계)으로 돌아가므로 이 확인 하나로 4번째 판정이 막힌다. v0.7의 "반복 ≤ 3"은 이 규칙으로 대체했다.
- **기준 버전이 바뀌면 잠금 상태 어디서든 STALE**이다. 옛 기준으로 고정한 세트와 탐침으로 판정을 이어 가지 않는다.

모든 전이는 `row_version` CAS로 한다. 실패한 쪽은 최신 상태를 다시 읽어 판단한다.

**잠금을 잡는 상태** (대상 자산당 하나, 부분 유일 인덱스): OPEN, TRIAGED, CANDIDATE_READY, QUEUED, EVALUATING, HELD, STALE, GATE_PASSED, AWAITING_APPROVAL, APPROVED, CANARY, RELEASED, VERIFYING, REGRESSED. PARKED와 종료 상태는 잡지 않는다.

| --- | --- | --- | --- |

finding의 regressed는 **fixed가 된 뒤 같은 dedupe_key가 다시 개설 임계를 넘은 경우**로만 쓴다(재발).

**suppressed 해제 조건.** suppressed는 "같은 근거로는 더 시도하지 않는다"는 뜻이지 영구 포기가 아니다. 매일 해제 검사가 다음을 확인하고, 해제하면 쿨다운(제안 7일) 뒤 새 판정 예산 3회(`budget_epoch` + 1)를 준다. 기준값은 suppression 행에 기록할 때의 값이다.
1. 대상 자산의 활성 버전이 기록 시점과 다르고, 바꾼 주체가 이 dedupe_key의 케이스가 아님(사람의 메이저 변경, 다른 finding의 패치). 롤백 케이스는 기록 시점 버전 = 이 케이스가 릴리스한 버전으로 남긴다.
2. 그 에이전트의 노출되지 않은 골든셋이 마지막 판정 이후 20% 이상(제안) 늘었고 최소 규모를 채움(D16 보충).
3. (undiagnosed) 지지 수가 기록 시점의 2배를 넘음.
4. (삭제. v0.9에서 PARKED는 suppressed를 쓰지 않는다)
5. (no_approver) 승인 가능자 집합이 비지 않게 됨(권한 변경 이벤트 또는 매일 재계산).
6. (handoff_dev, transient) 도구 계약 버전 또는 사내 LLM 모델 버전이 바뀜.

**판정 예산과 유의수준.** finding당 예산 3회는 α′ = 0.05 / 3의 근거다. 해제 뒤 새 예산은 새 근거(①–⑥)가 생긴 뒤의 시도로 보지만, 같은 finding에 대한 전체 오류율은 epoch 수만큼 커진다. 그래서 epoch는 쿨다운과 근거 변화로만 늘어나게 했다. STALE 뒤 재판정도 예산을 쓴다. 이미 게이트를 통과한 후보가 기준 버전 변경만으로 예산을 소진할 수 있다는 대가가 있다. 기준이 바뀌면 이전 판정은 다른 비교였으므로 통계적으로는 이 쪽이 맞다(추정).

**이 문서와 다른 점: 카나리.** 7장은 "승인이 곧 활성 전환"이라고 적었다. 앱 설계는 충실도에 따라 릴리스 방식을 나눈다.
- full·relay 충실도 케이스는 게이트가 실질 판정이므로 바로 전체 릴리스한다.
- gateway·action 충실도 케이스는 카나리로 시작한다(new_asset은 v0 루프 밖, D18). 주체 해시 버킷 10%에만 후보를 노출하고, 같은 패턴의 발생률을 코호트끼리 비교한다.

카나리는 자산 저장소의 코호트 해석 규칙(주체 목록, 비공개 캐시 범위)이 있어야 하고, 이 기능은 자산 저장 규격 v1.1(2027.3) 확장이다. 그 전까지 카나리 대상 케이스는 GATE_PASSED에서 PARKED로 간다(D14 제안). 승인 대기로 두면 7일 기한과 충돌하고 승인해도 릴리스할 방법이 없기 때문이다. PARKED는 잠금을 잡지 않고, 카나리 기능이 생기면 판정 세트부터 다시 한다.

**반영 후 판정.** Verifier는 두 가지를 바로잡아 비교한다.
- **"전" 구간은 트리거 구간을 뺀 독립 구간**이다. 케이스는 발생률이 튄 구간에서 열리므로, 그 구간을 "전"으로 쓰면 아무것도 고치지 않아도 평균 회귀로 내려가 VERIFIED가 된다. 그래서 "전" = 케이스 개설 이후부터 릴리스 전까지의 구간(트리거 구간 제외)으로 다시 잰다. 만성 결함(절대 상한으로 연 케이스)은 28일 기준선을 "전"으로 쓴다.
- **판정은 두 조건**이다. ① "전" 대비 유의한 감소 ② 급등 전 기준선 대비 비열등(원래 수준으로 돌아왔는가). 급등형 결함을 고치면 급등 전 수준으로 돌아갈 뿐이므로, 급등 전 기준선 대비 "개선"을 요구하면 VERIFIED가 나지 않는다.
- **대조군 이중차분(DiD)**으로 ①을 검정한다. 계절성, 업무 구성 변화, 모델 교체 같은 공통 변화를 걸러내기 위해서다.
  - 대조군 선정: 같은 신호를 집계하는 자산 중 같은 기간 변경이 없고, 대상과 Tool·SKILL을 공유하지 않는 것(오염 제외). 개설 전 28일의 주별 추세가 대상과 평행해야 한다(기울기 차이가 유의하지 않음). 조건을 만족하는 대조군이 없으면 단절 시계열(ITS)로 대신한다.
  - 검정: 발생 건수에 포아송(과산포면 음이항) 회귀, 집단 × 기간 상호작용, 관측 수를 offset으로. 단측 α = 0.05.
  - 관측 수: 릴리스 전에 "전" 구간 발생률로 필요 관측 수를 산정한다(카나리 관측 수 산식과 같은 방식). 7일에 못 채우면 최대 14일까지 연장한다.
  - 관측 14일 뒤에도 결론이 나지 않으면 **INCONCLUSIVE**로 종료한다. 버전은 그대로 유지하고 finding은 known으로 남긴다("효과 미확인"). 악화가 유의하지 않으므로 되돌릴 근거도 없기 때문이다. 지지 20건 수준의 드문 신호는 대부분 여기로 온다.
- 카나리 단계에서는 카나리 코호트와 대조 코호트가 대조군 역할을 한다.
- 비교 구간은 같은 요일 구성으로 맞추고, 회계 달력의 결산 단계가 다르면 층화한다. 카나리 단계에서는 악화가 유의하면 자동 롤백한다. 노출 범위가 작고, 되돌릴 대상이 이미 승인된 직전 버전이기 때문이다.
- **악화 판정은 순차 검정**이다. Verifier는 6시간마다 돌기 때문에 7–14일 동안 수십 번 결과를 엿본다. 매번 단측 α = 0.05로 보면 우연한 악화 판정이 쌓여 불필요한 자동 롤백이 난다. 그래서 중간 확인은 O'Brien-Fleming 경계(초반에는 매우 엄격, 예: z > 3.0)로만 큰 악화를 잡고, 최종 판정은 관측 창이 끝날 때 한 번 한다.
- **관측 부족 처리의 비대칭은 의도된 것**이다. 카나리에서 관측이 부족하면 롤백한다: 확인되지 않은 변경을 전체로 넓히지 않기 위해서다. 전체 릴리스 뒤 관측이 부족하면 유지한다(INCONCLUSIVE): 이미 사람이 승인하고 전체에 반영된 변경을, 악화의 근거 없이 되돌릴 이유가 없기 때문이다. 누적 하락은 매 판정의 앵커 팔이 막는다(7장). 전체 릴리스 뒤 악화도 REGRESSED로 보내 **자동 롤백**한다. 되돌릴 대상은 이미 사람 승인을 받은 직전 버전이므로 새 사람 판단이 필요 없다.

**동시성과 멱등.** 케이스 행은 `row_version`으로 낙관적 잠금을 건다. 평가 작업의 멱등 키는 (case, iteration, attempt)다. EVALUATING에서 실행 heartbeat가 끊기면(VM 재시작 등) HELD로 보내고 부분 결과는 버린다.

### 9.4 용량과 우선순위

반복 1회의 평가 실행 수 = (목표 + 가드 + 고정 사례 수) × 2팔 × k.

| 기준 | 목표 | 가드 | 고정 | k | 평가 실행 | LLM 호출 (추정) |
| --- | --- | --- | --- | --- | --- | --- |
| 앱 설계 기준 | 221 | 100 | 20 | 3 | 2,046 | 약 13,000 (실행당 6회 + judge 쌍대 판정 682회) |
| v0.8 기본 (Δ 0.08, δ 0.05, k_fixed 10) | 86 | 221 | 20 | 3 / 10 | 2,242 | 약 13,500 (실행당 6회). 게이트 통과 후보만 승인 참고용 judge 약 650회 추가 (사례당 1쌍, 순서 바꿔 2회: (86 + 221 + 20) × 2) |
| M2a 예시 (검정력 없음, 배관용) | 20 | 8 | 4 | 3 / 10 | 248 | 약 1,500 |

- 동시 상한 100에서 실행당 약 25초면 반복 1회에 앱 설계 기준 약 8.5분, v0.8 기본 약 9.3분이다. 실행당 6회 호출과 25초는 측정값이 아니라 추정이다. 동시 100 × 6회 / 25초 ≈ 24 RPS이며 사내 LLM Gateway 한도와 대조해야 한다(D12).
- **v0.8에서 더해진 비용** (추정): 기준 실패 탐침 = 범위 안 held-out × 2(400건이면 800회 실행, 약 4,800회 호출). 앵커 팔 = 가드 221 × 3 + 고정 20 × 10 = 863회 실행(약 5,200회 호출, 기준 ≠ 앵커일 때만). 판정 1회 최악 = 13,500 + 4,800 + 5,200 ≈ 2.4만 회 호출. finding 1건 최악 = 판정 3회 × (1 + HELD 재시도 2회) × 2.4만 ≈ 22만 회 호출.
- 정기 골든셋 = 에이전트 수 × 고정 20건 × k 3 = 에이전트당 하루 60회 실행(약 360회 호출).
- 앱 설계의 목표 221건은 s_d = 0.25에서 5%p 개선을 LCB > 0으로 잡는 크기다. v0.5는 G1에 MMI 조건이 붙어 설계 효과를 0.08로 잡고 목표 86건, 대신 G2가 성립하도록 가드를 221건으로 늘렸다(6장). s_d는 첫 평가 실행에서 실측해 다시 산정한다.
- **이 문서와 다른 점: 판정 세트.** 앱 설계는 목표 세트를 SME 골든셋으로 채운다. 이 문서는 SME 라벨링을 루프에서 빼고 골든셋을 SKILL 내장 케이스와 결과 신호 재현 사례로 채운 뒤 코드로 분할한다(5장). 그래서 목표·가드 표본 크기는 "골든셋에 그만큼의 사례가 있는가"에 달려 있다. 사례가 모자라면 업무 범위를 좁히거나 게이트 대상 업무를 정답 있는 사례가 충분한 것부터 시작한다. 크기는 6장 게이트 통계의 MDI와 검정력 계산으로 정한다.

**동시 활성 케이스 상한 10.** 평가 용량과 승인 처리량에서 나온 값이다. 상한을 넘으면 우선순위 순으로 제출한다.

- 우선순위 = rate × reach_weekly × signal_weight
- 하루 LLM 사용량 상한 안에서만 제출한다. 상한은 D12에서 정한다. 활성 케이스 10개가 모두 하루에 한 번씩 판정하면 하루 약 13.5만 회(탐침·앵커 포함 최악 약 24만 회) 호출이다. 상한에 걸린 케이스는 QUEUED에서 기다리고 기한 시계가 멈춘다.
- 평가 실행은 업무량이 적은 시간대에 낮은 우선순위로 돈다. 평가 실행 실패율이 10%를 넘으면 판정하지 않고 HELD로 보낸다. 런타임 장애를 자산 결과로 오인하지 않기 위해서다.

### 9.5 Admin UI · SEL API (앱 설계 11장)

Admin UI는 SEL API만 호출한다. 승인·롤백 같은 쓰기는 모두 Idempotency-Key를 요구한다. scope는 FW가 맡은 공통 진입점 권한 체계로 판정한다(D8).

| 메서드 · 경로 | 용도 | scope |
| --- | --- | --- |
| GET `/v1/cases?state=&target=&cursor=` | 케이스 목록 | sel.read |
| GET `/v1/cases/{id}` | 케이스 상세 (finding, 가설, diff 링크, 게이트 요약) | sel.read |

| POST `/v1/cases/{id}:request-changes` | 수정 요청 {instructions} → OPEN (세트 재고정) | asset.approve |

승인 요청은 반복 번호(iteration)와 후보 digest를 반드시 싣는다. 승인자가 화면을 연 뒤 반복이 바뀌었으면 409로 거부한다. 보지 않은 후보를 승인하는 일을 막기 위해서다. 기준 버전이 바뀌었거나 digest가 평가한 것과 다르면 자산 저장소가 활성 전환을 거부하고 케이스는 STALE로 간다.

### 9.6 장애 · 예외 (앱 설계 12장)

원칙은 하나다. **판단할 수 없으면 판단하지 않는다.** 런타임·데이터·judge 문제로 근거가 흔들리면 케이스를 진행시키지 않고 HELD로 세운다.

| 상황 | 감지 | 처리 |
| --- | --- | --- |
| 같은 패턴 finding 중복 | dedupe_key 일치 | 한 케이스로 병합 |
| 대상 자산에 활성 케이스 존재 | 부분 유일 인덱스 충돌 | 새 finding을 기존 케이스 증거로 추가 |
| 잠금 상태에서 기준 버전 변경 | `erp.asset.release.v1` | 승인 전이면 STALE → OPEN(예산 > 0), 새 기준으로 판정 세트부터 다시. RELEASED·VERIFYING·CANARY면 INCONCLUSIVE(base_changed), CANARY는 코호트 해제 후 (9.3) |
| 평가 실행 실패율 10% 초과 | eval_run.failure_rate | HELD(일시적). 같은 세트로 최대 2회 재시도, 실패 원인을 플랫폼 신호로 기록 |
| 골든셋 부족·정답 비율 미달 | 판정 세트 고정 때 사전 검사 | REJECTED(structural), finding suppressed(해제 조건 ②). 골든셋 보충은 SKILL 작성자(D16) |
| 격리 비율 상한 초과 | 에이전트 골든셋 격리 비율 > 5% | 루프 정지 플래그(신규 개설만 막음). 비율이 상한 이하로 돌아오면 자동 해제 |
| 모델·도구 계약 변경 | 사내 LLM 버전, 도구 계약 버전 이벤트 | 루프 정지 플래그(신규 개설 동결). 승인 전 케이스는 QUEUED로 대기(EVALUATING 결과 폐기, AWAITING_APPROVAL은 STALE 후 대기, 9.3). 반영 뒤 상태(CANARY·RELEASED·VERIFYING·REGRESSED)는 계속 진행. A/A 자동 재실행(M2a 규모) → 통과하면 플래그 해제. 실패하면 7일마다 A/A를 다시 돌리고, 통과하는 날 해제한다(사람이 풀 필요 없음, 대신 플랫폼 신호). 기준선은 새 키로 다시 쌓는다 |
| LLM 호출 실패 | 429, 타임아웃(제안 60초), 응답 잘림, JSON 파싱 실패 | 백오프 재시도 2회. 평가 실행·탐침 안이면 실행 실패(플랫폼 원인, 실패율 10%에 포함, 넘으면 HELD). Creator 단계면 HELD(transient, resume = 실패한 상태). 사용량은 LLM 사용량 원장에 기록 |
| judge 보정 무효·노이즈 과다 | judge_calibration.valid = false | judge는 게이트에 쓰지 않으므로 승인 화면의 참고 표시만 끈다 |
| Dry-Run 미지원 쓰기 도구가 평가 경로에 포함 | dry_run_unsupported | 판정 세트 고정 때 확인. 해당 사례 제외, 고정 세트 사례면 REJECTED(structural) |
| 판정 예산 소진 | budget_used = 3 | REJECTED(budget). 반복별 가설·결과 요약을 남긴다 |
| 등급 상한 때문에 의도 채널 릴리스 불가 | 후보 등급이 채널 상한보다 민감 | 코드가 상한 안의 채널로 범위를 줄여 승인 화면에 표시. 승인자는 승인·반려만 한다 |
| 승인 가능자 없음 | 소유 팀 ∩ 후보 등급 열람권 = ∅ | REJECTED(no_approver), 플랫폼 신호 |
| 카나리 관측 부족 | 14일 내 필요 관측 수 미달 | 코호트 할당 해제, ROLLED_BACK(insufficient_obs). 확인되지 않은 변경을 전체로 넓히지 않는다 |
| 카나리 악화 | 카나리 검정 | 자동 롤백 → ROLLED_BACK |
| 전체 릴리스 후 악화 | VERIFYING 순차 검정 | REGRESSED → 자동 롤백(CAS), finding suppressed |
| 반영 후 결론 없음 | 관측 14일 내 필요 관측 수 미달 또는 DiD 비유의 | INCONCLUSIVE로 종료, 버전 유지 |
| 브로커 소비 실패 | 재시도 3회 후 | DLQ. 케이스는 기한 표대로 처리 |
| 자동 롤백 CAS 불성립 | 현재 활성 ≠ 릴리스한 버전 | ROLLBACK_SKIPPED |

**데이터 모델** (앱 설계 8장): SEL 상태는 PostgreSQL `sel` 스키마에만 두고 Database Connector로만 접근한다. trace 원문은 복제하지 않고 trace_id로 참조한다. 모든 행에 등급을 두고 RLS로 등급 상한 밖의 행을 숨긴다. 테이블: finding, improvement_case, case_event(추가 전용), hypothesis, candidate, eval_case, eval_set(실행 전 고정), rubric, judge_calibration, eval_run, eval_result, gate_decision, approval_link, release_link, verification, outbox. v0.8에서 더한 것:

## 10. 마일스톤과 작업 분해

구현은 **Tester·Evaluator를 Creator·Improver보다 먼저** 만든다. 하네스가 회귀를 놓치면 개선 루프가 회귀를 개선으로 채택하기 때문이다. 설계는 네 단계 모두 지금 같이 한다.

- **M0 게이트**: Q7은 공용 자산만으로 정했다(v0.9, 설계자 확인 대기). 남은 것은 Q6(우리 Runtime·게이트 기록을 어디서 읽나), Q5(평가 실행 경로), Q2(평가 샌드박스 구현 상태·담당), 세션 기록 제공 여부(12장)다.
- **M1과 M2a는 병행**한다. M2a 대상 업무는 M0에서 파일럿 팀 인터뷰로 고른다. 기준은 운영에서 알려진 실패가 있는 조회 업무다.
- **M2a**: Tester·Evaluator 워킹 스켈레톤. 조회 업무 1개, 단일 턴 케이스, 규칙 검사(judge는 참고용). 게이트는 변형 검출, A/A 오판, 노이즈 측정이다.
- **M2c(Creator·Improver v0)는 M2b와 병행**한다. 선행 조건은 M2a 게이트와 M1의 finding이다. 대상은 단일 턴에서 판정할 수 있는 실패로 한정한다(예: 기간 누락, row limit 초과). 되묻기처럼 대화가 필요한 수정은 user simulator(M2b) 뒤로 미룬다. M2a 케이스 수로는 held-out 판정의 통계력이 없으므로 대상 업무 평가셋 확장을 포함한다.
- **결함 주입 시험** (A/A 선행 조건의 예외. 정답을 아는 시험 환경의 배관 검증이다): 운영 트래픽 없이 루프 한 바퀴를 우리 런타임 안에서 완주하는 것이 Creator·Improver의 첫 완료 기준이다. 정상 자산에서 핵심 지시 한 줄(예: 기간 형식 YYYY-MM)을 뺀 열화 버전을 시험 환경에 릴리스하고, 정기 골든셋이 실패를 만들고, 폴백 분석기가 finding을 발행하고, 개선안 → 게이트 → 승인 → 릴리스를 거쳐 다음 정기 실행에서 패턴이 사라지는지 본다. 정답(뺀 줄)을 알고 있으므로 원인을 제대로 짚었는지도 검증된다. Q6·Q7과 무관하게 할 수 있다. 저장소의 `sel-lab/`이 이 시험의 로컬 판이다.
- **달력 (v0.11: 기준 문서 13장 Phase 기준)**. 아래 M 단계는 이 Phase에 맞춰 읽는다.

**확인 필요**

- **세션 기록 제공**: 프론티어 도구(OpenAI Dots)가 세션 데이터를 어떤 형태·범위로 넘겨주는가. 없으면 R5와 "반복 절차" 경로가 사라진다
- **Agent 자산을 프론티어 도구가 읽는가**: Agent 허용 필드(`max_turns` 등)를 Dots가 쓰지 않으면 composition 개선은 대리 에이전트에만 효과가 있어 v0 대상에서 뺀다

- **Q8 등급 방향**: 앱 설계의 등급 표기(max, "등급 2 이상")가 "숫자가 클수록 민감"으로 읽힌다. 이 문서의 전제(1이 가장 민감)와 맞춰야 보안 경계의 등급 상속·누출 검사를 확정할 수 있다
- 기밀 구간 에이전트의 실행 위치: 로컬이면 relay 충실도, 중앙이면 full (앱 설계 미결 1)
- judge용 내부 모델의 가용성과 버전 고정 방법 (앱 설계 미결 3)

- 평가 샌드박스는 설계 방향 문서에 설계로 있다. 남은 것은 구현 상태, 담당, `standard-v1` 루틴, 체크포인터 분리다 (02 문서 Q2)
