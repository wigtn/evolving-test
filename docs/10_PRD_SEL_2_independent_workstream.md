## 1. 목적

② 자산 생성의 핵심 규칙(무엇을 왜 바꿔도 되는지, 무엇으로 시험하는지)을 **문서가 아니라 돌아가는 코드와 테스트로** 먼저 만든다. 그래서 12월 원칙 초안이 "검증된 규칙"이 되게 하고, P3(2027.2~)에 실제 Runtime · Registry가 오면 연결만 하면 되게 한다.

"검증된"의 뜻: 규칙을 만든 사람이 만든 시험만 통과하는 것이 아니라, **규칙을 보지 않은 사람이 만든 시험(held-out)과 자동 변형(퍼징)에서 측정한 차단율**을 보고한다(W3).

## 3. 설계 원칙

**1. 미정인 것은 인터페이스나 설정으로 빼 둔다.** 결정이 나면 구현체 · 설정만 바꾼다.

| 미정 | 빼 두는 방법 | 결정 주체 |
| --- | --- | --- |
| 시험 입력을 어디서 받나 | `TestInputSource` 인터페이스. 지금 구현은 sel-lab 하나 | PM |
| 자산 저장 · 등록 | `AssetStore` 인터페이스. 지금은 파일 기반 가짜 Registry | Registry |
| 원장 저장 | `LedgerStore` 인터페이스. 지금은 SQLite | (P3에 PostgreSQL · DBC) |
| 등급 방향 (Q8) | 정책 파일 `grade.more_sensitive: lower`(1이 가장 민감, 기본) | 보안 담당 |
| 결과 코드 이름 | 결과 코드 매핑 표 한 장 | Protocol common |
| 허용 필드(증거 구획) | 설정 파일. 지금은 sel-lab 필드 | ① · Protocol |
| finding당 후보 수 상한 | 정책 파일 `limits.candidates_per_finding: 3` | PM (docs/09 4.7-7) |
| SEL이 바꿀 수 있는 매니페스트 params | 정책 파일 `assets.agent.editable` 목록. **기본은 비어 있음** | PM (docs/09 4.7-5) |
| skill · prompt 자산 형식 | W0 최소 변환 + `registry.py` 어댑터 | Protocol P2 Asset (11월 중순) |

**2. 결정적이어야 한다.** W1~W5 · W9 · W10은 같은 입력에 같은 출력. W7의 LLM은 사내 엔드포인트의 고정 버전, temperature 0, 출력 스키마 검증. temperature 0도 결정성을 보장하지 않으므로 반복 측정의 분산을 보고한다.

**3. 실패하면 막는다(fail-closed).** 검사기 오류, 스키마 위반, 등급 불명, 모르는 정책 키 · 버전은 모두 "후보를 만들지 않음"이다.

**4. 합성 값만.** 모든 자산 · 입력은 합성 값이다. 합성 값 규약: 이름은 `가상` 접두(예: `가상거래처-0418`), 번호는 예약 범위(거래처 `9xxxxxxx`). 사내 LLM 엔드포인트만 쓰고, 외부 LLM API는 쓰지 않는다.

**5. 정답지는 루프가 읽지 않는다.** `data/defects/catalog.yaml`과 `data/ground_truth/`는 채점에만 쓴다(테스트로 강제, W6-6).

## 4. 요구사항

### W0. 자산 형식 최소 이관 + 결함 카탈로그 정답 열

지금 sel-lab 자산은 자체 형식(`asset_ref: skill/fi-open-items@1.4.2`, `allowed_tools`)이다. 기준 문서에는 agent(6장)와 tool(9장) 예시만 있고 skill · prompt 형식은 Protocol P2 Asset(11월 중순)에서 정해진다. 그래서 **최소 변환**만 한다.

| ID | 요구사항 | 수용 기준 |
| --- | --- | --- |
| W0-1 | **tool · agent**: 기준 문서 형식으로 변환(`asset://kind/ns/name@ver`, `kind` · `metadata{ref, grade}` · `spec`). tool은 `spec.name` · `description` · `input_schema` · `side_effect` · `required_capability` · `dry_run` · `idempotency` · `timeout_s` · `binding` | 스키마 검증 통과 |
| W0-2 | **skill · prompt**: Markdown + front matter를 유지하고 `kind` · `metadata{ref, grade}`만 덧붙임. 스킬별 `allowed_tools`는 front matter에 그대로 둠(스킬별 도구 범위가 W2-5 (g) 검사에 필요). P2 Asset 형식이 나오면 변환기만 고침 | — |
| W0-3 | `registry.py`에 **어댑터**: 새 형식을 읽어 기존 인메모리 뷰로 넘김. 기존 코드(`registry.py` · `worker.py` · `sel.py`)는 어댑터를 통해서만 읽음 | 기존 코드가 옛 필드를 직접 읽는 곳 0 |
| W0-4 | 결함 변형(variants)도 같은 방식, 변환은 `gen/build.py` 스크립트로 | 재생성 가능 |
| W0-5 | **실행 결과 스냅샷 일치**: 변환 전후 오프라인 demo D01~D10과 C00(정상) 결과가 같음 | 스냅샷 테스트 통과 |
| W0-6 | **결함 카탈로그에 docs/07 기준 정답 열 추가**: `cause_class`, `change_kind`, `target_address`(W1 주소), `expected_c6_code`, `flags`. 기존 앱 설계 열(`hypothesis_class`, `change_type`, `route`)은 대응표와 함께 보존 | 10종 모두 채움 (C6 열거값 안에서) |
| W0-7 | **정책과 맞지 않는 정답 정리**: D06 정답은 "description만 보강"(pattern 복원은 사람 작업). D05(`max_turns`)는 허용 params가 비어 있으므로 기대 결과 `governance_rejected`. D07은 `handoff_dev`(플랫폼 원인, 기존 `route: developer` 대응), D08은 `proceed` + `flags: [eval_case_suspect]`(표시만 하고 진행. 격리는 결정적 규칙), D09는 `out_of_scope`(new_asset, v0 루프 밖) | 카탈로그에 기록 |

### W9. 시험 문제 선정 이식

docs/07 C(Creator 4~5단계)를 lab에서 구현한다. lab에는 이미 `build_eval_set` · `split_golden` · `expose` · `exposed`가 있다. **재사용하되 다음 차이를 고친다**.

| ID | 요구사항 | 기존 lab과의 차이 | 수용 기준 |
