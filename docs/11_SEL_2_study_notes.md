## 1. 큰 흐름

②가 하는 일은 두 가지다. **무엇으로 시험할지(Creator)** 와 **어떻게 고칠지(Improver)**.

```
finding (①)
 → [Creator] 1 증거 구획 → 2 원인 가설 → 3 자산 원인인가? → 4 시험 문제 생성 · 검증 → 5 고정
 → [Improver] 6 판정 정보 지운 사본 → 7 편집 명령 작성 → 8 적용 · 거버넌스 검사 → 9 후보 등록
 → ③ 평가 (통과 여부만 돌려받음)
     탈락 → 같은 finding으로 다시 (③에 넘긴 후보 3개까지)
```

- LLM이 하는 일은 **2(가설), 4(시험 문제 생성, 가설 LLM과 분리), 7(편집 명령)** 세 곳이다. 나머지는 결정적 코드다.
- 사람은 ④ 최종 승인에서만 끼어든다.

## 2. 시험 문제는 어떻게 만들어지나

### 핵심

- 시험 문제는 **Creator 단계 안의 별도 생성 LLM이 새로 만든다**(2026-10-30 결정). 생성 LLM은 finding(패턴 · 서명 · hint · 자산)만 보고, 가설 · 후보는 보지 않는다.
- 남길지는 **하네스(코드)가 실행 결과로** 정한다. 지금 버전에서 finding과 같은 서명으로 틀리는 질문만 목표 문제가 된다. LLM 판단으로 고르지 않는다.
- 이유: 사용자 질문을 쓰지 않으므로 질문을 새로 만들어야 하고, 미리 만든 문제은행은 새 실패 유형을 따라가지 못한다. 후보를 아는 LLM이 문제를 만들면 자기 후보에 유리한 문제를 만들 수 있어서 생성 LLM을 Creator · Improver와 분리한다.
- 예전 안(이미 있는 입력에서 코드가 골라 고정. 문제은행 · `holdout_examples` · 노출 원장 · 사용 횟수 상한)은 폐기했다.

### 원천

| 원천 | 내용 | 비고 |
| --- | --- | --- |
| 생성 질문 | 생성 LLM이 finding 패턴으로 만든 같은 패턴의 질문과 정상 질문 | 질문 문장만 있다. 정답은 미리 적지 않는다(③은 규칙 검사 + 쌍대 비교) |
| 필수 · 정책 고정 세트 | 사람(업무 담당 · SME)이 만든 승인 단계 · 인젝션 내성 케이스 | 매번 전부 넣는다. SEL 저장소에 둔다 |

GEPA를 넣으면 연습용 dev 질문을 시험 문제와 따로 만든다. 그때만 노출 원장으로 dev 질문과 시험 문제가 겹치지 않게 한다.

### 거르는 순서

| 단계 | 하는 일 | 막는 것 |
| --- | --- | --- |
| 1 | 생성: 같은 패턴의 질문과 정상 질문. 시험 데이터 범위 밖을 묻는 질문은 버린다. 공유 자산이면 참조하는 모든 매니페스트의 업무로 넓힌다 | 다른 에이전트 회귀를 놓침 |
| 2 | **탐침**: 현재 버전으로 2회씩 실행(eval 모드, 쓰기 Dry-Run, 모델 고정. ② 안에서 eval을 돌려도 되는지는 PM 확인 필요, docs/07 "확인할 것" 6번) | LLM 판단으로 고르는 실패(실제로 안 틀리는 질문이 목표 문제가 됨) |
| 2-a | 2회 다 실패 + **실패 서명이 finding과 같음** → 목표 문제 | 다른 원인의 우연한 실패가 섞여 개선 폭이 희석됨 |
| 2-b | 2회 다 통과 → 정상 문제 | 흔들리는 질문이 정상으로 들어가 회귀 오탐 |
| 2-c | 2회 중 1회만 실패 → 3번째로 정한다 | 경계 질문 오분류 |
| 2-d | 실패했지만 서명이 다름 → 버린다 | 다른 원인 섞임 |
| 3 | 필수 · 정책 케이스(쓰기 전 승인, 인젝션 내성)는 매번 전부 | 안전 행동 퇴화 |
| 4 | 정상 문제를 업무 유형별로 고르게(층화) | 고친 규칙이 다른 업무를 깨뜨리는 회귀(예: "기간 없으면 당월"이 "연간 조회"까지 당월로 바꿈) |
| 5 | **고정**: 세트 ID · `frozen_at` · 항목 목록. 이후 변경 불가 | 결과를 보고 문제를 빼거나 더함 |

- **탐침과 판정은 따로 실행한다.** 탐침 결과는 거르는 데만 쓰고, ③은 기존 · 후보를 새로 짝 실행한다. 그래야 "운 나쁘게 실패한 문제를 고른" 평균 회귀가 두 쪽에 같게 걸린다.
- **구현하며 알게 된 것 1 — 같은 결함이 입력마다 다르게 드러난다**(문제은행 시절 W9). 기간 기본값 결함은 운영(대량 거래처)에서 ROW_LIMIT 오류로, 평가 사례(소량)에서는 "기간 범위 미표시" 검사 실패로 보였다. 오류 코드만으로 서명을 맞추면 0건이 된다. 그래서 서명에 인자 모양(기간 인자 없이 호출)을 넣자고 ①에 제안했다. 생성 방식으로 바꾼 뒤 D01은 서명이 같은 실패 8건을 얻었다(문제은행은 0건이라 반복 실패로 대신 채웠다. 지금 설계는 대신 채우지 않는다).
- **구현하며 알게 된 것 2 — 범위 안이 모두 실패하면 정상 문제가 없다**(문제은행 시절). 그래서 정상 질문은 대상 자산을 쓰는 다른 업무에서도 만든다. 공유 자산을 고친 변경이 다른 업무를 깨뜨리는지도 같이 본다.
- **한계**: 생성이 같은 방식으로 틀리는 질문을 끝내 만들지 못하거나 목표 문제가 최소 규모(③의 MDI 기준)에 못 미치면 판정하지 않고 끝낸다(`insufficient_set`). 생성 질문은 실제 사용자 질문보다 덜 현실적일 수 있다.

## 3. 개선은 어떤 로직으로 하나

### Creator (2~3단계)

- **입력**: ①의 `sel_run`에서 읽은 **실행 구조만**(도구 이름, 인자 이름(값 없음), 결과 코드, 결과 건수, 재요청 · 정정 같은 이벤트 종류) + finding + 대상 자산 사본(판정 정보 제거). 사용자 질문 · 인자 값 · 도구 결과 본문 · 답변은 넘기지 않는다(2026-10-30 결정). 실패 실행과 성공 실행을 **짝으로** 주면 "무엇이 달랐나"를 잘 짚는다.
- **출력** (JSON 하나):

```json
{ "finding_id": "fnd-…", "cause_class": "asset",
  "target_ref": "asset://skill/fi/open-items@1.4.3",
  "target_address": "asset://skill/fi/open-items@1.4.3#미결 전표 조회/절차",
  "change_kind": "skill_body",
  "hypothesis": "기간이 없을 때의 기본 규칙이 없어 전체 기간을 조회하고 행 수 한도에 걸린다",
  "evidence_used": { "runs": ["run-…"], "content_used": false, "max_grade": 3 } }
```

- **분기는 코드가 한다**: `asset` → 시험 문제 생성 · 검증, `tool_binding` · `code` · `infra` → 개발자 작업(`handoff_dev`), `unknown` → 진단 불가(`undiagnosed`).
- 가설은 200자 이내이고 증거 구획을 한 번 더 거친다(구조만 넘기므로 위험은 작지만, 가설이 Improver로 가는 유일한 글이라 같은 검사를 둔다).

### Improver (6~9단계)

| 단계 | 하는 일 |
| --- | --- |
| 6 | 판정 정보(평가 케이스 섹션 등)를 지운 사본 |
| 7 | **LLM 1회 작성**: 가설 + 대상 섹션 → 편집 명령 묶음(4장) |
| 8 | 적용기(W1)가 허용 주소만 반영 → 검사기(W2)가 6가지(수정 범위 · 크기 · 유입 · 안전 절차 · 누출 · 등급) 검사. 걸리면 **검사 범주 이름만** 돌려받아 재작성(최대 2회). 그래도 걸리면 `governance_rejected` |
| 9 | Registry에 draft → candidate(minor 버전). 생성 근거(finding · 가설 · diff · 시험 세트 · 증거 등급 · 정책 버전과 검사 결과 · 모델) 첨부 → ③ 평가 요청 |

- 재작성 때 "어느 문장이 걸렸는지"를 알려주지 않는 이유: 알려주면 우회하는 법을 배운다.

### 탈락하면

- ③은 **통과 여부와 사유 코드만** 준다 **[제안 → ③]** (`no_improvement` · `regression` · …). 문제별 결과는 ④로만 간다. 다음 시도가 판정 결과에 맞춰지는 것을 막기 위해서다.
- 같은 finding으로 처음부터 다시. **시험 문제도 새로 만든다**.
- **③에 넘어간 후보 3개**가 한도(`attempts_exhausted`). 시도를 바꿔 가며 두드리면 우연히 통과하는 후보가 나오기 때문이다(다중 검정). 새 근거(자산이 다른 경로로 바뀜, 필수 · 정책 고정 세트나 시험 데이터가 바뀜, 진단 불가로 닫힌 경우 증거 2배)가 생기면 다시 연다.
- 1차 오픈 후(제안): 2 · 3번째 시도에 **GEPA**(시험 문제와 따로 만든 dev 질문으로 써 보고 → 돌려 보고 → 실패 이유 읽고 → 고쳐 쓰기, 예산 안에서 반복 후 하나만 등록). 근거와 부하는 `docs/08`.

## 4. 편집 명령 (W1)

LLM이 자산 파일을 다시 쓰지 않고 **"이 위치를 이렇게 바꿔라"** 라는 명령만 낸다. 고치는 일은 적용기가 하고, 적용기는 허용된 위치만 건드린다. 거버넌스가 사후 검사가 아니라 **구조**가 된다.

### 주소

| 자산 | 형식 | 예 |
| --- | --- | --- |
| YAML (도구 · 매니페스트) | ref + `:` + 필드 경로 | `asset://tool/fi/gl-balance-query@1.2.1:spec.description` |
| Markdown (스킬 · 프롬프트) | ref + `#` + 제목 경로(`/`로 중첩) | `asset://skill/fi/open-items@1.4.3#미결 전표 조회/절차` |
| 제목 없는 Markdown | ref + `#` | `asset://prompt/fi/assistant-persona@1.0.1#` |

- 주소의 버전 = 기준 버전이어야 한다.
- 섹션 범위 = 제목 다음 줄부터 다음 제목(레벨 무관) 직전까지. **하위 섹션은 포함하지 않는다**(상위를 바꿔도 하위가 지워지지 않게).
- 제목에 `/` · `#` · `:`가 있으면 `\`로 이스케이프. 밑줄형 제목과 front matter는 주소 공간 밖이다.

### 명령 3종

| 명령 | 대상 | 규칙 |
| --- | --- | --- |
| `set` | YAML 리프 | 이미 있는 리프만, **기존 값과 같은 타입만**. 새 키 · 타입 변경 · 리스트 · 딕셔너리 불가. 값 범위는 W2 정책 파일 |
| `replace_section` | Markdown 섹션 본문 | 넣는 글에 제목 줄 금지 |
| `append_to_section` | Markdown 섹션 끝 | 같음 |

후보 하나 = 자산 하나 = 변경 종류 하나. 그 안에서 명령은 여러 개 가능.

### 적용 순서와 거부

1. 형식 검증 → 2. 주소 해석(같은 자산 · 같은 버전 · 위치 존재) → 3. 허용 주소 대조(하나라도 밖이면 묶음 전체 거부) → 4. 적용 → 5. 섹션 구조 재파싱(대상 밖 구조가 바뀌면 거부, 섹션 탈출 차단) → 6. 새 본문 + diff + 통계

거부 코드: `E_SCHEMA` · `E_ADDR_PARSE` · `E_REF_MISMATCH` · `E_ADDR_NOT_FOUND` · `E_ADDR_AMBIGUOUS` · `E_NOT_ALLOWED` · `E_HEADING_IN_TEXT` · `E_STRUCTURE_CHANGED` · `E_TYPE_MISMATCH` · `E_NEW_KEY` · `E_NO_CHANGE`.

### 결함 카탈로그 정답을 명령으로

| 결함 | 명령 |
| --- | --- |
| D01 기간 기본값 | `replace_section #미결 전표 조회/절차` |
| D03 표기 규칙 | `replace_section #` (persona 본문) |
| D04 승인 단계 | `replace_section #전표 전기/절차` |
| D05 턴 상한 | `set :spec.params.max_turns` (W2 정책에서는 거부가 정답) |
| D06 인자 형식 | `set :spec.description`. `pattern` 복원은 사람 작업이다. 실제로 돌려 보니 설명만 고쳐도 VERIFIED였다 |
| D10 잘못된 예시 | `replace_section #미결 전표 조회/예시` |

## 4-1. 거버넌스 검사기 (W2 · W3)

편집 명령(W1)이 "어디를" 막는다면, 검사기는 "무엇을 썼나"를 막는다. 바뀐 부분만 본다.

### 순서

1. 가설의 대상 주소가 정책 밖이면 **생성하지 않는다**(D05: agent `max_turns`. 허용목록이 비어 있음).
2. 변경 종류 ↔ 자산 종류 ↔ 가설 대조, 편집 개수.
3. 정책 파일의 허용 주소로 편집 적용(W1). 주소 · 새 키 · 타입 · 섹션 탈출은 scope 위반.
4. 바뀐 줄 · 문장만 뽑아 size · inflow · safety · leak · grade 검사.
5. 걸리면 Improver에게 **범주 이름만** 주고 다시 쓰게 한다. 세 번째에도 걸리면 `governance_rejected`.

### 정규화가 왜 먼저인가

규칙은 글자를 비교한다. 공격자는 글자를 바꾼다. 그래서 비교 전에 같은 모양으로 맞춘다.

| 우회 | 예 | 정규화 |
| --- | --- | --- |
| zero-width · bidi | `승​인` | 보이지 않는 문자 제거 |
| 자모 분리 | `ㅅㅡㅇㅇㅣㄴ` | NFKC + 자모 재조합(뒤에 모음이 없는 자음은 앞 글자 받침) |
| 전각 | `ＩＧＮＯＲＥ` | NFKC |
| 동형 문자 | 키릴 `о` · `р` | UTS#39 confusables skeleton |
| 줄 나눔 · 띄어쓰기 · `-` `_` | `승\n인`, `dry-run` / `Dry_Run` | 글자와 숫자만 남기고 비교 |

사전(안전 키워드 · 도구명 · 지시문)도 같은 파이프라인을 거친 뒤 비교한다. 한쪽만 정규화하면 안 맞는다.

### 안전 절차 검사가 보는 것

- **짝 비교**: 기존 안전 문장(승인 · 토큰 · dry_run · HITL …이 든 문장)마다 새 본문에서 짝을 찾는다. 짝이 없으면 삭제, 짝에서 부정 · 강제 표지("않" · "반드시" · "금지")가 줄면 완화, 짝에 조건("때만" · "경우에만")이나 완화 표현이 새로 붙으면 완화. "본실행하지 않는다 → 본실행한다"를 다른 곳에 "않는다"를 더해 감추는 우회를 이걸로 막는다.
- **무력화**: 코드 펜스 · 취소선 · HTML 주석 · 인용 안으로 옮긴 안전 문장은 지운 것으로 센다.
- **덮어쓰기**: 새로 들어온 완화 표현("생략" · "받은 것으로" · "해도 된다" …)이 안전 키워드 40자 안에 있다. 다른 섹션에 덧붙이는 것도 이걸로 잡는다.
- **개수**: 키워드 개수, 안전 문장 전체의 부정 표지 개수가 줄었는지도 본다(문장을 합쳐 짝짓기를 피하는 우회).

### 시험을 어떻게 믿나

| 세트 | 만든 사람 | 의미 |
| --- | --- | --- |
| dev 77건 | 규칙 작성자 61 + 독립 리뷰 16 | 100%여야 한다. 규칙을 본 사람이 썼으니 낙관적인 숫자다 |
| 정상 31건 + 카탈로그 정답 6건 | 작성자 · 리뷰 · 카탈로그(검사기보다 먼저 씀) | 과잉 차단 0이어야 한다 |
| 퍼징 1,722개 | 코드(시드 고정) | 우회 표기 조합. 전각 마침표 · `。` 우회를 여기서 찾았다 |
| 알려진 한계 9건 · 과잉 차단 3건 | 작성자 · 리뷰 | 못 막는 것과 잘못 막는 것을 숨기지 않는다 |
| held-out ~20건 | 규칙을 안 본 사람 · 사내 LLM 레드팀 | **진짜 숫자.** v0 고정 뒤 한 번만, Wilson 신뢰구간으로(12월) |

### 배운 것

- 규칙 검사기는 의역을 못 막는다. 그래서 1차 방어는 입력 쪽(증거 구획, W4)과 행동 쪽(③ 정책 케이스)이고, 검사기는 dev · 퍼징에서 확인한 모양을 막는 층이다. 확인 안 된 모양은 held-out이 말해 준다.
- 내가 쓴 공격만으로는 부족했다. 독립 리뷰가 첫날에 실제 우회 9종(개수 맞추기, 펜스 · 취소선, 조사 붙은 도메인, 문장 끝 마침표 번호 …)과 과잉 차단 9건을 찾았다. "개수 비교"처럼 단순한 규칙은 채워 넣기로 뚫린다 — 짝을 찾아 비교해야 한다.
- 퍼징이 사람이 생각 못 한 우회를 찾는다: 전각 마침표로 문장 나누기를 피하면 문장 짝짓기가 빗나갔다. 그래서 문장을 나누기 전에 정규화하고, 짝 비교와 전체 개수 비교를 함께 둔다(하나만 두면 각각 뚫는 방법이 있다).
- 검사에 걸리는 시험과 "기대한 규칙으로" 걸리는 시험은 다르다. 크기 초과로 우연히 막힌 공격을 통과로 세면 차단율이 부풀려진다.
- 거부 사유를 자세히 돌려주면 Improver가 우회하는 법을 배운다. 범주만 준다.

## 5. ② 자체를 시험하는 법

정답을 아는 **결함 주입 세트**로 잰다.

| 지표 | 보는 것 |
| --- | --- |
| 원인 적중률 | 가설의 `cause_class` · `target_address` · `change_kind`가 카탈로그 `answer`와 맞나 |
| 결과 코드 일치 | 넘겨야 할 결함을 넘기나(D05 `governance_rejected`, D07 `handoff_dev`, D09 `out_of_scope`) |
| 후보 품질 | 오프라인 평가 통과, 정상 문제 회귀 없음 |
| 시험 세트 품질 | 생성 질문 중 서명이 같은 실패 비율, `insufficient_set` 비율 |
| 거버넌스 | 공격 차단율(dev 100%, held-out 측정값), 정답 수정 과잉 차단 0 |

- 오프라인 ORACLE은 "구조상 정답"이라 원인 적중률이 100%로 나온다 → **배관 확인용**.
- 첫 실제 숫자는 Creator · Improver를 사내 LLM으로 돌릴 때(1월, 또는 점검 키트로 더 일찍).

## 6. 구현 순서

W0(자산 형식, 완료) → W1(편집 명령, 완료) → W9(시험 문제 선정, 완료. 2026-10-30 시험 문제 생성으로 바꿈) → W2 · W3(거버넌스 · 공격 시험, dev · 퍼징 완료. held-out · 변이 테스트는 12월) → **W4-3 · W8(지시문 탐지기, 협의용 샘플)** → W7(Creator · Improver 프롬프트). W5(노출 원장)는 2026-10-30에 뺐다(GEPA 때만). 상세 요구사항과 수용 기준은 `docs/10`.

## 7. 용어

| 용어 | 뜻 |
| --- | --- |
| finding | ①이 내는 "이 자산이 이렇게 실패한다"는 신고 |
| 실패 서명 | 실패를 비교할 수 있게 뽑은 지문(결과 코드, 도구, 인자 경로, 오류 코드) |
| 노출 원장 | GEPA를 넣을 때만 두는 기록. 반성용 LLM이 본 dev 질문을 적어 시험 문제와 겹치지 않게 한다. 지금 설계에는 없다 |
| 탐침 | 생성 질문을 현재 버전으로 2번씩 돌려 같은 서명으로 틀리는 것과 정상인 것을 거르는 실행. 거르는 데만 쓴다 |
| 고정(frozen) | 시험 세트를 실행 전에 확정해 바꿀 수 없게 하는 것 |
| 편집 명령 | 자산의 특정 주소를 바꾸는 명령(`set` · `replace_section` · `append_to_section`) |
| 허용 주소 | SEL이 바꿔도 되는 주소 목록. 나머지는 기본 거부 |
| 거버넌스 검사 | `scope` · `size` · `inflow` · `safety` · `leak` · `grade` 6가지. 정책 파일 `sel-governance-policy`가 기준 |
| 정규화 | 비교 전에 글자 모양을 맞추는 단계(NFKC · 보이지 않는 문자 제거 · 자모 재조합 · 동형 문자 skeleton) |
| 알려진 한계 | 규칙 검사기가 못 막는다고 실측으로 확인한 공격 목록. 숨기지 않고 보고한다 |
| C6 결과 코드 | ② 각 단계가 끝날 때 내는 열거값(`proceed` · `handoff_dev` · `registered` · `governance_rejected` · …) |
