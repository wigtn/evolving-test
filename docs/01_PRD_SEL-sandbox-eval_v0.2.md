# PRD · SEL 샌드박스 평가·개선 플랫폼 (Phoenix 분석 → 합성 데이터 → 테스트·평가 → 개선)

Oct 27, 2026 · @WIGTN · 상태: 논의용 초안 v0.2 (개선 루프 범위 편입)

## 1. 개요

Phoenix에 쌓인 Business·Personal 에이전트 trace를 분석해 실데이터 없는 합성 업무 환경과 테스트 시나리오를 만들고, 그 위에서 에이전트 버전을 테스트·평가하는 샌드박스를 만든다. 평가 결과로 skill·prompt 개선안을 만들고 검증하는 개선 루프(Creator·Improver)까지 이 문서에서 설계한다. 샌드박스는 비즈니스 영역이 직접 열어 쓰는 것을 목표로 한다.

**배경**

- 트레이싱(계측, Collector, Phoenix 운영)은 다른 팀이 맡는다. 우리는 Phoenix에 들어온 데이터를 트레이싱 스케줄러로 가져와 쓴다.
- 팀 설계자의 지시는 세 가지다. Phoenix 데이터를 가져와 분석한다. 그걸 기반으로 데이터를 새로 생성한다. 그걸 테스트하고 평가한다. 테스트와 평가는 샌드박스로 열려 비즈니스 영역에서 활용할 수 있어야 한다.
- 대상 에이전트는 Business와 Personal 둘 다다. 샌드박스에서는 실데이터를 쓸 수 없을 것으로 보고 설계한다.

**지시 해석: "새로 생성하는 데이터"는 합성 환경과 개선안 둘 다다** (D1에서 확인)

- trace 수집은 이미 스케줄러가 맡는다. 따라서 새 데이터는 수집이 아니라 trace를 재료로 만드는 것이다.
- 샌드박스에 실데이터가 없으면 에이전트가 조회할 SAP 데이터도, 검색할 문서도 없다. 분석과 평가 사이의 "생성"은 이 빈자리를 채우는 단계다.
- 생성 대상은 두 가지다. 하나는 **합성 업무 환경**(가짜 SAP 데이터, 가짜 문서, Personal용 가짜 사용자 자료)이고, 다른 하나는 그 위에서 돌릴 **시나리오와 정답**이다.
- 개선안(skill·prompt 패치, 새 skill)도 생성 대상이다. v3 SEL의 Creator·Improver 자리이며, 7장에서 설계한다.
- 둘은 한 루프다. 합성 환경과 시나리오가 있어야 개선안을 판정할 수 있다. 그래서 구현 순서는 하네스(M2a)가 먼저이고, 개선 루프 v0(M2c)이 그 위에 바로 붙는다.

**목표**

1. G1 · 분석: Phoenix trace를 run 단위 레코드로 만들고, 실패 유형·skill별 성공률·도구 오류를 볼 수 있다.
2. G2 · 합성 환경: 실데이터 없이, 운영과 같은 도구 이름·응답 스키마로 동작하는 업무 환경을 만든다. 에이전트 코드는 바꾸지 않는다.
3. G3 · 재현 가능한 평가: 정답을 합성 환경에서 계산해 규칙으로 채점하는 비중을 최대화한다. 반복 실행으로 점수의 노이즈를 측정한다.
4. G4 · 셀프서비스: 비즈니스 영역 담당자가 자기 에이전트 버전을 올려 평가를 돌리고 결과를 해석할 수 있다.
5. G5 · 개선 루프: 운영 실패 클러스터에서 개선안을 만들고, 회귀 없이 개선됐다고 판정된 후보만 사람 승인을 거쳐 자산 레지스트리에 등록한다.

**비목표**

- 트레이싱 계측, Collector, Phoenix 운영 (타 팀). 우리는 필요한 필드를 요구사항으로 전달한다.
- 샌드박스에서 실데이터 사용
- fine-tuning용 학습 데이터 생성
- 운영 배포 자동화 (승인된 개선안은 자산 레지스트리 등록까지만)
- 도구 구현·권한·런타임 코드의 자동 수정

**성공 판정 (제안값)**

- M2a 종료: 일부러 망가뜨린 변형(심각도별 3종 이상)을 모두 회귀로 잡고, 같은 버전끼리 비교(A/A)했을 때 회귀 오판이 상한 이하이며, 반복 실행 노이즈 폭이 측정되어 있다.
- M2b 종료: 과거에 롤백·사고가 있었던 버전과 정상 버전을 백테스트로 구분한다.
- M2c 종료: 실패 클러스터 1개 이상에서 Improver 후보가 7장 채택 조건(개선 케이스 있음, 회귀 0, 정책 통과, 예산 이내)과 사람 승인을 통과한다. held-out 규모가 검정력 기준에 못 미치면 "루프가 끝까지 돈다(dry-run)"를 종료 기준으로 쓰고, 채택 판정은 suite 확장 뒤로 미룬다.
- M4 종료: 파일럿 팀이 우리 도움 없이 평가를 돌리고 결과를 참고 지표로 쓴다. 배포 게이트로 쓸지는 D6에서 정한다.

## 2. 입력 데이터의 제약

Phoenix는 사람이 보는 사본이라 내용이 빠져 있다. 그래서 운영 run을 그대로 재실행하는 방식은 쓸 수 없고, **구조를 본떠 합성 환경을 만드는 방식**을 택한다. 아래 제약은 트레이싱 팀 설계(보안 2등급 이상은 사본에 내용 없음) 기준이며, 최종 규칙은 그 팀 문서를 따른다.

| 제약 | 우리에게 주는 영향 | 대응 |
| --- | --- | --- |
| 1·2등급과 등급 미표시 run은 내용 없이 구조만 있음 | 원인 분석과 케이스 복사 불가 | 구조(도구 op 순서, 결과 스키마, 오류 코드)만으로 시나리오 템플릿을 만든다. 1·2등급·미표시 run의 구조를 샌드박스로 가져올지는 D4에서 정한다 |
| 3등급 run은 마스킹본 (`[EMP]`, `[PHONE]` 등) | 재실행하면 도구 조회가 실패해 에이전트 결함과 데이터 결함이 섞임 | 운영 입력을 재사용하지 않고 합성 환경에서 새 입력을 만든다 |
| 도구 출력은 본문 대신 요약(`erp.tool.output.summary`: 행 수, 커럼명, 오류 코드)만 남음 | 결과 값은 모름 | 합성 데이터의 스키마와 분포를 맞추는 재료로 쓴다 |
| 라벨(validator, HITL, 피드백, 다음 턴 재요청)은 실행 원장에 있음 | 실패 run 선별에 원장 접근이 필요 | 원장 읽기 권한 요청 (D5). 없으면 result\_class와 Phoenix annotation만 쓴다 |
| 샌드박스에서 실데이터 불가 (추정) | SAP·문서·개인 자료 없이 실행해야 함 | 합성 환경 + SAP 자격증명이 없는 별도 배포 샌드박스 Gateway (6장) |
| 샌드박스 run도 Phoenix에 들어감 (`erp.run.source=eval`) | 분석 때 운영 run과 섞일 수 있음 | 수집기가 source로 분리. 평가 trace도 등급 규칙에 따라 내용이 지워질 수 있으므로 채점은 Phoenix에 의존하지 않는다 (6장 C4) |
| Personal은 개인정보 비중이 큼 | 실데이터에 가까운 자료는 더 어렵다 | 가짜 사용자(페르소나) 작업 공간을 만든다 (5장) |

합성 환경 방식의 대가는 운영과 샌드박스의 차이다. 합성 SAP가 실제와 다르게 동작하면 샌드박스 통과가 운영 성공을 뜻하지 않는다. 이 차이는 8장의 현실성 지표로 계속 잰다.

## 3. 전체 구조

Phoenix에서는 구조와 분포만 가져오고, 평가는 우리가 만든 합성 세계 위에서 돌린다. 샌드박스 run의 trace는 다시 Phoenix(erp-eval)로 들어가 디버깅과 현실성 비교에 쓰인다.

![SEL 샌드박스 평가·개선 플랫폼 구조 · A·B·C·L 네 영역](images/sel-architecture.png)

그림의 Tester·Evaluator·Creator·Improver는 v3 SEL 명칭이다. Tester는 C의 실행기, Evaluator는 C의 채점·비교다. Creator·Improver는 L 개선 루프(7장)다. 네 역할 모두 이 문서에서 설계한다.

핵심 부품은 강조한 샌드박스 런타임과 **별도 배포한 샌드박스 Gateway**다. 운영과 같은 도구 이름·스키마로 합성 세계에서 응답하므로 에이전트 코드는 바뀌지 않고, SAP 자격증명이 없으므로 운영으로 나갈 수 없다. 채점은 실행기가 직접 모은 응답·호출 로그·최종 DB 상태로 하고, Phoenix는 열람에만 쓴다.

| 경계 | 우리 팀 | 다른 팀 |
| --- | --- | --- |
| 트레이싱 | 필요한 필드·평가 run 내용 보존 규칙 요구사항 | 계측, Collector, Phoenix 운영 |
| 도구 | 샌드박스 Gateway (별도 배포, 공통 진입점) | Tool 레지스트리, 실제 SAP 도구, op별 동작 검증(SAP 기능 담당) |
| 런타임 | 평가 실행기, 격리 요구사항 | Aegra 평가 샌드박스 인프라 (담당 미확인 → M0 게이트) |
| Gateway 밖 경로 | 목록 작성과 차단 요구 | RAG 백엔드, Personal 메일·일정 커넥터, 장기 메모리, HITL 시스템 담당 |
| 라벨 | 라벨 join | 실행 원장 |
| 자산 | 개선안 생성·판정, 승인 후 레지스트리 등록 | 자산 레지스트리 운영, 운영 배포 |

**v3 SEL과의 대응** (v3 SEL 섹션과 `eval-job/v1` 규격을 받으면 형식과 게이트를 맞춘다)

이 문서는 v3 SEL의 네 역할을 모두 설계한다. 역할 정의가 v3 문서와 다르면 차이를 정리해 설계자와 맞춘다.

| 이 문서 | v3 SEL | 맞춰야 할 것 |
| --- | --- | --- |
| A 분석 (실패 클러스터) | Creator·Improver 트리거 | 집계 단위와 트리거 기준 |
| B 시나리오·정답 suite | Tester의 평가셋 | 전달받은 요약에 따르면 v3는 운영 run 재실행(`replay_candidate`)을 전제했다(v3 원문 미확인 · Q4). 샌드박스에서 실데이터를 못 쓰면 합성 세계로 바뀌어야 하는 충돌 지점 |
| C 실행기 | Tester | 실행 요청·결과 형식은 `eval-job/v1`을 쓴다 |
| C 채점·비교·회귀 판정 | Evaluator, `regressed_cases: 0` 게이트 | 회귀의 정의와 판정 규칙 |
| L 개선 루프 | Creator·Improver | 역할 경계(7장 정의)와 후보 기록 형식 |

## 4. A · 수집·분석

A의 산출물은 두 가지다. 사람이 보는 분석 뷰와, B가 합성 환경을 만들 때 쓰는 **시나리오 템플릿**이다. 템플릿은 구조만 담고 값은 담지 않으므로 등급과 상관없이 모든 run에서 만들 수 있다.

| # | 작업 | 내용 | 메모 |
| --- | --- | --- | --- |
| A1 | Phoenix 접근 | 읽기 전용 API key, 대상 프로젝트(Business·Personal 운영, eval), 조회 한도 | 트레이싱 팀과 합의. 쓰기 권한은 요청하지 않는다 (6장 결과 저장) |
| A2 | 필드 요구사항 | 우리가 필요한 `erp.*`: run\_id, agent·skill 버전(`erp.asset.refs`), `erp.tool.op`·mode·result\_class·output.summary, `erp.data.grade`, `erp.run.source`, 평가 job·case id. 합성 데이터만 쓰는 평가 run의 내용 보존 여부도 함께 요청 | 요구사항 문서로 전달. 없는 필드는 분석 불가 항목으로 표시 |
| A3 | 수집기 (트레이싱 스케줄러) | `phoenix-client`의 `spans.get_spans_dataframe`로 시간 창 단위 조회. 기본 `limit`은 1000이고 문서에 페이지네이션이 없으므로, 결과가 limit에 닿으면 창을 쓰개 다시 조회한다. 재스캔 폭은 최대 지연 이상, `(trace_id, span_id)` 중복 제거 | 대량 조회가 부족하면 트레이싱 팀과 export 경로 협의. 시간 필터가 어느 시각에 적용되는지는 M1에서 확인 |
| A4 | run 조립·정규화 | `erp.run_id`로 span을 묶어 RunRecord/StepRecord로 정규화. 내용 유무를 `content: full / masked / none`으로 표시. RunRecord는 upsert와 버전 관리 | HITL 승인 재개는 수시간 뒤 다른 trace로 이어지므로 한 번에 완성되지 않는다 |
| A5 | 라벨 join | 실행 원장(validator, HITL, 피드백, 다음 턴 재요청) + Phoenix annotation. 출처별 열 분리 | D5 선행 |
| A6 | 분석 리포트 | 실패 서명·클러스터, skill별 성공률, 도구 op별 오류 분포, 비용·지연 | 제품이 아니라 노트북 리포트. 탐색은 Phoenix UI로 충분 |
| A7 | 시나리오 템플릿 추출 | 요청 유형(닫힌 분류 라벨) × 도구 op 시퀀스 × 결과 스키마 × 실패 유형을 구조만 뽑는다. 빈도와 실패율도 함께 | B의 입력. 포함 등급 범위는 D4 |

**템플릿이 운영 정보를 흘리지 않게 하는 규칙**: 요청 유형은 미리 정한 닫힌 분류 체계의 라벨로만 저장하고, 사용자 입력에서 나온 자유 텍스트는 B로 넘기지 않는다. 3등급 마스킹본에도 거래처명·프로젝트 코드·금액은 남기 때문이다. 표본이 최소 건수(제안 30건) 미만인 템플릿은 버린다. 희귀 업무가 있다는 사실 자체가 드러나지 않게 하기 위해서다. 1·2등급 run은 도구 op 시퀀스로만 분류하고, 분류에 LLM을 쓰면 사내 LLM만 쓴다.

**시나리오 템플릿 예시** (값이 없다는 점이 핵심)

```yaml
template_id: biz.fi.open_items_by_vendor
source: {agent: biz-finance, runs: 412, period: 2026-10, grades: [3]}   # 포함 등급은 D4
min_support: 30                    # 미만이면 템플릿을 버림
intent: fi.open_items.lookup       # 닫힌 분류 체계 라벨. 입력 원문은 저장하지 않음
tool_sequence:
  - {op: tool.sap.fi/search_vendor, mode: read}
  - {op: tool.sap.fi/query_open_items, mode: read}
result_shape:                      # erp.tool.output.summary에서
  tool.sap.fi/query_open_items: {columns: [BELNR, BUDAT, WRBTR, WAERS], rows_p50: 18, rows_p95: 240}
outcomes: {ok: 0.81, empty: 0.07, client_error: 0.09, timeout: 0.03}
failure_modes: [vendor_ambiguous, period_missing, row_limit_exceeded]
```

위 예시의 op 이름, 커럼, 수치는 형식을 보여주기 위한 가상값이다. 실제 값은 Tool 레지스트리와 M1 분석에서 채운다.

## 5. B · 합성 데이터 생성

B는 "가짜 회사" 하나를 만들고 그 안에서 시나리오와 정답을 만든다. 세계를 우리가 만들었으므로 정답을 계산할 수 있고, 그래서 LLM judge 없이 규칙으로 채점할 수 있는 범위가 넓다. 이 방식은 τ-bench(최종 DB 상태를 정답 상태와 비교)와 AppWorld(앱 9개·API 457개, 가상 사용자 약 100명, 상태 기반 테스트)가 쓴 방식과 같다.

**원칙**

1. **실값 복사 금지**: Phoenix에서 가져오는 것은 구조와 분포뿐이다. 사람 이름, 거래처, 금액 같은 값은 새로 만든다.
2. **누가 봐도 가짜인 값**: ID·코드는 예약 범위만 쓴다(예: 거래처 번호 9xxxxxxx). 이름은 "가상거래처-0418"처럼 한눈에 가상인 규칙으로 만든다. 한국어 회사명은 우연히 실존 회사와 겹치기 쉽기 때문이다.
3. **정답은 세계에서 계산**: 시나리오마다 참조 풀이(스크립트)를 두고, 그 결과를 정답으로 쓴다.
4. **동작은 우리가 검증하지 않는다**: 합성 SAP 백엔드와 참조 풀이를 같은 사람이 같은 이해로 짜면 둘이 같은 착각을 공유한다. 그러면 실제 SAP 기준으로 맞게 동작하는 에이전트가 감점된다. op마다 동작 테스트(필터 의미, 페이지네이션, row limit, 권한 오류, 통화)를 SAP 기능 담당자가 검증한다.
5. **자동 채택 없음**: 생성된 시나리오는 품질 게이트와 사람 검수를 거쳐야 suite에 들어간다.
6. **생성 LLM은 사내 LLM만**: 입력에 3등급 마스킹본이 들어갈 수 있기 때문이다.

| # | 작업 | 산출물 | 메모 |
| --- | --- | --- | --- |
| B1 | 도구 계약 수집 | 샌드박스 대상 도구 op 목록, 입력·응답 스키마, 오류 코드 | Tool 레지스트리가 원천. 합성 환경 정확도가 여기서 결정됨 |
| B2 | 합성 업무 세계 (Business) | 엔티티 모델(회사코드, 거래처, 사원, 계정, 전표 등)과 데이터. 참조 무결성과 회계 불변식(차대 일치 등) 유지, 행 수·결과 분포는 A7 템플릿에 맞춤. op별 동작 테스트 포함 | 규칙 + Faker(`ko_KR`) + 텍스트 필드만 LLM. 공개판 SDV는 학습(fit)할 실데이터가 필요하다. 메타데이터만으로 생성하는 DayZSynthesizer는 유료(Enterprise)이고 회계 불변식 보장 여부는 확인하지 못했다. 비운영 SAP 클라이언트(QA/dev)에 합성 데이터를 넣을 수 있으면 mock 대신 그걸 쓰는 안을 먼저 검토 |
| B3 | 합성 문서 (RAG) | 가짜 사내 규정·매뉴얼. 등급 메타데이터 포함 | 등급 처리 경로(GradeGuard)도 시험할 수 있음. 단, 1·2등급을 붙이면 평가 trace도 Phoenix에서 내용이 지워진다 (6장 C4) |
| B4 | Personal 페르소나 | 가짜 사용자 N명의 개인 작업 공간(일정·메일·문서 등). 페르소나마다 역할·업무·동료 관계를 갖는다 | D3 결정 후 M2b 이후에 추가. 장기 메모리도 페르소나 전용으로 분리 |
| B5 | 시나리오·정답 생성 | 템플릿 × 세계 → 사용자 목표(user simulator에 주는 숨은 지시), 초기 상태, 정답(최종 상태, 구조화된 답 필드, 금지 행동) | 답은 문자열 매칭이 아니라 구조화 필드나 숫자 정규화로 비교. "4,821만 원"과 "48,210,000원"을 같게 본다 |
| B6 | 품질 게이트 | 풀 수 있음(참조 풀이 성공), 누출 검사(예약 범위 위반 + 데이터 소유 팀의 salted hash 대조), 사람 검수 표본 | 누출의 정의는 이름 단독이 아니라 "ID 일치, 또는 (이름·금액) 튜플 일치" |
| B7 | 버전 관리 | git 하나로 `world@v`, `suite@v`, 각 시나리오의 출처 템플릿을 관리 | 도구 스키마가 바뀌면 세계와 정답을 다시 계산하는 절차를 둔다 |

## 6. C · 샌드박스 테스트·평가

샌드박스의 핵심은 **SAP 자격증명이 없는 별도 배포 샌드박스 Gateway**다. 운영 Tools Gateway에 모드 플래그를 다는 방식은 플래그가 빠지면 운영 SAP로 나가므로(fail-open) 쓰지 않는다. 같은 도구 이름·응답 스키마로 합성 세계에서 응답하므로 에이전트 코드는 바뀌지 않는다. 공통 진입점은 우리 팀 영역이라 직접 만든다.

**평가가 진행되는 방식: 실행은 자동, 판단은 사람**

| 계기 | 시작하는 주체 | 단계 |
| --- | --- | --- |
| 자산 버전 등록 | 새 skill·prompt·에이전트 버전이 등록되면 CI처럼 자동 실행 | M2a– |
| 정기 회귀 | 야간에 운영 버전으로 suite 전체. 세계·도구 스키마가 바뀌어도 통과하는지 확인 | M2a– |
| 셀프서비스 제출 | 비즈니스 영역 담당자가 에이전트 버전이나 바꾼 자산을 제출 | M4 |
| 개선 루프 후보 | Creator·Improver가 만든 후보 (7장) | M2c– |

1. 실행기가 시나리오마다 합성 세계 스냅샷을 띄운다.
2. 에이전트가 샌드박스 Gateway로 합성 DB를 조회·변경한다. M2b부터는 user simulator가 숨은 목표를 들고 사용자 역할을 하고, HITL 승인 요청은 시나리오에 적힌 정책으로 자동 응답한다.
3. 실행기가 에이전트 응답, 샌드박스 Gateway 호출 로그, 최종 DB 상태를 직접 모은다.
4. 채점기가 정답과 비교하고, 같은 시나리오를 k번 반복한 뒤 기준 버전(현재 운영 버전)과 케이스별로 짝지어 비교한다.
5. 리포트가 나온다. 여기까지 사람은 개입하지 않는다.

사람이 하는 일은 판단뿐이다. 평가에서는 시나리오를 suite에 넣을지 승인하고, 채점 결과를 표본 점검하고, 배포·승격을 결정한다. 개선 루프에서는 진단 표본 점검과 후보 승인을 한다(7장). 배포까지 자동으로 하지 않는 이유는 샌드박스와 운영의 차이가 아직 측정되지 않았기 때문이다 (D6).

**케이스 통과 기준**: 해당하는 검사를 모두 통과해야 통과다. ① 최종 상태 일치(의도하지 않은 변경 없음) ② 구조화 답이 정답과 일치 ③ 도구 호출 규칙(필수·금지) ④ 정책 준수(필요한 HITL 요청, 등급 처리). LLM judge는 규칙으로 판정할 수 없는 업무가 실제로 생길 때 보조 점수로만 추가한다.

**버전 판정 기준**: 회귀 케이스의 정의와 임계값은 7장 판정 규칙 하나만 쓴다. 가장 무거운 기준은 회귀 케이스 0개(`regressed_cases: 0`, 전달받은 v3 요약의 이름)다. 비용·지연 예산 초과도 실패로 본다.

| # | 작업 | 내용 | 메모 |
| --- | --- | --- | --- |
| C1 | 샌드박스 런타임 | Aegra 평가 샌드박스에서 에이전트 버전을 자산 참조(`erp.asset.refs`)로 고정해 실행. 체크포인터·스토어는 운영과 분리 | **M0 게이트**: 담당 팀, 버전 고정 실행, 분리된 저장소를 확인. 없으면 격리된 네임스페이스에 우리가 띄우고 공수를 M2a에 반영 |
| C1b | 외부 경로 목록과 차단 | 에이전트가 밖으로 나가는 모든 경로를 나열하고 각각 합성 대용물 또는 차단으로 지정. Gateway 밖 경로(RAG 백엔드, Personal 메일·일정, 장기 메모리, HITL 시스템) 포함. 네트워크는 기본 차단, 허용은 사내 LLM Gateway와 샌드박스 Gateway뿐 | M0 산출물. "차단 0건"은 네트워크 계층 deny 로그로 잰다 |
| C2 | 샌드박스 Gateway | 별도 배포, SAP 자격증명 없음. 같은 op·스키마, 백엔드는 합성 세계 DB. 에피소드마다 스냅샷에서 시작하고 끝나면 버린다. 호출 로그를 실행기에 넘긴다 | 합성 DB에 대한 `commit` 허용 여부는 D2. 쓰기 업무를 최종 상태로 채점하려면 필요 |
| C3 | user simulator·HITL 대역 | LLM이 숨은 사용자 목표를 들고 대화. 승인 요청은 시나리오 정책으로 자동 응답 | M2b부터. M2a는 단일 턴만 쓴다. 운영 HITL 구현(LangGraph interrupt 또는 외부 결재)을 가로챌 수 있는지 확인 필요 |
| C4 | 실행기 | suite × 에이전트 버전 × 반복 k회. 비용 한도, 동시 실행 제한. **채점 입력(응답, 호출 로그, 최종 DB 상태)을 직접 수집** | Phoenix에는 `source=eval`로 들어가지만 등급 규칙으로 내용이 지워질 수 있어 열람용으로만 쓴다 |
| C5 | 채점기 | ① 최종 상태 ② 구조화 답(숫자 정규화) ③ 도구 규칙 ④ 정책 준수 | LLM judge는 M2에 넣지 않는다. M2 시나리오는 규칙으로 채점 가능한 것만 고른다 |
| C6 | 비교·통계 | 기준 버전 대비 케이스별 짝 비교와 결과 뒤집힘(flip) 비율, pass@1과 pass^k, A/A 오판률. suite 크기는 검정력 계산으로 정한다 | 거친 추정으로 25케이스 × 5회면 10–15pp 미만 하락은 놓칠 수 있다 (검증 안 된 추정, M2a에서 실측) |
| C7 | 셀프서비스 공개 | 제출 → suite 선택 → 실행 → 리포트. 팀별 suite·결과 분리, 실행 쿼터, 감사 로그. 제출물 스커(skill·prompt의 few-shot 예시에 실값이 있는지), skill에 실행 코드가 있으면 실행 격리 | 권한은 권한체계 Gateway 연동 검토 (D8). 비즈니스 사용자에게 운영 Phoenix 계정을 주지 않는다 |

**pass^k를 쓰는 이유**: τ-bench는 같은 과제를 k번 반복해 모두 성공할 확률로 신뢰성을 잰다. n번 중 c번 성공했을 때 추정치는 C(c,k)/C(n,k)의 과제 평균이다. 업무 에이전트는 "가끔 되는 것"보다 "매번 되는 것"이 중요하므로, pass@1만 보면 불안정한 버전이 통과한다.

**결과 저장은 자체로, Phoenix는 열람만**: suite와 world는 git, 실행 결과는 자체 파일(JSONL/parquet)에 저장한다. Phoenix datasets·experiments는 쓰지 않는다. dataset이나 experiment를 만들려면 쓰기 권한(member)이 필요한데, Phoenix에는 admin·member·viewer 역할만 있고 프로젝트 단위 권한이 없어 운영 프로젝트에도 쓸 수 있게 되기 때문이다. 이렇게 하면 버전을 두 곳에서 관리하는 문제도 없어진다.

## 7. L · 개선 루프 (Creator·Improver)

C의 하네스는 "이 버전이 나아졌나"를 판정한다. 개선 루프는 "무엇을 바꿔야 나아지나"를 만든다. 지시의 "생성"에는 합성 환경(B)과 개선안(L)이 둘 다 들어간다. 둘은 따로 있지 않다. 개선안은 합성 환경 위에서만 판정할 수 있기 때문이다.

**역할 정의** (이 문서가 정한다. v3 SEL 원문은 아직 확인하지 못했다. 원문과 다르면 차이를 정리해 설계자와 맞춘다 · Q4)

| 역할 | 하는 일 | 입력 | 출력 |
| --- | --- | --- | --- |
| Tester | suite를 후보 버전과 기준 버전으로 k회 실행 | suite, 자산 버전 | 실행 기록 (C4) |
| Evaluator | 채점, 짝 비교, 아래 판정 규칙에 따른 회귀·개선 판정 | 실행 기록, 정답 | 케이스별 판정, 리포트 (C5, C6) |
| Improver | 특정 기존 자산(skill 지시문, prompt)의 결함을 고치는 증분 패치 | 실패 클러스터, 진단, 대상 자산 | 패치 후보 (diff) |
| Creator | 맞는 skill이 없거나 선택되지 않는 경우, 새 skill 또는 skill 목록·설명 수정 | 실패 클러스터, 진단 | 새 skill 후보 |

**Creator와 Improver의 경계는 진단 결과로 정한다.**
- 원인이 특정 기존 자산의 지시 결함이면 Improver가 맡는다.
- 맞는 skill이 없거나 있어도 선택되지 않으면 Creator가 맡는다.
- Creator 후보는 skill 선택(라우팅)을 바꿔 모든 케이스에 영향을 줄 수 있다. 그래서 판정에 full suite와 라우팅 회귀 검사가 필수다.
- Creator의 세부 규칙은 Improver가 한 사이클 이상 돈 뒤에 정한다.

**핵심 결정: 개선의 근거는 샌드박스에서 재현한 실행 기록에서 얻는다**

- 운영 trace만으로는 원인을 진단할 수 없다. 1·2등급 trace에는 내용이 없고, 3등급은 마스킹본이다.
- 그래서 운영에서는 "어떤 실패가 얼마나 자주"(클러스터와 빈도)만 가져오고, 원인 진단은 샌드박스에서 재현한 run으로 한다.
- 진단 입력은 C4 실행기가 직접 수집한 기록(응답, Gateway 호출 로그, 최종 상태)으로 고정한다. Phoenix의 eval trace는 등급 규칙으로 내용이 지워질 수 있다(D7).
- 합성 데이터만 쓰는 run이므로 사내 LLM에 넣어도 운영 정보가 나가지 않는다. 두 가지 전제가 있다.
  - 대상 자산(skill·prompt의 few-shot 등)이 실값 스캔을 통과했다 (C7과 같은 스캔).
  - Q1-a·1-b(QA SAP 사용)라면 QA 데이터 출처를 보안 파트가 판정했다.

**재현의 정의**

- 재현 = 운영 실패 서명(op 시퀀스, 오류 코드, result_class)과 샌드박스 실패 서명이 일치하는 것이다. 단순히 "시나리오가 실패한다"는 재현이 아니다. 운영과 다른 원인으로 실패할 수 있기 때문이다.
- 기준 실패율 = dev 시나리오에서 기준 버전이 k회 중 실패한 비율이다. 제안 기준은 0.5 이상이며, M2a 노이즈 측정 후 확정한다.
- 재현되지 않는 클러스터는 개선 대상에서 빼고 B에 시나리오 보강을 요청한다. 실데이터 특성 때문에 생긴 운영 실패는 합성 세계에서 재현되지 않으므로 계속 빠질 수 있다. 이 편향이 보이도록 **제외된 클러스터의 운영 빈도 비중**을 리포트에 매번 싣는다.

**판정 규칙** (6장 회귀 판정, 8장 지표, `regressed_cases: 0`은 모두 이 정의를 쓴다)

- 케이스마다 기준 버전과 후보 버전을 각각 k회 실행하고 통과 횟수를 센다.
- **회귀 케이스**: 기준 대비 통과 횟수 감소가 케이스 노이즈 상한을 넘는 케이스다. 노이즈 상한은 M2a에서 A/A로 측정한다(제안: A/A 감소 분포의 95% 분위).
- **개선 케이스**: 같은 기준으로 통과 횟수가 늘어난 케이스다.
- 임계값과 k는 판정 전에 고정하고, 판정 중에 바꾸지 않는다.
- `regressed_cases: 0` = 회귀 케이스가 0개. 이 이름은 전달받은 v3 요약에서 왔다(v3 원문 미확인).

**사이클** (한 사이클 = 클러스터 하나 → 후보 하나)

1. **클러스터 선택**: A6의 실패 클러스터를 빈도 × 심각도로 정렬하고, 최소 지지 건수 미만은 제외한다. 심각도는 result_class와 A5 라벨(HITL 거절, 재요청)로 매긴다. 등급표는 M1에서 정한다.
2. **재현**: dev 시나리오로 기준 실패율과 실패 서명 일치를 확인한다. held-out의 기준 실패율도 기록한다. held-out에서 기준 버전이 이미 통과하면 개선을 확인할 수 없기 때문이다.
3. **진단**: 재현된 실행 기록으로 원인 위치를 분류한다. 분류 결과는 사람이 표본 점검한다.
   - skill 지시, prompt → Improver
   - skill 없음·선택 안 됨 → Creator
   - 도구 설명 → 제안만 작성하고 도구 담당에게 이관
   - 도구 구현 결함 → 도구 담당에게 보고
   - 합성 세계, 시나리오, 참조 풀이 결함 → B에서 수정
   - 채점 결함 → C에서 수정
   - 모델 한계(자산 수정으로 해결 불가), 원인 불명 → 사이클 중단, 기록만 남김
4. **후보 생성**: 전체를 다시 쓰지 않고 증분 패치로 만든다. 클러스터당 패치 하나만 만든다.
5. **판정**: held-out 시나리오와 나머지 suite를 판정 규칙대로 돌린다. 채택 조건은 네 가지를 모두 충족하는 것이다.
   - 대상 클러스터 held-out에서 개선 케이스가 있다.
   - 전체에서 회귀 케이스가 0이다.
   - 정책 준수 케이스(HITL 요청, 등급 처리, 금지 행동)를 전부 통과한다.
   - 비용·지연이 예산 안에 있다.
6. **승인**: 승인자(D10)는 diff, 판정 리포트, held-out 실행 기록 표본을 보고 승인한다. 표본 점검이 필요한 이유는 루프가 채점의 사각을 파고들어 통과하는 경우를 사람만 잡을 수 있기 때문이다. 승인된 후보는 자산 레지스트리에 새 버전으로 등록된다.

**held-out 관리** (과적합과 오염 방지)

- dev(재현·진단·생성용)와 held-out(판정용)을 나눈다. held-out은 패치를 만드는 경로(진단자, Improver LLM)와 다른 사람·경로가 만든다.
- held-out은 같은 템플릿에서 엔티티·값을 바꾼 것만으로 채우지 않는다. 가능하면 일부를 같은 failure_mode의 다른 템플릿에서 뽑는다. 템플릿 구조에 맞춘 패치를 걸러내기 위해서다.
- Improver에게는 held-out의 통과·실패 집계만 돌려준다. 케이스 내용은 주지 않는다.
- 클러스터당 판정 시도는 2회(제안)까지다. 재시도할 때는 held-out을 새로 뽑는다. 같은 held-out으로 여러 후보를 시험하면 held-out이 dev가 되고 우연한 통과가 늘어난다.
- held-out마다 사용 횟수를 기록하고, 상한(제안 3회)을 넘으면 교체한다.

**기준 버전, 누적, 롤백**

- 기준 버전은 자산 레지스트리의 **최신 승인 버전**이다. 승인됐지만 아직 배포되지 않은 버전도 포함한다.
- 판정은 자산 단위로 직렬화한다. 판정 중에 기준 버전이 바뀌면 진행 중인 후보는 새 기준 위에서 다시 판정한다(rebase).
- 노이즈 상한 아래의 작은 하락이 누적될 수 있다. 그래서 승인 패치 N개마다(제안 5개), 그리고 배포 전에 고정 앵커 버전과 full suite로 누적 비교한다.
- 후보 기록에 parent version을 남긴다. 롤백 트리거는 두 가지다: 운영 효과 악화(8장), 샌드박스 통과·운영 회귀 발생. 롤백 결정은 승인 주체(D10)가 한다.

**잠정 원칙** (원문 미확인. 각 원칙은 괄호 안의 우리 쪽 근거로 선다. 논문은 10장에서 확인할 참고 후보다)

- release line은 하나만 둔다. (판정 비용이 후보 수에 비례한다. 추적과 롤백이 단순해진다.) 참고 후보: GEPA
- 패치는 증분으로 만든다. (전체를 다시 쓰면 잘 되던 지시가 사라지고, 사람이 diff를 검토할 수 없다.) 참고 후보: ACE
- 판정은 평균 점수가 아니라 케이스별 변화로 한다. (평균은 개선과 회귀가 상쇄돼 회귀를 숨긴다.) 참고 후보: AgentDevel
- Creator는 보수적으로 쓴다. (새 skill은 라우팅을 바꿔 영향 범위가 가장 크다.) 참고 후보: SkillsBench
- 안전 행동을 모든 판정에 넣는다. (개선 압력이 HITL 요청 같은 "비용이 드는 행동"을 줄이는 쪽으로 작용할 수 있다.) 참고 후보: Misevolution

**수정 허용 범위**

| 대상 | 허용 여부 | 이유 |
| --- | --- | --- |
| skill 지시문, prompt | 허용 (Improver) | 주 대상 |
| 새 skill | 지시문만 허용, 실행 코드 금지 (Creator) | 실행 코드는 격리·보안 검토 대상이다 (C7) |
| skill 목록·선택 설명 | 허용 (Creator), full suite와 라우팅 회귀 검사 필수 | 모든 케이스의 skill 선택에 영향을 준다 |
| 도구 설명 (description, 인자 설명) | 제안만. 도구 담당에게 이관 | 원본이 Tool 레지스트리 소유이고 다른 에이전트에도 영향. 반영하려면 Gateway 응답이 바뀌어야 한다 |
| few-shot 예시 | 합성 값만 | 실값이 들어가면 셀프서비스로 노출된다 |
| 도구 구현, 권한, Gateway 정책, 런타임 코드 | 금지 | 실행 기반이다. 바꾸면 비교 기준이 깨진다 |
| 패치 크기 | Improver·Creator 각각 상한 (D9) | 큰 diff는 사람이 제대로 검토하지 못한다 |

**후보 기록 예시** (가상값)

```yaml
candidate_id: imp-2026-11-0003
role: improver                        # creator | improver
cluster: biz.fi.period_missing        # A6 실패 클러스터
failure_signature: {ops: [search_vendor, query_open_items], error: ROW_LIMIT, result_class: client_error}
target: {asset: skill/fi-open-items, parent_version: 14}
diagnosis: 기간이 없을 때 기본값(당월) 규칙이 없어 전체 기간을 조회하고 row limit에 걸림
patch: patches/imp-2026-11-0003.diff  # 증분 diff
attempt: 1                            # 클러스터당 상한 2
evidence:
  reproduced: {set: dev, base_fail_rate: 0.8, k: 5, signature_match: true}
  judged: {set: held-out@3, set_uses: 1, eval_job: ej-0192, improved_cases: 7, regressed_cases: 0, policy_pass: true}
status: awaiting_approval
```

| # | 작업 | 내용 | 메모 |
| --- | --- | --- | --- |
| L1 | 클러스터 선택·재현 | A6 클러스터 정렬, 실패 서명 일치 확인, 기준 실패율, 제외 클러스터 비중 | 재현 안 되면 B에 시나리오 보강 요청 |
| L2 | 진단 | C4 실행 기록으로 원인 위치 분류. 사내 LLM | 분류 결과를 사람이 표본 점검 |
| L3 | Improver | 원인 위치에 맞춘 증분 패치. 클러스터당 하나 | 수정 허용 범위 표를 기계적으로 검사 |
| L4 | Creator | 새 skill, skill 목록·설명 | Improver 한 사이클 이후. full suite + 라우팅 회귀 필수 |
| L5 | 판정 연동 | 판정 규칙, held-out 관리, 기준 버전 직렬화·rebase, 누적 비교 | C4–C6 재사용 |
| L6 | 승인·등록 | diff·리포트·held-out 표본을 보는 승인 화면, 레지스트리 등록, 롤백 기록 | 운영 배포는 범위 밖 |

## 8. 지표와 수용 기준

평가 플랫폼 자체가 믿을 만한지를 재는 지표가 먼저다. 모든 지표는 계획된 산출물로 측정할 수 있는 것만 둔다. "운영 예측력"처럼 회귀 판정된 버전이 배포되지 않아 관측할 수 없는 지표는 백테스트로 바꿨다. 목표값은 모두 제안값이며 M2a 측정치를 보고 확정한다.

| 지표 | 정의 | 목표 (제안) | 측정 시점 | 역할 |
| --- | --- | --- | --- | --- |
| 변형 검출률 | 일부러 망가뜨린 버전(도구 인자 오류, skill 누락, prompt 손상 등, 심각도별) 중 회귀로 잡힌 비율 | 중대 변형 100% | M2a | 플랫폼 신뢰 기준 |
| A/A 오판률 | 같은 버전끼리 비교했을 때 회귀로 판정된 비율 | 5% 이하 | M2a | 오탐 상한 |
| 반복 노이즈 | 같은 버전 n회 실행 시 suite 점수 표준편차와 케이스별 뒤집힘 비율 | 측정 후 결정 | M2a | 회귀 판정의 노이즈 폭 |
| 백테스트 판별력 | 과거 롤백·사고 버전과 정상 버전을 샌드박스가 구분한 비율 | 측정 후 결정 | M2b | 운영 예측력의 대체 |
| 규칙 채점 비율 | 상태·구조화 답·도구 규칙만으로 판정된 케이스 비율 | M2는 100%, 이후 70% 이상 | M2a– | LLM judge 의존도 |
| 행동 현실성 | 같은 템플릿에서 샌드박스와 운영의 op 시퀀스 n-gram·호출 수·재시도 차이 | 측정 후 결정 | M2b | "샌드박스 동작 = 운영 동작"인지. 구조만 남은 trace로도 측정 가능 |
| 샌드박스 통과·운영 회귀 | 샌드박스는 통과했는데 운영에서 회귀한 버전 수 | 0으로 수렴 | M4– | 놓친 회귀 추적 |
| 누출 0건 | 예약 범위 위반 + 데이터 소유 팀 해시 대조에서 일치(ID, 또는 이름·금액 튜플)한 건수 | 0건 | 생성 때마다 | 배포 차단 |
| 차단 0건 | 네트워크 계층 deny 로그에 잡힌 샌드박스 밖 호출과, 샌드박스에서 운영 자원에 도달한 호출 | 0건 (도달) | 상시 | 배포 차단 |
| 셀프서비스 성공 | 파일럿 팀이 도움 없이 완료한 평가 비율 | 측정 후 결정 | M4 | M4 종료 기준 |

**개선 루프 지표** (M2c부터)

| 지표 | 정의 | 목표 (제안) | 역할 |
| --- | --- | --- | --- |
| 채택률 | 생성된 후보 중 판정과 승인을 모두 통과한 비율 | 측정 후 결정 | 루프 효율 |
| held-out 판정 | 채택 후보의 개선 케이스 수와 회귀 케이스 수 (7장 판정 규칙) | 회귀 0 | 채택 기준 |
| 제외 클러스터 비중 | 재현되지 않아 개선 대상에서 빠진 클러스터의 운영 빈도 합 / 전체 실패 빈도 | 측정 후 결정 | 합성 세계 편향 가시화 |
| 운영 효과 | 배포 후 해당 클러스터의 운영 발생 빈도 변화 (A6로 측정). M4부터, 배포 기록 연동 전제 | 측정 후 결정 | 샌드박스 개선이 운영에 이어지는지. 롤백 트리거 |
| 재현율 | 선택한 클러스터 중 샌드박스에서 재현된 비율 | 측정 후 결정 | 합성 세계가 운영 실패를 담는지 |
| 후보당 비용 | 진단·생성·판정의 LLM 비용 합 | 예산 이내 | 비용 통제 |

LLM judge를 도입하면 그때 "judge와 사람 판정의 일치율"을 추가한다.

## 9. 마일스톤과 작업 분해

지시의 순서는 분석 → 생성 → 평가지만, 구현은 **평가 하네스를 생성 자동화와 개선 루프보다 먼저** 만든다. 생성한 데이터와 개선안이 쓸모 있는지는 하네스로만 판단할 수 있고, 자동 생성과 자기 개선의 효과는 우리 환경에서 측정된 적이 없기 때문이다. 설계는 개선 루프(7장)까지 지금 같이 하고, 구현만 이 순서를 따른다.

- **M1과 M2a는 병행**한다. 손으로 만드는 세계가 M1에서 받는 것은 대표 업무 선정뿐인데, 이건 M0에서 Tool 레지스트리와 파일럿 팀 인터뷰로 할 수 있다. 직렬로 두면 M1(대량 조회, 라벨 의존)의 위험이 하네스까지 늦춘다.
- **M2를 M2a와 M2b로 나눈다.** 한 단계에 독립 작업 흐름 4개(런타임 격리, op별 SAP 동작 재구현, 시뮬레이터·HITL 대역, 채점·통계)와 외부 의존 3개 이상이 몰려 있었다. Personal은 D3이 정해진 뒤 M2b 이후에 추가한다. 범위에서 빼는 것이 아니라 순서를 미룬다.
- **M2c(개선 루프 v0)는 M2b와 병행**한다. 선행 조건은 두 가지다: M2a 게이트 통과, M1에서 나온 A6 실패 클러스터.
  - 대상은 단일 턴 조회 업무에서 규칙으로 채점할 수 있는 실패 유형으로 한정한다(예: period_missing, row_limit_exceeded). 되묻기처럼 대화가 필요한 수정은 user simulator(M2b) 뒤로 미룬다.
  - M2a의 시나리오 10개로는 held-out 판정의 통계력이 없다. 그래서 M2c는 대상 업무의 suite 확장을 포함한다(held-out과 나머지 suite 규모는 검정력 계산으로 정한다).
  - Creator는 Improver가 한 사이클 이상 돈 뒤에 붙인다.
- **M3는 조건부**다. 시나리오 수요가 사람이 만드는 속도를 넘을 때만 착수한다. 개선 루프가 클러스터마다 held-out 시나리오를 요구하므로 수요는 M2c에서 측정한다. 단계 간 날짜와 인력은 M0에서 추정한다.

![단계와 게이트 · M0–M4](images/sel-milestones.png)

M2a가 전체의 고비다. 여기서 하네스가 변형을 잡지 못하거나 A/A 오판이 많으면, 이후 개선 루프·생성·공개는 의미가 없다. 하네스가 회귀를 놓치면 개선 루프는 회귀를 개선으로 채택한다.

## 10. 학습·조사 로드맵

가장 먼저 알아야 할 것은 기법이 아니라 **우리 입력의 실물**(Phoenix에 실제로 무엇이 남는가)과 **도구 계약**(합성 세계의 뼈대)이다. 이 둘이 정해져야 템플릿·합성 세계·채점 설계가 가능하고, 평가 방법론은 그 다음에 읽어야 우리 상황에 맞춰 고를 수 있다. 각 항목은 "산출물"이 나오면 끝난 것으로 본다.

| --- | --- | --- | --- | --- |
| 1 (병행) | Phoenix에 남는 데이터의 실물 | 모든 설계의 입력이다. 템플릿에 무엇을 넣을 수 있는지가 여기서 정해진다 | dev Phoenix의 실제 trace, OpenInference span 종류·속성, 트레이싱 팀의 `erp.*` 계약과 등급별 제거 규칙, [Phoenix Python client](https://arize.com/docs/phoenix/sdk-api-reference/python), [spans API](https://arize-phoenix.readthedocs.io/projects/client/api/spans.html) | trace 해부 노트: 등급(1·2·3·미표시)과 HITL 재개 여부로 층화해 Business·Personal 각각 추출 |

**지금 공부하지 않아도 되는 것**: fine-tuning, 대규모 분산 실행 인프라, 자체 평가 UI. 앞의 두 개는 규모가 측정되기 전에는 필요 여부를 알 수 없고, UI는 Phoenix로 버틸 수 있는지 만저 확인한다.

## 11. 리스크, 결정 요청, 확인 필요

가장 큰 리스크는 두 가지다. 하나는 샌드박스에서 운영으로 호출이 새는 것이고, 다른 하나는 합성 환경이 운영과 달라 결과가 운영을 예측하지 못하는 것이다. 앞의 것은 구조(자격증명이 없는 별도 배포, 기본 차단 네트워크)로 막고, 뒤의 것은 백테스트와 행동 현실성 지표(8장)로 초기부터 잰다.

**리스크**

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 샌드박스 탈출 | 평가 중 운영 SAP나 외부로 호출이 나감. `commit`이면 운영 데이터 변경 | SAP 자격증명이 없는 별도 배포 Gateway, 외부 경로 목록(C1b), 네트워크 기본 차단, deny 로그 지표 |
| 평가 런타임을 확보하지 못함 | M2a 범위가 크게 늘어남 | M0 게이트. 없으면 격리 네임스페이스에 자체 구축, 공수 반영 |
| 합성 환경과 운영의 차이 | 샌드박스 통과가 운영 성공을 뜻하지 않음 | 도구 계약을 그대로 따름, 백테스트, 행동 현실성 지표, 비운영 SAP 클라이언트 활용 검토 |

| 셀프서비스 제출물의 실데이터 | few-shot 예시의 실값이 다른 팀에 노출 | 제출물 스캔, 팀별 결과 분리, 운영 Phoenix 계정 미발급 |
| user simulator의 오류 | 시뮬레이터가 틀린 말을 해 에이전트가 실패로 판정됨 | M2a는 단일 턴만. M2b부터 실패 표본을 사람이 점검하고 시뮬레이터 오류는 따로 집계 |
| 평가 비용 | suite × 버전 × k회로 LLM 호출이 빠르게 늘어남 | 팀별 쿼터, 스모크(소규모)와 전체 suite 분리 |
| suite 과적합 | 개선안이 합성 suite에만 맞고 운영에서는 효과 없음 | dev/held-out 분리, 운영 효과 지표(A6 클러스터 빈도) 추적 |
